# v0.7 — GitHub API와 Projects 동적 렌더링

## 1. 버전 목표

v0.6까지는 사용자 행동과 브라우저 내부의 값만으로 상태를 결정했다.

v0.7에서는 처음으로 **외부 서버의 데이터를 비동기로 요청하고, 요청 결과에 따라 Projects 영역의 상태와 DOM을 다시 렌더링하는 구조**를 구현한다.

이 버전의 핵심 흐름은 다음과 같다.

```text
Projects 기능 시작
        ↓
GitHub API 요청 시작
        ↓
loading 상태 렌더링
        ↓
비동기 응답 대기
        ↓
HTTP 응답 확인
        ↓
데이터 처리
        ↓

repository 있음
→ success
→ Project 카드 렌더링

repository 없음
→ empty
→ 빈 상태 렌더링

요청 또는 응답 오류
→ error
→ 오류 상태 렌더링
```

v0.7이 끝나면 최소한 다음 관계를 설명할 수 있어야 한다.

```text
왜 API 요청은 즉시 결과를 돌려주지 않는가
→ fetch는 무엇을 시작하는가
→ Promise는 여기서 무엇을 의미하는가
→ await는 무엇을 기다리는가
→ HTTP 응답이 성공인지 어떻게 판단하는가
→ 응답 데이터를 어떻게 JavaScript 데이터로 읽는가
→ loading / success / error / empty 상태는 언제 결정되는가
→ repository 데이터가 어떻게 Project 카드 DOM으로 변환되는가
→ 오류 후 Retry가 어떻게 다시 API 요청으로 연결되는가
```

이번 버전에서는 **GitHub repository 데이터를 가져와 상태별로 Projects 영역을 렌더링하는 것까지만 구현한다.**

repository 언어를 기준으로 프로젝트를 필터링하는 기능은 v0.8에서 다룬다.

---

## 2. 요구사항

### 2.1 기존 Projects 영역을 기반으로 작업

v0.1~v0.6에서 만든 기존 HTML, CSS, 반응형 레이아웃, DOM 인터랙션, 다크 모드, Contact Form validation을 유지한다.

Projects 영역은 이미 다음 기반을 가지고 있다.

```text
Projects section
        ↓
Project 목록 영역
        ↓
임시 Project article
```

v0.7에서는 v0.1에서 구조 확인용으로 사용하던 임시 Project 데이터를 **GitHub API에서 받은 실제 repository 데이터의 동적 렌더링으로 교체한다.**

기존 Projects Grid 구조는 유지한다.

불필요하게 Projects section 전체를 다시 작성하지 않는다.

---

### 2.2 GitHub API 사용

본인의 공개 GitHub repository 데이터를 다음 형태의 API에서 가져온다.

```text
https://api.github.com/users/{username}/repos
```

`{username}`에는 실제 GitHub 사용자 이름을 사용한다.

API 요청은 브라우저 JavaScript에서 수행한다.

이 버전에서는 GitHub 인증 기능이나 별도의 백엔드 서버를 만들지 않는다.

---

### 2.3 `fetch`

외부 HTTP 요청에 `fetch()`를 사용한다.

핵심 관계는 다음과 같다.

```text
fetch(API URL)
        ↓
HTTP 요청 시작
        ↓
Promise 반환
        ↓
응답이 준비될 때까지 비동기 진행
```

`fetch()` 문법 전체나 네트워크 프로그래밍 전체를 학습하지 않는다.

현재 GitHub API 요청에서 어떤 입력 URL을 사용하고 어떤 응답을 받는지 이해하는 데 집중한다.

---

### 2.4 Promise의 기본 의미

v0.7에서는 Promise를 **아직 완료되지 않은 비동기 작업의 결과를 나타내는 값**이라는 수준에서 이해한다.

기본 관계:

```text
API 요청 시작
        ↓
결과는 즉시 없음
        ↓
나중에 성공 또는 실패 결과가 결정됨
```

Promise의 내부 동작, chaining 패턴 전체, 이벤트 루프의 세부 구조까지 학습 범위를 확대하지 않는다.

이번 프로젝트에서는 Promise를 직접 복잡하게 조합하기보다 `async/await`를 통해 다룬다.

---

### 2.5 `async / await`

GitHub API 요청을 수행하는 함수는 비동기 작업을 명확하게 읽을 수 있도록 `async/await`를 사용한다.

기본 흐름:

```text
async 함수 시작
        ↓
fetch 요청
        ↓
await response
        ↓
응답 확인
        ↓
await response data
        ↓
다음 처리
```

핵심은 `await`가 사용된 코드가 **비동기 결과가 준비된 뒤 다음 단계로 이어지는 흐름을 읽기 쉽게 표현한다**는 점을 이해하는 것이다.

`async/await` 문법 전체를 별도의 장기 학습 과정으로 확대하지 않는다.

---

### 2.6 HTTP 응답 확인

네트워크 요청이 완료되었다는 사실과 요청이 성공했다는 사실을 구분한다.

GitHub API 응답을 받은 뒤 HTTP 응답이 정상 범위인지 확인한다.

기본 관계:

```text
HTTP response 도착
        ↓
성공 응답인가?

YES
→ 데이터 읽기

NO
→ error 상태 처리
```

특히 GitHub API rate limit 등으로 `403` 응답이 발생할 수 있음을 확인한다.

`403`도 사용자에게 정상 Project 카드처럼 보여서는 안 되며 error 상태로 처리한다.

HTTP 상태 코드 전체를 암기하지 않는다.

현재 프로젝트에서 최소한 다음 정도를 구분한다.

```text
정상 응답
403 rate limit 등 오류 응답
그 밖의 API 오류 응답
```

---

### 2.7 응답 데이터 읽기

정상 HTTP 응답에서 repository 데이터를 JavaScript가 사용할 수 있는 데이터로 읽는다.

핵심 흐름:

```text
HTTP response
        ↓
응답 body의 JSON 데이터 읽기
        ↓
JavaScript repository 데이터
        ↓
Projects 렌더링에 사용
```

JSON 형식 전체를 별도 학습 과정으로 만들지 않는다.

현재 GitHub API 응답이 여러 repository 객체를 포함하는 데이터라는 점과 필요한 필드를 읽을 수 있는 수준까지 다룬다.

---

### 2.8 Projects UI 상태

Projects 영역은 최소한 다음 네 상태를 구분한다.

```text
loading
success
error
empty
```

각 상태는 단순한 변수 이름으로 끝나는 것이 아니라 실제 사용자 화면에 대응해야 한다.

```text
loading
→ 데이터를 가져오는 중임을 표시

success
→ repository 카드 표시

error
→ 요청 실패 사실과 Retry 표시

empty
→ 요청은 성공했지만 표시할 repository가 없음을 표시
```

복잡한 상태 관리 라이브러리나 별도의 전역 store를 사용하지 않는다.

---

### 2.9 Loading 상태

API 요청을 시작하면 repository 데이터가 도착하기 전까지 Loading UI를 표시한다.

기본 흐름:

```text
API 요청 직전
        ↓
Projects = loading
        ↓
Loading UI 렌더링
        ↓
API 요청
```

네트워크가 빠르더라도 코드 구조상 loading 상태가 존재해야 한다.

Loading UI의 디자인 자체를 복잡하게 만들지 않는다.

예:

```text
Loading projects...
```

정도의 명확한 사용자 피드백이면 충분하다.

---

### 2.10 Success 상태와 Project 카드

API 요청에 성공하고 repository 데이터가 하나 이상 존재하면 success 상태다.

GitHub repository 데이터를 Project 카드로 변환하여 Projects Grid 안에 렌더링한다.

v0.1에서 임시 Project 구조에 사용한 정보를 기준으로 최소한 다음 데이터를 표현할 수 있다.

```text
repository 이름
repository 설명
주요 언어
GitHub repository 링크
```

GitHub API의 실제 필드 이름은 구현 과정에서 응답 데이터를 확인하여 연결한다.

B1-1 기준 문서는 카드에 표시할 모든 세부 필드를 고정하지 않는다.

따라서 stars, forks, homepage 등 추가 정보는 **v0.7 필수 요구사항으로 만들지 않는다.**

현재 학습 목표에 필요한 최소 데이터로 카드 렌더링 흐름을 이해하는 것을 우선한다.

---

### 2.11 동적 DOM 렌더링

v0.1의 정적 임시 `article`을 반복해서 직접 작성하는 대신 repository 데이터에 따라 Project 카드가 동적으로 생성되도록 한다.

핵심 관계:

```text
repository 데이터 배열
        ↓
각 repository를 카드 표현으로 변환
        ↓
Projects DOM 갱신
```

최종 카드가 기존 CSS Grid의 Grid Item으로 동작하도록 기존 class 구조를 가능한 범위에서 재사용한다.

JavaScript가 카드의 색상, 간격, Grid 배치를 직접 지정하지 않는다.

```text
JavaScript
→ 데이터와 DOM 콘텐츠 생성

CSS
→ 카드의 시각 표현과 Grid 레이아웃
```

---

### 2.12 템플릿 리터럴

동적 Project 카드의 문자열 또는 HTML 조각을 만들 때 템플릿 리터럴을 실제 기능 안에서 사용한다.

핵심 목적:

```text
고정 HTML 구조
+
repository별 데이터
        ↓
동적 카드 표현
```

템플릿 리터럴의 모든 기능을 학습하지 않는다.

현재 카드 생성 코드에서 문자열 안에 repository 데이터를 넣는 방식을 읽고 설명할 수 있으면 된다.

---

### 2.13 구조분해 할당

GitHub repository 객체에서 카드에 필요한 값을 읽을 때 구조분해 할당을 실제 코드에서 사용할 수 있다.

예시 개념:

```text
repository 객체
        ↓
name
 description
 language
 repository URL
```

구조분해 할당 문법 전체를 별도로 확대하지 않는다.

현재 API 객체에서 필요한 데이터만 꺼내는 목적을 이해한다.

---

### 2.14 `map()`

repository 데이터 여러 개를 Project 카드 표현 여러 개로 변환하는 과정에서 `map()`을 사용한다.

핵심 관계:

```text
repositories
        ↓ map
각 repository → card 표현
        ↓
card 표현들의 새 결과
```

`map()`과 `forEach()`의 모든 차이를 이론적으로 깊게 다루지 않는다.

이번 기능에서는 **데이터 배열을 다른 표현의 배열로 변환한다**는 의미를 중심으로 이해한다.

---

### 2.15 `forEach()`의 위치

`forEach()`는 v0.4에서 여러 DOM 요소에 같은 작업을 적용하는 데 이미 사용했다.

v0.7에서도 필요한 경우 반복 작업에 사용할 수 있다.

단, repository 데이터를 카드 표현으로 **변환하는 핵심 흐름은 `map()`을 실제로 사용하는 방향을 우선한다.**

`map()`과 `forEach()`를 억지로 같은 코드에 모두 넣기 위해 불필요한 반복을 만들지 않는다.

---

### 2.16 Empty 상태

HTTP 요청은 성공했지만 repository 데이터가 하나도 없다면 empty 상태를 렌더링한다.

```text
요청 성공
        ↓
repository 데이터 확인
        ↓
길이 = 0
        ↓
empty 상태
        ↓
빈 상태 메시지 표시
```

empty와 error를 구분해야 한다.

```text
empty
→ 요청 자체는 성공
→ 표시할 데이터가 없음

error
→ 요청 또는 응답 처리에 실패
```

빈 데이터에 대해 아무것도 표시하지 않는 것으로 완료하지 않는다.

---

### 2.17 Error 상태

다음과 같은 상황에서는 error 상태를 표시한다.

```text
네트워크 요청 실패
HTTP 오류 응답
응답 처리 과정의 오류
GitHub API 403 rate limit 오류
```

사용자에게 최소한 다음 사실이 보여야 한다.

```text
Projects를 불러오지 못했다.
다시 시도할 수 있다.
```

Console에 오류를 남기는 것만으로 사용자 오류 처리를 완료한 것으로 보지 않는다.

개발자는 Console에서 원인을 확인할 수 있고, 사용자는 Projects 영역에서 오류 상태를 확인할 수 있어야 한다.

---

### 2.18 GitHub API `403` rate limit 처리

GitHub API가 `403` 응답을 반환하는 경우 일반 success 또는 empty 상태로 처리하지 않는다.

기본 흐름:

```text
HTTP response
        ↓
status = 403
        ↓
rate limit 관련 오류로 판단
        ↓
error 상태 렌더링
```

사용자 메시지는 정확한 내부 구현 세부사항을 장황하게 보여줄 필요는 없지만, 데이터를 불러오지 못했다는 사실과 다시 시도할 수 있음을 알 수 있어야 한다.

GitHub 인증이나 rate limit 회피 기술을 이번 버전의 범위로 확대하지 않는다.

---

### 2.19 Retry 기능

Error 상태에는 다시 API 요청을 시도할 수 있는 Retry control을 제공한다.

기본 흐름:

```text
error 상태
        ↓
Retry 버튼 표시
        ↓
사용자 click
        ↓
API 요청 함수 다시 실행
        ↓
loading
        ↓
새 응답에 따라 success / empty / error
```

Retry는 페이지 전체를 새로고침하는 기능이 아니라 **Projects 데이터 요청 흐름을 다시 시작하는 기능**으로 구현한다.

이벤트는 `addEventListener()`를 사용한다.

---

### 2.20 상태 전환의 일관성

Projects 영역에서 이전 상태의 DOM이 다음 상태에 잘못 남지 않아야 한다.

예:

```text
error
→ Retry
→ loading
→ success
```

이때 이전 error 메시지와 Retry 버튼이 success 카드와 함께 남아 있어서는 안 된다.

반대로:

```text
loading
→ error
```

이후에도 Loading 메시지가 계속 남아 있어서는 안 된다.

현재 상태에 맞게 Projects 영역을 다시 렌더링한다.

---

### 2.21 기존 Grid와 반응형 구조 유지

v0.3에서 구현한 Projects CSS Grid를 그대로 활용한다.

동적으로 생성된 카드도 다음 기존 원칙을 유지한다.

```text
CSS Grid
repeat()
auto-fit
minmax()
```

API 기능 추가를 이유로 Grid를 JavaScript 기반 레이아웃으로 바꾸지 않는다.

모바일 / 태블릿 / 데스크톱에서 동적 카드가 기존 반응형 구조 안에서 정상 배치되어야 한다.

---

### 2.22 기존 기능과의 공존

GitHub API와 Projects 렌더링을 추가한 뒤에도 이전 버전 기능이 계속 정상 동작해야 한다.

확인 대상:

```text
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Theme Toggle
Light / Dark theme
localStorage theme 복원
Contact Form validation
```

Project 카드와 loading / error / empty 상태는 light / dark theme 모두에서 읽을 수 있어야 한다.

---

## 3. 목표 설계

v0.7 완료 시 전체 학습 구조는 다음과 같다.

```text
HTML 구조                    ← v0.1
        ↓
CSS 기본 표현                ← v0.2
        ↓
반응형 Grid                  ← v0.3
        ↓
DOM / Event                  ← v0.4
        ↓
Theme State / localStorage   ← v0.5
        ↓
Form Validation State        ← v0.6
        ↓
GitHub API Request
        ↓
fetch
        ↓
Promise
        ↓
async / await
        ↓
HTTP response
        ↓
JSON repository data
        ↓
Projects 상태 결정
        │
        ├── loading
        ├── success
        ├── error
        └── empty
        ↓
Projects DOM 렌더링
```

API 요청 전체 흐름:

```text
Projects 기능 시작
        ↓
loading 렌더링
        ↓
fetch GitHub API
        ↓
await response
        ↓
HTTP 응답 확인
        ↓

오류 응답 / 요청 실패
→ error
→ 오류 메시지 + Retry

정상 응답
→ repository 데이터 읽기
        ↓

0개
→ empty

1개 이상
→ success
→ Project cards
```

Retry 흐름:

```text
error
        ↓
Retry click
        ↓
같은 API 요청 함수 재실행
        ↓
loading
        ↓
새 결과 렌더링
```

이전 상태→렌더링 흐름과 연결하면 다음처럼 확장된다.

```text
v0.5
사용자 click
→ theme 상태
→ theme UI

v0.6
사용자 input / submit
→ validation 상태
→ Form UI

v0.7
외부 API 요청 / 응답
→ loading / success / error / empty 상태
→ Projects UI
```

v0.7은 **외부 비동기 데이터가 화면 상태를 결정하는 첫 번째 단계**다.

## 4. 새롭게 배우는 개념

### 4.1 외부 데이터

지금까지 화면에서 사용한 값은 HTML에 이미 있거나 사용자가 브라우저에서 입력한 값이었다.

v0.7에서는 데이터가 웹페이지 밖의 GitHub 서버에 존재한다.

```text
브라우저
        ↓ 요청
GitHub API
        ↓ 응답
브라우저
        ↓
DOM 렌더링
```

외부 데이터가 화면에 나타나기까지 네트워크 요청 과정이 필요하다는 것을 이해한다.

---

### 4.2 동기와 비동기의 기본 차이

일반적인 순차 코드는 앞의 작업 결과를 즉시 사용할 수 있는 경우가 많다.

네트워크 요청은 결과가 돌아오기까지 시간이 필요하다.

```text
요청 시작
→ 즉시 repository 데이터가 생기는 것이 아님
→ 응답을 기다리는 시간이 존재
```

비동기 프로그래밍 전체 이론으로 확대하지 않는다.

현재 API 요청이 왜 별도의 비동기 처리를 요구하는지만 이해한다.

---

### 4.3 `fetch()`

브라우저에서 HTTP 요청을 시작하는 API라는 수준에서 이해한다.

현재 프로젝트에서는 GitHub repository endpoint를 요청한다.

```text
URL
→ fetch
→ Promise
→ HTTP response
```

---

### 4.4 Promise

아직 완료되지 않은 작업의 미래 결과를 표현한다는 수준에서 이해한다.

현재 프로젝트에서는 다음 질문에 답할 수 있으면 된다.

```text
왜 fetch() 직후에 repository 데이터가 바로 있는 것이 아닌가?
왜 await가 필요한가?
```

Promise 생성자나 고급 Promise 조합은 다루지 않는다.

---

### 4.5 `async`

함수가 비동기 작업을 포함하고 `await`를 사용할 수 있는 함수라는 의미를 현재 코드에서 이해한다.

함수 설계 이론 전체로 확대하지 않는다.

---

### 4.6 `await`

Promise로 표현되는 비동기 결과가 준비될 때까지 해당 비동기 함수의 다음 처리를 이어가기 전에 기다리는 형태로 이해한다.

```text
await fetch(...)
→ response를 받은 뒤 다음 줄 처리
```

브라우저 전체가 멈춘다고 이해하지 않는다.

---

### 4.7 HTTP Request / Response

API 통신을 최소한 다음 관계로 이해한다.

```text
Request
→ 브라우저가 GitHub에 repository 데이터를 요청

Response
→ GitHub가 요청 결과를 돌려줌
```

HTTP 메서드, 헤더, 프로토콜 전체를 학습 범위로 확대하지 않는다.

현재 공개 repository 조회 흐름에 필요한 수준만 다룬다.

---

### 4.8 HTTP 성공과 실패

응답 객체가 도착했다고 해서 항상 원하는 데이터 요청에 성공한 것은 아니라는 점을 이해한다.

```text
response 도착
        ↓
HTTP 상태 확인
        ↓
정상 / 오류 판단
```

특히 `403` rate limit을 error로 처리하는 이유를 설명할 수 있어야 한다.

---

### 4.9 JSON

GitHub API가 구조화된 데이터를 응답으로 제공하고 이를 JavaScript 데이터로 읽어 사용한다는 수준에서 이해한다.

JSON 문법 전체를 암기하지 않는다.

API 응답에서 repository 객체와 필요한 속성을 확인할 수 있으면 된다.

---

### 4.10 `try / catch`

비동기 요청이나 데이터 처리 중 오류가 발생할 수 있는 코드를 처리하는 구조로 이해한다.

기본 관계:

```text
try
→ 정상적으로 실행을 시도할 코드

오류 발생
→ catch
→ error 상태 처리
```

오류를 숨기는 용도로 사용하지 않는다.

사용자에게 error UI를 보여 주면서 개발자는 Console에서 원인도 확인할 수 있어야 한다.

---

### 4.11 API 상태

v0.7의 상태는 사용자가 직접 선택한 값이 아니라 **비동기 요청의 진행 상황과 결과**에 의해 결정된다.

```text
요청 시작
→ loading

성공 + 데이터 있음
→ success

성공 + 데이터 없음
→ empty

실패
→ error
```

이 네 상태가 동시에 화면에 나타나는 것이 아니라 현재 상황에 맞는 하나의 UI로 연결된다는 것을 이해한다.

---

### 4.12 Loading State

비동기 작업이 끝나지 않았다는 사실도 사용자에게 의미 있는 UI 상태라는 것을 이해한다.

데이터가 늦게 오는 동안 빈 화면만 보여 주는 것과 loading 상태를 표시하는 것의 차이를 이해한다.

---

### 4.13 Success State

API 요청과 데이터 해석이 성공했고 화면에 표시할 repository가 존재하는 상태다.

success는 단순히 HTTP 응답을 받았다는 뜻이 아니라 현재 Projects 화면에 렌더링할 데이터가 준비되었다는 의미로 이해한다.

---

### 4.14 Empty State

정상 응답이지만 표시할 데이터가 없는 상태를 error와 구분한다.

```text
empty ≠ error
```

이 차이는 이후 다른 데이터 기반 UI에서도 반복되는 중요한 패턴이다.

---

### 4.15 Error State

요청 또는 처리에 실패했을 때 사용자에게 정상 데이터가 없는 이유를 알려 주는 상태다.

Console 오류와 사용자용 error UI의 목적 차이를 이해한다.

---

### 4.16 Retry

실패한 작업을 사용자가 다시 실행할 수 있게 하는 인터랙션이다.

새로운 별도 로직을 만드는 것이 아니라 기존 API 요청 흐름을 다시 시작한다.

```text
Retry click
→ fetch 함수 재실행
```

이 구조를 통해 이벤트 처리와 비동기 상태 변화가 연결된다.

---

### 4.17 동적 렌더링

HTML에 Project 카드 수가 고정되어 있지 않고 데이터 개수에 따라 DOM 결과가 달라지는 것을 이해한다.

```text
repository 2개
→ 카드 2개

repository 8개
→ 카드 8개
```

데이터가 화면 구조를 결정하는 경험이 핵심이다.

---

### 4.18 템플릿 리터럴

동적 문자열 안에 JavaScript 값을 넣을 수 있다는 것을 Project 카드 생성과 연결해서 이해한다.

단순 문법 연습이 아니라 실제 repository 데이터를 HTML 표현과 연결하는 도구로 사용한다.

---

### 4.19 구조분해 할당

repository 객체에서 필요한 속성을 명확하게 꺼내 사용할 수 있다는 수준에서 이해한다.

객체 문법 전체를 별도 학습 과정으로 확대하지 않는다.

---

### 4.20 `map()`

원본 repository 데이터 각각을 Project 카드 표현으로 변환하여 새로운 결과를 만드는 배열 메서드로 이해한다.

```text
repository 배열
→ map
→ card 표현 배열
```

v0.8의 `filter()`와 혼동하지 않는다.

```text
v0.7 map
→ 각 데이터를 다른 표현으로 변환

v0.8 filter
→ 조건에 맞는 데이터만 선택
```

---

### 4.21 DevTools Network / Console

API 기능이 예상대로 동작하지 않을 때 브라우저 DevTools에서 최소한 다음을 확인할 수 있어야 한다.

```text
Console
→ JavaScript 오류

Network
→ GitHub API 요청이 발생했는가
→ 응답 상태는 무엇인가
→ 요청 URL은 올바른가
```

문제가 생겼다고 전체 코드를 다시 작성하지 않는다.

## 5. 완료 / 검증 기준

### 5.1 GitHub API 요청

본인의 GitHub username을 사용하는 repository endpoint로 실제 요청이 발생한다.

DevTools Network에서 요청을 확인할 수 있다.

---

### 5.2 `fetch` / `async` / `await`

GitHub API 요청 코드에 `fetch()`와 `async/await`가 실제로 사용된다.

각각이 어떤 역할인지 설명할 수 있다.

---

### 5.3 `try / catch`

API 요청과 관련된 오류를 처리하는 구조가 존재한다.

오류가 발생해도 Projects 영역이 무반응 상태로 끝나지 않는다.

---

### 5.4 HTTP 응답 확인

응답이 도착한 뒤 성공 여부를 확인한다.

HTTP 오류 응답을 정상 repository 데이터처럼 처리하지 않는다.

`403` 응답은 error 상태로 처리하는 코드 경로가 존재한다.

---

### 5.5 Loading

API 요청이 시작될 때 Projects 영역에 loading 상태가 존재한다.

이전 카드나 error 메시지가 loading UI와 잘못 섞여 있지 않다.

---

### 5.6 Success

API 요청에 성공하고 repository가 존재하면 실제 repository 데이터로 Project 카드가 표시된다.

최소한 다음 정보가 카드에 연결된다.

```text
repository 이름
설명
주요 언어
GitHub repository 링크
```

API 응답에서 각 값이 어떤 속성과 연결되는지 설명할 수 있다.

---

### 5.7 동적 카드 수

Project 카드 수가 HTML에 고정되어 있지 않다.

API가 반환한 repository 데이터 개수에 따라 렌더링 결과가 달라진다.

v0.1의 임시 Project 데이터가 최종 Projects 목록으로 그대로 남아 있지 않는다.

---

### 5.8 기존 Grid 유지

동적으로 생성된 카드가 v0.3의 CSS Grid 안에서 정상적으로 배치된다.

모바일 / 태블릿 / 데스크톱에서 카드 때문에 레이아웃이 깨지지 않는다.

---

### 5.9 템플릿 리터럴

동적 Project 카드 생성에 템플릿 리터럴이 실제로 사용된다.

왜 일반 정적 HTML만으로는 현재 데이터 개수에 대응하기 어려운지 설명할 수 있다.

---

### 5.10 구조분해 할당

GitHub API repository 객체에서 필요한 값을 읽는 실제 코드에 구조분해 할당을 사용한다.

무엇을 꺼내는지 설명할 수 있다.

---

### 5.11 `map()`

repository 데이터를 Project 카드 표현으로 변환하는 과정에 `map()`을 사용한다.

`map()`이 원본 데이터에서 무엇을 새로운 결과로 만드는지 설명할 수 있다.

---

### 5.12 Empty

repository 데이터가 빈 배열인 상황에서 Project 카드 대신 명확한 empty UI가 표시된다.

검증 과정에서는 현재 코드 경로를 임시 빈 데이터로 실행하는 등의 방법으로 empty 렌더링을 직접 확인할 수 있다.

검증을 위해 임시 변경했다면 확인 후 원래 API 흐름으로 되돌린다.

---

### 5.13 일반 Error

API 요청 실패 또는 비정상 응답 상황에서 error UI가 표시된다.

검증 과정에서는 임시로 잘못된 endpoint를 사용하거나 DevTools의 네트워크 차단 기능 등으로 오류 경로를 확인할 수 있다.

검증 후 정상 endpoint로 반드시 복원한다.

---

### 5.14 `403` rate limit

코드에서 GitHub API `403` 응답을 error 상태로 처리한다.

실제 rate limit을 인위적으로 소진하는 것을 검증 목표로 삼지 않는다.

다음 두 가지를 확인하면 된다.

```text
403 응답을 정상 데이터로 처리하지 않는 코드가 있는가
403이 발생하면 사용자 error UI로 이어지는가
```

---

### 5.15 Retry

Error UI의 Retry를 사용하면 페이지 전체 새로고침 없이 GitHub API 요청을 다시 실행한다.

Retry 후 다음 흐름이 다시 시작된다.

```text
loading
→ success / empty / error
```

---

### 5.16 상태 간 정리

다음 전환을 확인한다.

```text
loading → success
loading → empty
loading → error
error → Retry → loading
```

각 전환 후 이전 상태 UI가 잘못 남아 있지 않는다.

---

### 5.17 Light / Dark Theme

다음 UI가 light와 dark theme 모두에서 읽을 수 있다.

```text
Project cards
Loading
Error
Retry
Empty
```

GitHub API 추가 때문에 기존 theme 상태 유지가 깨지지 않는다.

---

### 5.18 기존 기능 회귀 확인

다음 기능이 계속 정상 동작한다.

```text
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Theme Toggle
localStorage theme 복원
Contact Form validation
```

---

### 5.19 Console / Network 확인

정상 동작 시 현재 구현으로 인한 예상하지 못한 JavaScript 오류가 Console에 없어야 한다.

Network에서 GitHub API 요청 URL과 응답 상태를 직접 확인할 수 있어야 한다.

---

### 5.20 프로젝트 필터 없음

v0.7에서는 다음이 아직 존재하지 않아야 한다.

```text
언어별 Filter UI
현재 filter 상태
Array.filter() 기반 repository 선택
filter 결과 재렌더링
```

이 기능들은 v0.8에서 구현한다.
