# v1.0 — B1-1 기본 완료 / 배포

## 1. 버전 목표

v0.9까지 구현한 B1-1 기능 전체를 `final-design.md`의 완료 조건과 대조하여 검증하고, GitHub Pages에 배포하여 **외부에서 접근 가능한 제출 가능한 v1.0 상태**로 만든다.

v1.0은 새로운 핵심 기능을 추가하는 버전이 아니다.

핵심 목표는 다음 네 가지다.

```text
1. v0.1 ~ v0.9에서 구현한 기능 전체
   → final-design.md와 최종 대조

2. 로컬에서 정상 동작하는 사이트
   → GitHub Pages에 배포

3. 배포된 사이트
   → 실제 배포 환경에서 다시 검증

4. 프로젝트 결과
   → README / 스크린샷 / 버전 기준점으로 정리
```

전체 흐름은 다음과 같다.

```text
v0.9 로컬 완성 상태
        ↓
final-design.md 요구사항 대조
        ↓
누락 / 회귀 최소 수정
        ↓
GitHub repository 최종 확인
        ↓
GitHub Pages 배포
        ↓
배포 URL에서 전체 기능 재검증
        ↓
README 최종 정리
        ↓
스크린샷 정리
        ↓
최종 제출 체크
        ↓
git tag v1.0
```

v1.0이 끝나면 최소한 다음을 설명할 수 있어야 한다.

```text
왜 로컬에서 정상이라는 사실만으로 완료가 아닌가
→ GitHub Pages는 무엇을 배포하는가
→ 배포 환경에서 무엇을 다시 확인해야 하는가
→ final-design.md와 실제 결과를 어떻게 대조하는가
→ README는 어떤 정보를 전달해야 하는가
→ 스크린샷은 어떤 상태를 증명해야 하는가
→ 구현 기준값을 왜 README에 기록하는가
→ git tag v1.0은 어떤 기준점을 남기는가
```

v1.0은 **B1-1 필수 요구사항 전체 + 이 프로젝트에서 필수로 승격한 프로젝트 필터링**의 완료 기준이다.

v1.1 이후 확장 기능은 v1.0 완료 후에만 진행한다.

## 2. 요구사항

### 2.1 v0.9 완료 상태를 기반으로 작업

v1.0은 v0.9에서 이미 완성된 기능 구현을 유지한다.

현재 사이트에는 최소한 다음 기능이 존재해야 한다.

```text
HTML 의미 구조
CSS 기본 표현
반응형 레이아웃
Flexbox Navigation
Grid Projects
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Light / Dark theme
localStorage theme 복원
Contact Form validation
GitHub API
loading / success / error / API empty
403 rate limit error 처리
Retry
Projects 동적 렌더링
Projects language filter
Filter empty
Intersection Observer scroll animation
```

v1.0에서는 위 기능을 다시 설계하거나 대규모 리팩터링하지 않는다.

기능 누락이나 배포 환경에서의 문제를 발견했을 때만 필요한 범위에서 최소 수정한다.

### 2.2 `final-design.md`를 최종 완료 기준으로 사용

v1.0의 최종 기준 문서는 `final-design.md`다.

단순히 다음처럼 판단하지 않는다.

```text
사이트가 보기 좋다
→ 완료
```

또는:

```text
브라우저에서 대략 동작한다
→ 완료
```

대신 다음 흐름으로 판단한다.

```text
final-design.md 요구사항
        ↓
현재 구현 확인
        ↓
충족 / 미충족 판단
        ↓
미충족 항목만 최소 수정
        ↓
다시 검증
```

v0.1~v0.9 문서는 구현 과정의 기준이고, v1.0에서는 `final-design.md`의 최종 상태와 실제 산출물이 일치하는지를 확인한다.

### 2.8 Projects GitHub API 최종 검증

```text

```

다음 흐름이 유지되어야 한다.

```text
API 요청
        ↓
loading
        ↓
HTTP 응답
        ↓
정상 데이터
→ success 또는 API empty

오류
→ error
→ Retry
```

최종 코드에서 다음 개념이 실제 기능에 사용되고 있어야 한다.

```text
fetch
async / await
try / catch
HTTP 응답 확인
JSON data
```

403 rate limit 오류도 일반 success 상태로 처리하지 않는다.

### 2.9 Projects 상태 UI 최종 검증

Projects 영역은 최소한 다음 상태를 구분한다.

```text
loading
success
error
API empty
Filter empty
```

각 상태는 화면에서 의미가 구분되어야 한다.

```text
loading
→ 데이터를 가져오는 중

success
→ repository cards

error
→ 불러오기 실패 + Retry

API empty
→ 원본 repository 데이터 없음

Filter empty
→ 원본은 존재하지만 현재 filter 결과 없음
```

이전 상태의 UI가 다음 상태에 잘못 남지 않아야 한다.

예:

```text
error
→ Retry
→ loading
→ success

결과
→ 이전 error 메시지와 Retry가 남아 있지 않음
```

### 2.10 Projects 동적 카드 최종 검증

GitHub repository 데이터가 정적인 임시 카드가 아니라 동적으로 카드로 변환되어야 한다.

최소 표현 데이터:

```text
repository 이름
repository 설명
주요 언어
GitHub repository 링크
```

기존 설계에 따라 다음 역할 분리가 유지되어야 한다.

```text
JavaScript
→ 데이터 처리 / DOM 콘텐츠 생성

CSS
→ 카드 시각 표현 / Grid 레이아웃
```

Project 카드 레이아웃은 CSS Grid를 사용한다.

반응형 Grid에서 다음 개념을 유지한다.

```text
auto-fit
minmax()
```

### 2.11 Project Filter 최종 검증

프로젝트 필터링은 이 프로젝트에서 v1.0 필수 기능이다.

기본 흐름:

```text
API 성공
→ 원본 repositories 유지

사용자 filter 선택
→ currentFilter 변경
→ 원본 repositories에 filter()
→ filtered repositories
→ map()
→ DOM 재렌더링
```

반드시 확인한다.

```text
All
→ 전체 원본 repository 표시

Language 선택
→ 해당 language만 표시

조건에 맞는 항목 없음
→ Filter empty
```

필터 선택 때마다 GitHub API를 다시 호출하지 않는다.

DevTools Network에서 확인한다.

```text
초기 로드
→ API request 있음

filter click
→ 새로운 API request 없음

Retry
→ API request 다시 있음
```

예:

```text

forEach()
→ 여러 DOM 요소에 같은 작업 적용
```

### 2.13 Contact Form 최종 검증

Contact Form에는 다음 입력이 존재한다.

```text
Name
Email
Message
Submit
```

각 입력에는 올바르게 연결된 `label`이 있어야 한다.

Validation 흐름은 다음과 같다.

```text
submit
→ preventDefault()
→ 입력값 읽기
→ 필수값 검사
→ 이메일 형식 검사
→ valid / invalid 결정
→ 오류 또는 성공 UI
```

확인 항목:

```text
빈 Name
빈 Email
잘못된 Email 형식
빈 Message
모든 값 valid
오류 수정 후 input 상태 갱신
```

v1.0의 성공 메시지는 **실제 전송 성공**을 의미하지 않는다.

실제 Form 전송은 v1.2 범위다.

### 2.14 Theme 최종 검증

Theme Toggle을 통해 다음 전환이 가능해야 한다.

```text
light ↔ dark
```

기본 구조:

```text
사용자 click
→ theme 상태 변경
→ DOM data-theme 변경
→ CSS 변수 집합 변경
→ 화면 변경
→ localStorage 저장
```

새로고침 후 저장된 사용자 theme가 복원되어야 한다.

확인한다.

```text
light 선택
→ 새로고침
→ light 유지

dark 선택
→ 새로고침
→ dark 유지
```

사용자 저장값이 없을 때 시스템 theme를 감지하지 않는다.

`prefers-color-scheme` 및 실시간 OS 변경 반영은 v1.3 범위다.

### 2.16 Intersection Observer 최종 검증

v0.9에서 구현한 스크롤 진입 애니메이션을 유지한다.

기본 흐름:

```text
관찰 대상
→ Intersection Observer
→ viewport 교차
→ threshold 충족
→ callback
→ visible 계열 class 추가
→ CSS transition
```

확인 사항:

```text
관찰 대상이 정상 등록됨
viewport 진입 시 class 변경
애니메이션 후 콘텐츠 정상 표시
기존 scroll event와 충돌 없음
Projects filter / Retry와 충돌 없음
```

B1-1은 threshold `0.2 이상`을 권장하지만 고정값은 아니다.

다른 threshold를 사용했다면 README에 실제 값을 기록한다.

### 2.23 Git repository 최종 확인

배포 전에 repository의 기본 상태를 확인한다.

최소 확인:

```text
index.html 존재
CSS 파일 경로 정상
JavaScript 파일 경로 정상
images 경로 정상
README.md 위치 정상
docs 문서 위치 정상

```

브라우저에서만 보이고 Git에 commit되지 않은 파일에 의존하지 않는지 확인한다.

예:

```text

하지만 Git에 commit되지 않음
→ GitHub Pages에서는 이미지가 깨질 수 있음
```

배포 대상 파일이 repository에 실제로 포함되어 있어야 한다.

### 2.24 GitHub Pages 배포

최종 사이트를 GitHub Pages에 배포한다.

핵심 개념은 다음이다.

```text
로컬 프로젝트
        ↓
Git repository
        ↓
GitHub remote repository
        ↓
GitHub Pages 배포 설정
        ↓
공개 URL
```

정확한 Pages 설정 방식은 현재 GitHub repository의 구조에 맞춰 선택한다.

v1.0의 목표는 **외부에서 접근 가능한 배포 URL이 존재하는 것**이다.

배포 방법 자체를 CI/CD 전반 학습으로 확대하지 않는다.

---

### 2.25 로컬과 배포 환경의 차이 확인

로컬 Live Server에서 정상이어도 GitHub Pages에서는 다르게 동작할 수 있다.

따라서 다음을 구분한다.

```text
로컬 검증
→ 내 PC의 개발 환경에서 동작

배포 검증
→ GitHub Pages URL에서 실제 사용자 환경처럼 동작
```

특히 다음 문제를 확인한다.

```text
상대 경로
파일명 대소문자
이미지 경로
CSS / JavaScript 로드
GitHub API 호출
Navigation hash link
localStorage
```

문제가 발생하면 배포 환경에서 관찰한 실제 원인을 기준으로 최소 수정한다.

---

### 2.26 배포 URL에서 전체 기능 재검증

GitHub Pages 배포에 성공한 것만으로 완료하지 않는다.

배포된 URL에서 최소 다음을 다시 확인한다.

```text
반응형 레이아웃
Hamburger menu
Navigation / CTA 이동
smooth scroll
Scroll-to-Top
Navigation scrolled style
Theme Toggle
localStorage theme 복원
Contact Form validation
GitHub API
loading / success / error / empty
Retry
Projects filter
Filter empty
Intersection Observer
```

배포 URL에서 DevTools Console과 Network도 확인한다.


### 2.32 v1.0 tag

모든 최종 검증이 끝난 뒤 현재 commit을 B1-1 기본 완료 기준점으로 표시할 수 있다.

```text
git tag v1.0
```

Tag는 기능을 추가하는 도구가 아니라 **이 commit이 v1.0 완료 상태라는 이름표를 붙이는 기준점**으로 이해한다.

Tag를 만들기 전에 다음이 모두 완료되어 있어야 한다.

```text
최종 요구사항 충족
GitHub Pages 배포
배포 환경 검증
README 완료
스크린샷 완료
Console 오류 확인
```

Tag 운영을 Git 고급 브랜치 전략 학습으로 확대하지 않는다.

v1.0은 기능 개발 흐름이 아니라 **완료 판정 흐름**으로 본다.

```text
v0.9

로컬 통합 완료

final-design.md 대조
        ↓

        ↓
스크린샷
        ↓

```

검증 대상은 기능별로 다음과 같이 연결된다.

```text
├── Skills

├── Hamburger
├── smooth scroll
├── Scroll-to-Top
├── Navigation scroll state
├── Theme state / localStorage
├── Form validation
├── GitHub API state
├── Project filter state

Delivery
├── GitHub repository
├── GitHub Pages
├── README
```

```text
        ↓

YES
→ v1.0 완료
```

## 4. 새롭게 배우는 개념

### 4.1 구현 완료와 프로젝트 완료의 차이

v0.9까지는 기능 구현을 완료했다.

하지만 프로젝트 완료에는 다음이 추가로 필요하다.

```text
기능 구현
+
요구사항 대조
+
실제 배포
+
배포 검증
+
결과물 문서화
```

즉 다음은 다르다.

```text
내 PC에서 동작한다
≠
외부에서 제출 가능한 프로젝트가 완성됐다
```

---

### 4.2 Acceptance Criteria

완료 기준은 "느낌상 완성"이 아니라 미리 정한 조건으로 판단한다.

현재 프로젝트에서는 `final-design.md`가 사실상 v1.0의 acceptance criteria 역할을 한다.

기본 구조:

```text
Requirement
→ 실제 구현 확인
→ Expected result와 비교
→ Pass / Fail
```

테스트 자동화 체계를 새로 만드는 것이 목적은 아니다.

현재 미션에서는 사람이 직접 브라우저와 DevTools를 사용해 검증하는 수준으로 이해한다.

---

### 4.3 Regression의 최종 의미

v0.9에서 회귀 확인을 이미 수행했다.

v1.0에서는 배포와 최종 수정 이후에도 다시 확인한다.

```text
문제 하나 수정
→ 다른 기능이 깨지지 않았는가?
```

특히 최종 경로 수정이나 README 직전의 작은 코드 변경도 회귀를 만들 수 있으므로 최종 확인이 필요하다.

---

### 4.4 로컬 환경과 배포 환경

개발 중에는 Live Server를 사용했다.

v1.0에서는 실제 GitHub Pages 환경을 확인한다.

```text
Local
→ 내 컴퓨터의 파일과 개발 서버

Deployment
→ GitHub가 제공하는 공개 웹 환경
```

같은 HTML/CSS/JavaScript라도 파일 경로나 배포 상태에 따라 결과가 달라질 수 있다.

---

### 4.5 Deployment

Deployment는 개발한 웹사이트를 사용자가 실제로 접근할 수 있는 환경에 올리는 과정이다.

현재 프로젝트에서는 GitHub Pages를 사용한다.

개념 구조:

```text
소스 코드
→ GitHub repository
→ Pages가 정적 파일 제공
→ 브라우저가 공개 URL로 요청
→ 사이트 표시
```

서버 운영, Docker, 클라우드 인프라, CI/CD 전체를 학습하지 않는다.

---

### 4.6 정적 사이트 배포

현재 B1-1 사이트는 HTML, CSS, JavaScript로 구성된 정적 프런트엔드 사이트다.

GitHub Pages는 이 결과물을 공개 URL로 제공할 수 있다.

이번 단계에서는 다음 수준을 이해하면 충분하다.

```text
브라우저가 HTML 요청
→ HTML이 CSS / JS / 이미지 요청
→ 파일 경로가 올바르면 정상 로드
```

별도 백엔드 서버를 추가하지 않는다.

---

### 4.7 상대 경로와 배포

로컬과 배포에서 파일 경로 문제를 확인한다.

예:

```text
index.html
→ css/style.css
→ js/script.js
→ images/profile.jpg
```

핵심은 **HTML 문서 기준으로 브라우저가 실제 파일을 찾을 수 있는 경로인가**를 확인하는 것이다.

경로 문제를 해결하기 위해 새로운 빌드 도구를 추가하지 않는다.

---

### 4.8 파일명 대소문자

배포 환경에서는 파일명 대소문자 차이가 문제로 드러날 수 있다.

예:

```text
HTML: images/Profile.jpg
실제 파일: images/profile.jpg
```

로컬 환경에 따라 우연히 동작하더라도 배포에서는 실패할 수 있다.

따라서 실제 repository의 파일명과 코드의 경로를 확인한다.

---

### 4.9 Public URL

배포가 완료되면 다른 사람이 자신의 로컬 파일 없이 URL만으로 사이트에 접근할 수 있다.

이 공개 URL은 README의 핵심 정보다.

```text
Repository URL
→ 소스 코드를 보는 위치

GitHub Pages URL
→ 완성된 사이트를 실행해서 보는 위치
```

둘을 구분한다.

---

### 4.10 배포 환경에서의 DevTools

배포된 사이트에서도 DevTools를 사용할 수 있다.

최소 확인:

```text
Console
→ JavaScript error

Network
→ CSS / JS / image
→ GitHub API request

Elements
→ DOM / state class

Application
→ localStorage
```

로컬에서 사용한 검증 방법을 배포 환경에도 적용한다.

---

### 4.11 README의 역할

README는 프로젝트를 처음 보는 사람이 결과물을 이해하는 입구다.

현재 v1.0에서는 최소한 다음 질문에 답해야 한다.

```text
무엇을 만들었는가?
어떤 기술을 사용했는가?
어디에서 실행할 수 있는가?
화면은 어떤 모습인가?
```

문서 작성 자체를 별도의 기술 문서 프로젝트로 확대하지 않는다.

---

### 4.12 스크린샷의 역할

스크린샷은 단순 장식이 아니라 구현 결과의 빠른 시각적 증거다.

최소 다음 상태를 보여준다.

```text
Desktop
Mobile
Dark mode
```

스크린샷을 통해 반응형과 theme 구현 상태를 빠르게 확인할 수 있다.

---

### 4.13 구현값과 문서값의 일치

README에 기준값을 기록할 때 코드의 실제 값과 일치해야 한다.

예:

```text
코드 threshold = 0.25
README threshold = 0.2
```

이 상태는 잘못된 문서다.

따라서 먼저 코드를 확인하고 실제 값을 기록한다.

---

### 4.14 최종 검증과 증거

완료를 판단할 때 다음 세 가지를 함께 사용한다.

```text
코드 확인
→ 요구 구현이 존재하는가

브라우저 확인
→ 실제 동작하는가

DevTools 확인
→ 상태 / 요청 / 오류를 확인할 수 있는가
```

단순히 코드가 존재한다고 기능이 정상이라고 판단하지 않는다.

---

### 4.15 Release 기준점으로서의 `v1.0`

`v1.0`은 단순한 숫자가 아니라 현재 프로젝트에서 정의한 **B1-1 기본 완료 상태의 기준점**이다.

```text
v0.x
→ v1.0을 만드는 개발 단계

v1.0
→ 기본 완료 상태

v1.1+
→ 확장 기능
```

따라서 `v1.0` tag는 확장 기능을 시작하기 전 안정적인 완료 지점을 표시한다.

---

### 4.16 Git Tag

Git tag는 특정 commit에 이름을 붙여 중요한 버전 기준점을 표시하는 기능이라는 수준에서 이해한다.

```text
특정 commit
→ tag: v1.0
```

브랜치 전략, semantic versioning 전체 이론, release automation까지 확장하지 않는다.

이번 프로젝트에서는 다음 의미만 이해하면 된다.

```text
이 commit이 B1-1 기본 완료 상태다.
```

---

### 4.17 최종 범위 통제

v1.0에서 가장 중요한 운영 개념 중 하나다.

최종 단계에서는 새로운 아이디어를 추가하고 싶어질 수 있다.

하지만 다음 원칙을 유지한다.

```text
final-design.md에 없는 새 기능
→ v1.0 직전 추가하지 않음
```

특히 다음 기능은 이후 버전으로 남긴다.

```text
Hero typing
실제 Contact Form 전송
시스템 theme 감지
OS theme 변경 실시간 반영
```

완료 직전의 기능 추가는 회귀 위험과 검증 범위를 늘린다.

```text
사용 기술
배포 URL
스크린샷
변경한 기준값 기록
```

#### 범위

```text
Hero typing 없음
실제 Form 전송 없음
system theme 감지 없음
OS theme 실시간 반영 없음
```

최종적으로 모든 항목을 PASS한 뒤 현재 commit을 기준점으로 표시한다.

```text
git tag v1.0
```

필요한 경우 tag를 remote에 반영하는 Git 절차는 현재 사용하는 Git workflow에 맞춰 수행한다.

Diff 확인:

```text
최종 검증 과정에서 불필요한 수정이 생기지 않았는가
```

코드 확인:

```text
마지막 수정 이후 다시 필요한 회귀 검증을 했는가
```

브라우저 확인:

```text
최종 배포 URL을 다시 열어 핵심 기능 확인
```

이해 확인:

```text
왜 현재 commit을 v1.0이라고 부를 수 있는가
```

## 8. v1.0 완료 후 상태

v1.0이 완료되면 프로젝트는 다음 상태다.

```text
B1-1 필수 요구사항 전체 구현
+
Project filtering 구현
+
로컬 최종 검증
+
GitHub Pages 배포
+
배포 환경 전체 검증
+
README
+
스크린샷
+
최종 요구사항 대조
+
v1.0 기준점
```

즉 다음을 만족한다.

```text
다른 사람이 GitHub Pages URL로 사이트에 접근할 수 있다.

final-design.md의 v1.0 요구사항을 실제 결과에서 확인할 수 있다.

핵심 상태 → 렌더링 구조를 코드와 화면을 연결하여 설명할 수 있다.

B1-1 기본 완료 상태와 이후 확장 기능의 경계가 명확하다.
```

이후 버전은 기본 완료 결과를 유지한 채 확장한다.

```text
v1.1
→ Hero 타이핑 효과

v1.2
→ 실제 Contact Form 전송

v1.3
→ 시스템 다크 모드 감지
→ 실행 중 OS 테마 변경 실시간 반영
```

v1.0은 기능 구현 과정의 마지막 숫자가 아니라 **B1-1 기본 완료를 외부에서 검증 가능한 형태로 확정한 기준점**이다.
