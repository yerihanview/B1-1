# v0.9 — Intersection Observer 및 최종 통합

## 1. 버전 목표

v0.8까지 구현한 모든 기능을 유지한 상태에서 **Intersection Observer를 이용한 스크롤 진입 애니메이션을 추가하고, v1.0 직전의 전체 통합 상태를 검증한다.**

이 버전은 새로운 기능을 계속 늘리는 단계가 아니다.

핵심 목표는 두 가지다.

```text
1. 남아 있는 v1.0 필수 인터랙션
   → Intersection Observer 기반 스크롤 애니메이션 구현

2. v0.1 ~ v0.8 기능 전체
   → 함께 동작하는지 통합 / 회귀 확인
```

Intersection Observer의 핵심 흐름은 다음과 같다.

```text
관찰할 DOM 요소 등록
        ↓
Intersection Observer
        ↓
viewport와 요소의 교차 상태 감지
        ↓
threshold 조건 충족
        ↓
observer callback 실행
        ↓
화면 진입 상태 class 추가
        ↓
CSS transition에 의해 콘텐츠 표시
```

v0.9 전체 흐름은 다음과 같다.

```text
기존 완성 기능                 ← v0.1 ~ v0.8
        ↓
Intersection Observer 추가
        ↓
스크롤 진입 상태를 class로 표현
        ↓
CSS가 애니메이션 표현
        ↓
기존 기능 전체 회귀 확인
        ↓
기본 HTML / CSS / JS 품질 확인
        ↓
v1.0 기능 구현 상태 완성
```

v0.9가 끝나면 다음을 설명할 수 있어야 한다.

```text
viewport는 무엇인가
→ Observer는 무엇을 관찰하는가
→ threshold는 무엇을 결정하는가
→ callback은 언제 실행되는가
→ entry는 어떤 관찰 결과를 나타내는가
→ 화면 진입 여부를 어떻게 판단하는가
→ JavaScript가 어떤 class를 변경하는가
→ CSS가 실제 애니메이션을 어떻게 표현하는가
→ 왜 scroll 이벤트로 매번 위치를 직접 계산하지 않는가
→ 기존 기능이 새 기능 추가 후에도 정상인지 어떻게 검증하는가
```

v0.9 완료 시 **v1.0에서 요구하는 기능 구현은 모두 존재**해야 한다.

다만 다음은 아직 하지 않는다.

```text
GitHub Pages 최종 배포
최종 README 작성
최종 제출 검증
v1.0 tag
```

이들은 v1.0의 책임이다.

## 2. 요구사항

### 2.1 기존 v0.8 상태를 기반으로 작업

v0.8까지 구현한 구조와 기능을 유지한다.

현재 사이트에는 최소한 다음 기능이 존재한다.

```text
HTML 의미 구조
CSS 기본 표현
반응형 레이아웃
Flexbox / Grid
Hamburger menu
Navigation 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Light / Dark theme
localStorage theme 복원
Contact Form validation
GitHub API
loading / success / error / API empty
403 rate limit 처리
Retry
Projects 동적 렌더링
Projects language filter
Filter empty
```

v0.9에서는 Intersection Observer 추가를 이유로 기존 기능을 다시 작성하지 않는다.

특히 다음 구조를 유지한다.

```text
Projects
GitHub API
→ 원본 repositories
→ filter()
→ filtered repositories
→ map()
→ Project cards
→ DOM
```

스크롤 애니메이션을 추가하기 위해 Projects API 또는 filter 흐름을 수정하지 않는다.

### 2.2 Intersection Observer 사용

스크롤에 따라 콘텐츠가 viewport에 진입하는 것을 감지하는 데 `IntersectionObserver`를 사용한다.

이번 기능의 핵심 구조:

```text
new IntersectionObserver(...)
        ↓
관찰 대상 observe()
        ↓
viewport 진입 감지
        ↓
callback
        ↓
class 변경
```

기존 `scroll` 이벤트에서 모든 요소의 위치를 반복 계산하는 방식으로 새 애니메이션을 구현하지 않는다.

v0.4에서 이미 사용 중인 `scroll` 이벤트는 다음 기능을 위해 그대로 유지할 수 있다.

```text
Navigation scroll style
Scroll-to-Top 표시
```

즉 두 방식의 역할을 구분한다.

```text
기존 scroll event
→ 현재 스크롤 위치 기반 기능

Intersection Observer
→ 특정 콘텐츠의 viewport 진입 감지
```

---

### 2.3 관찰 대상 결정

스크롤 진입 효과를 적용할 대상을 명확하게 정한다.

기본 대상은 페이지의 주요 section 또는 각 section 안의 대표 콘텐츠 묶음으로 한다.

예:

```text
About
Skills
Projects
Contact
```

필요하면 Hero 또는 기타 정적인 콘텐츠를 포함할 수 있다.

하지만 모든 작은 DOM 요소를 개별 관찰 대상으로 만들 필요는 없다.

특히 Projects 카드들은 v0.7~v0.8에서 다음 상황에 따라 동적으로 다시 생성된다.

```text
API success
Filter 변경
Retry 후 success
```

따라서 v0.9의 기본 설계에서는 **동적으로 재생성되는 각 Project 카드를 Observer 대상 하나씩 관리하는 구조로 확대하지 않는다.**

가능하면 다음처럼 정적인 상위 콘텐츠를 관찰한다.

```text
Projects section 또는 Projects 콘텐츠 wrapper
        ↓
Observer
        ↓
진입 애니메이션

내부 Project cards
→ 기존 동적 렌더링 구조 유지
```

이렇게 하면 Intersection Observer와 API / filter 렌더링의 책임이 분리된다.

---

### 2.4 초기 애니메이션 상태

관찰 대상은 화면에 진입하기 전의 기본 시각 상태를 가진다.

예시 개념:

```text
기본 상태
→ 투명하거나 약간 이동된 상태

화면 진입 상태
→ 정상 위치 / 정상 표시
```

정확한 CSS 값은 실제 디자인에 맞춰 결정한다.

이 단계의 목적은 복잡한 애니메이션 디자인이 아니다.

필요한 것은 다음 관계가 명확한 것이다.

```text
JavaScript
→ 상태 class 추가

CSS
→ class에 따라 표현 변화

transition
→ 변화 과정을 부드럽게 표현
```

JavaScript에서 `style` 값을 직접 반복 작성하지 않는다.

---

### 2.5 화면 진입 상태 class

관찰 대상이 기준을 만족하여 viewport에 진입하면 JavaScript가 해당 요소에 상태 class를 추가한다.

개념 예:

```text
진입 전
.reveal

진입 후
.reveal.visible
```

정확한 class 이름은 현재 프로젝트의 naming 방식에 맞춰 정한다.

핵심 역할 분담:

```text
JavaScript
→ 진입 여부 판단
→ class 추가

CSS
→ 진입 전 / 후 표현
→ transition
```

v0.4에서 배운 `classList` 기반 DOM 상태 변경을 새로운 브라우저 관찰 API에 다시 적용한다.

---

### 2.6 `threshold`

Intersection Observer에는 요소가 viewport와 어느 정도 교차했을 때 callback 조건을 만족할지 정하는 `threshold`를 설정한다.

B1-1에서는 다음 기준을 권장한다.

```text
threshold 0.2 이상 권장
```

이는 고정값이 아니다.

실제 디자인에 따라 다른 값을 사용할 수 있다.

예를 들어 `0.2`는 관찰 대상의 일정 비율이 viewport와 교차했을 때 진입으로 판단하는 기준으로 이해한다.

정확한 수학적 계산이나 Intersection Observer 옵션 전체를 학습하지 않는다.

v1.0에서 최종 README를 작성할 때 B1-1 예시와 다른 threshold를 사용했다면 해당 값을 기록한다.

---

### 2.7 Observer callback

Observer가 관찰 결과를 전달하면 callback에서 각 대상의 현재 교차 상태를 확인한다.

개념 흐름:

```text
Observer
        ↓
관찰 결과 entries
        ↓
각 entry 확인
        ↓
현재 viewport에 진입했는가
        ↓
YES
→ 화면 진입 class 추가
```

이번 버전에서는 callback 함수 전체 이론이나 브라우저 렌더링 내부 구조까지 학습하지 않는다.

다음 관계를 읽고 설명할 수 있으면 된다.

```text
어떤 요소가 관찰되고 있는가
→ 어떤 결과가 callback으로 전달되는가
→ 어떤 조건에서 class가 추가되는가
```

---

### 2.8 `isIntersecting`

관찰 대상이 현재 viewport와 교차하는지 판단할 때 Observer가 제공하는 교차 상태를 사용한다.

핵심 의미:

```text
현재 요소가 관찰 조건에 따라 viewport와 교차하고 있는가?
```

이 값을 이용해 진입 상태를 판단한다.

IntersectionObserverEntry의 모든 속성을 학습하지 않는다.

이번 기능에서 실제 사용하는 값만 이해한다.

---

### 2.9 `observe()`

각 관찰 대상 요소를 Observer에 등록한다.

기본 흐름:

```text
querySelectorAll(...)
        ↓
관찰 대상 여러 개 선택
        ↓
forEach()
        ↓
observer.observe(element)
```

`forEach()`는 v0.4에서 여러 DOM 요소에 같은 작업을 적용하기 위해 이미 경험했다.

v0.9에서는 여러 요소를 같은 Observer에 등록하는 데 다시 사용한다.

새로운 반복 처리 이론을 별도로 확대하지 않는다.

---

### 2.10 한 번 나타난 콘텐츠의 처리

스크롤 애니메이션의 기본 설계는 **콘텐츠가 처음 진입했을 때 나타난 뒤 계속 보이는 방식**을 우선한다.

개념:

```text
viewport 진입
→ visible class 추가
→ 콘텐츠 표시
→ 이후 class 유지
```

따라서 화면에서 벗어날 때마다 다시 숨기고 재진입할 때 반복 애니메이션을 실행하는 구조를 필수로 만들지 않는다.

필요하면 진입 후 더 이상 관찰하지 않는 단순한 구조를 사용할 수 있다.

정확한 해제 API는 실제 구현에서 필요할 때 확인한다.

핵심은 애니메이션을 복잡한 상태 시스템으로 만들지 않는 것이다.

## 구현 요약 (실습 기록)

- 주요 섹션(`hero`, `about`, `skills`, `projects`, `contact`)에 `.reveal` 클래스를 추가하여 초기 숨김 상태를 적용했습니다.
- CSS에서 `.reveal`(투명 + 약간 이동)과 `.reveal.visible`(정상 표시)을 정의했고 전환 애니메이션을 적용했습니다.
- `IntersectionObserver`를 초기화하는 `initIntersectionObserver()`를 추가했으며, `threshold: 0.2`를 기본값으로 사용합니다.
- 관찰 대상이 처음 진입하면 `.visible` 클래스를 추가하고 `unobserve()`로 관찰을 중단합니다(재진입 반복 없음).
- IntersectionObserver가 지원되지 않는 환경에서는 폴백으로 모든 `.reveal` 요소에 `.visible`을 즉시 추가합니다.
- 애니메이션 동작 확인을 위한 로그(`console.log('observing ...')`, `console.log('observer entry ...')`)를 남겨 디버깅을 쉽게 했습니다.

### 2.11 CSS transition 재사용

v0.2에서 배운 `transition`을 스크롤 진입 표현에도 사용한다.

개념 구조:

```text
기본 상태
→ opacity / 위치 등의 초기 값

visible 상태
→ 정상 값

transition
→ 두 상태 사이의 변화 표현
```

CSS animation 전체나 keyframes 중심의 복잡한 효과로 범위를 확대하지 않는다.

Intersection Observer는 **언제 상태를 바꿀지 결정**하고, CSS는 **어떻게 보이게 바꿀지 결정**한다.

---

### 2.12 기존 scroll 기능과 충돌 금지

v0.4에서 이미 존재하는 다음 기능은 유지한다.

```text
scroll
→ Navigation style
→ Scroll-to-Top 표시
```

v0.9의 Observer 추가 후에도 기존 scroll handler가 정상 동작해야 한다.

다음 문제가 생기지 않아야 한다.

```text
Observer 추가 후 Scroll-to-Top이 작동하지 않음
Navigation의 scrolled 상태가 깨짐
스크롤 시 Console 오류 발생
```

Intersection Observer를 추가하기 위해 기존 scroll 기능 전체를 Observer 방식으로 리팩터링하지 않는다.

---

### 2.13 Projects 동적 렌더링과 충돌 금지

v0.7과 v0.8의 Projects 기능은 그대로 유지한다.

다음 상태에서 스크롤 애니메이션 때문에 Projects 기능이 깨지지 않아야 한다.

```text
loading
success
API empty
error
Retry
Filter 변경
Filter empty
```

특히 다음을 확인한다.

```text
Filter 변경
→ Project cards 재렌더링
→ filter 기능 정상
→ Projects section 표시 상태 정상

Retry
→ loading
→ 새 API 결과
→ Projects 렌더링 정상
→ Observer 관련 오류 없음
```

동적으로 생성되는 카드마다 Observer를 다시 연결해야만 동작하는 설계는 이번 버전의 기본 범위로 만들지 않는다.

### 2.14 다크 모드와 애니메이션 상태의 공존

Theme 상태와 reveal 상태는 서로 다른 UI 상태다.

```text
data-theme
→ light / dark theme 결정

reveal / visible class
→ 스크롤 진입 표현 결정
```

둘을 하나의 상태로 섞지 않는다.

다크 모드에서 진입 전 / 후 콘텐츠가 읽기 어렵거나 잘못 숨지 않아야 한다.

Theme Toggle 이후에도 이미 표시된 콘텐츠가 정상적으로 보여야 한다.

---

### 2.15 반응형 레이아웃과 애니메이션의 공존

스크롤 애니메이션은 모바일 / 태블릿 / 데스크톱 레이아웃을 변경하는 기능이 아니다.

v0.3의 반응형 구조를 유지한다.

다음 환경에서 확인한다.

```text
모바일
태블릿
데스크톱
```

애니메이션용 transform이나 초기 위치 때문에 다음 문제가 발생하지 않아야 한다.

```text
의도하지 않은 가로 스크롤
콘텐츠 잘림
Grid 폭 깨짐
Navigation 위치 깨짐
Form 영역 이탈
```

문제가 생기면 애니메이션 값 또는 대상 범위를 수정한다.

반응형 레이아웃 자체를 다시 설계하지 않는다.

```text
모바일
태블릿

```

특히 확인할 조합:

```text
모바일
```

## 4. 새롭게 배우는 개념

### 4.1 Viewport

Viewport는 브라우저에서 현재 사용자가 보고 있는 페이지 표시 영역이라는 수준에서 이해한다.

v0.3에서는 Media Query가 viewport 폭을 기준으로 반응형 레이아웃을 바꾸는 데 사용되었다.

v0.9에서는 viewport가 다음 판단의 기준이 된다.

```text
관찰 대상 요소가
현재 보이는 영역과 교차하는가?
```

같은 viewport 개념이 다른 기능에서 다시 사용된다는 점을 연결해서 이해한다.

---

### 4.2 Intersection

Intersection은 관찰 대상 요소와 viewport가 서로 겹치는 상태라고 이해한다.

이번 버전에서는 복잡한 좌표 계산을 직접 하지 않는다.

```text
요소 위치
+
viewport
        ↓
브라우저가 교차 상태 계산
        ↓
Observer 결과 제공
```

---

### 4.3 Intersection Observer

Intersection Observer는 특정 요소가 viewport와 교차하는 상태 변화를 브라우저가 관찰하고 JavaScript에 알려주는 API라는 수준에서 이해한다.

핵심 질문:

```text
무엇을 관찰하는가?
→ 특정 DOM 요소

무엇을 기준으로 보는가?
→ viewport와의 교차

결과가 발생하면 무엇을 하는가?
→ callback 실행
```

API 전체 옵션을 학습하지 않는다.

---

### 4.4 Observer와 관찰 대상

Observer와 관찰되는 요소를 구분한다.

```text
Observer
→ 관찰 로직

Target element
→ 실제로 관찰되는 DOM 요소
```

하나의 Observer가 여러 요소를 관찰할 수 있다는 것을 이해한다.

---

### 4.5 `observe()`

특정 DOM 요소를 Observer의 관찰 대상으로 등록하는 동작이다.

```text
observer
        ↓
observe(element)
        ↓
해당 요소의 교차 상태 추적
```

여러 요소는 `forEach()`를 이용해 등록할 수 있다.

---

### 4.6 Observer callback

관찰 대상의 교차 상태가 Observer 조건에 맞게 변하면 실행되는 함수다.

v0.4의 Event Handler와 연결해서 이해할 수 있다.

```text
v0.4
click / scroll event
→ event handler

v0.9
intersection 변화
→ observer callback
```

둘 다 어떤 사건이 발생했을 때 실행되는 코드이지만 입력원이 다르다.

---

### 4.7 `entries`

Observer callback은 관찰 결과들을 전달받는다.

여러 요소를 관찰할 수 있기 때문에 결과 역시 여러 항목으로 전달될 수 있다는 정도로 이해한다.

```text
관찰 대상 여러 개
        ↓
교차 결과 entries
        ↓
각 entry 확인
```

IntersectionObserverEntry의 전체 구조를 암기하지 않는다.

---

### 4.8 `isIntersecting`

현재 entry의 대상이 viewport와 교차하는 상태인지 알려주는 값이라는 수준에서 이해한다.

```text
isIntersecting = true
→ 현재 교차 상태
→ reveal 처리 가능
```

이 값을 이용해 class 추가 조건을 판단한다.

---

### 4.9 `threshold`

`threshold`는 관찰 대상이 어느 정도 교차했을 때 Observer가 기준을 만족한 것으로 판단할지 정하는 옵션이다.

개념 예:

```text
threshold: 0.2
→ 대상의 약 20% 수준이 교차하는 지점을 기준으로 사용
```

B1-1에서는 `0.2` 이상을 권장한다.

정확한 값은 디자인에 따라 조정할 수 있다.

옵션 전체를 암기하지 않는다.

---

### 4.10 Observer State → CSS Rendering

v0.9의 핵심 상태→화면 구조다.

```text
viewport 진입 여부
        ↓
Observer가 감지
        ↓
visible 상태 class
        ↓
CSS 규칙 변경
        ↓
화면 표현 변화
```

기존 버전과 연결하면 다음처럼 볼 수 있다.

```text
v0.5
Theme state
→ data-theme
→ CSS

v0.6
Validation state
→ 오류 class / message
→ DOM

v0.7
API state
→ loading / success / error / empty
→ DOM

v0.8
Filter state
→ filtered data
→ DOM

v0.9
Viewport intersection state
→ reveal class
→ CSS
```

---

### 4.11 Event와 Observer의 차이

둘 다 JavaScript가 어떤 변화를 감지하는 구조지만 입력이 다르다.

```text
Event
→ click, submit, scroll, input 같은 사건

Intersection Observer
→ DOM 요소와 viewport의 교차 상태 변화
```

모든 브라우저 변화를 `addEventListener()` 하나의 방식으로만 처리하는 것이 아니라, 목적에 맞는 브라우저 API를 사용할 수 있음을 이해한다.

---

### 4.12 scroll event 직접 계산과 Observer

스크롤 진입 애니메이션을 구현하기 위해 매 scroll마다 모든 요소의 위치를 직접 계산하지 않는다.

개념 차이:

```text
직접 scroll 계산
→ scroll마다 위치를 읽고 조건 판단

Intersection Observer
→ 브라우저에 관찰 대상 등록
→ 교차 상태 변화를 전달받음
```

성능 이론 전체를 깊게 다루는 것이 목적은 아니다.

현재 기능에 Observer가 더 직접적인 도구라는 점을 이해한다.

---

### 4.13 회귀(Regression)

새 기능을 추가한 뒤 이전에 정상 동작하던 기능이 깨지는 것을 회귀 문제라고 이해한다.

예:

```text

        ↓
기존 filter가 작동하지 않음

또는

        ↓
모바일에서 가로 스크롤 발생
```

v0.9에서는 단순히 새 기능만 확인하지 않고 이전 기능을 다시 검증하는 습관을 익힌다.

각 버전에서 따로 구현한 기능이 한 페이지 안에서 함께 동작하는지 확인하는 과정이다.

```text

Projects API
Filter
Form
Navigation

Observer
```

각 기능이 단독으로 동작하는 것과 전체 사이트에서 함께 동작하는 것은 별도 검증 대상이라는 점을 이해한다.

---

### 4.15 기능 책임 분리

v0.9에서는 여러 기능을 통합하지만 하나의 거대한 함수나 상태 객체로 합치지 않는다.

기본 책임은 유지한다.

```text

→ theme 상태 담당

→ validation 담당

→ 외부 데이터와 API 상태 담당
```

통합은 모든 기능을 하나로 합치는 것이 아니라 **서로 충돌하지 않고 함께 동작하는 상태**를 만드는 것이다.

## 5. 완료 / 검증 기준

### 5.1 Observer 생성

Intersection Observer가 실제 JavaScript 코드에 존재한다.

외부 animation library를 사용하지 않는다.

---

### 5.2 관찰 대상 등록

최소한 페이지의 여러 주요 콘텐츠가 Observer에 등록되어 있다.

어떤 selector로 어떤 DOM 요소를 관찰하는지 설명할 수 있다.

---

### 5.3 threshold

Observer에 의도한 `threshold`가 설정되어 있다.

B1-1 권장값인 `0.2` 이상을 사용할 수 있다.

다른 값을 사용했다면 v1.0 README에서 기록해야 함을 인지한다.

---

### 5.4 진입 전 상태

관찰 대상이 화면에 진입하기 전 CSS 상태가 존재한다.

그 상태가 콘텐츠를 영구적으로 보이지 않게 만들거나 레이아웃을 깨뜨리지 않는다.

---

### 5.5 진입 상태 class

대상이 viewport에 진입하면 JavaScript가 의도한 class를 추가한다.

DevTools Elements에서 class 변화를 직접 확인할 수 있다.

---

### 5.6 CSS transition

class 변화에 따라 콘텐츠가 갑자기 바뀌는 것이 아니라 필요한 transition을 통해 자연스럽게 나타난다.

JavaScript에서 스타일 값을 직접 반복 지정하지 않는다.

---

### 5.7 Observer 흐름 설명

다음 흐름을 자신의 말로 설명할 수 있다.

```text
관찰 대상 등록
→ viewport 진입
→ threshold 충족
→ callback
→ isIntersecting 확인
→ class 추가
→ CSS transition
→ 화면 표시
```

---

### 5.8 기존 scroll 기능 유지

다음 v0.4 기능이 정상 동작한다.

```text
Navigation scroll style
Scroll-to-Top 표시
Scroll-to-Top click
```

Observer 추가로 기존 scroll 기능이 깨지지 않는다.

## 8. v0.9 완료 후 상태

v0.9가 완료되면 프로젝트는 다음 상태다.

```text
HTML / CSS / JavaScript 기능 구현
        ↓
B1-1 v1.0 필수 기능 전체 존재
        ↓
Intersection Observer 완료
        ↓
전체 기능 로컬 통합 확인 완료
        ↓
기본 품질 확인 완료
        ↓

남은 작업
        ↓
v1.0
GitHub Pages 배포
README
스크린샷
배포 환경 검증
최종 요구사항 대조
최종 제출 검증
```
