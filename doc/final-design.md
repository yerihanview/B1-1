# B1-1 Final Design

## 1. 문서 목적

이 문서는 B1-1 프로젝트의 **v1.0 최종 산출물 설계**를 정의한다.

이 문서에서는 다음을 결정한다.

- 최종 웹사이트가 어떤 구조를 가지는가
- 어떤 기능이 존재해야 하는가
- 각 기능이 어떤 역할을 담당하는가
- 사용자 행동과 화면 변화가 어떻게 연결되는가
- v1.0 완료 시 어떤 상태여야 하는가

이 문서는 구현 순서를 정의하지 않는다.

구현 순서는 `roadmap.md`에서 관리하고, 각 단계의 구체적인 구현 범위는 `vX.X.md`에서 관리한다.

---

# 2. 최종 산출물 정의

v1.0의 최종 산출물은 다음 조건을 만족하는 **개인 반응형 포트폴리오 웹사이트 1개**다.

사용 기술은 다음으로 제한한다.

- HTML
- CSS
- JavaScript

핵심 기능 구현에 React, Vue, jQuery, Bootstrap, Tailwind CSS 등의 외부 프레임워크나 라이브러리를 사용하지 않는다.

다음은 사용할 수 있다.

- Font Awesome
- Google Fonts

HTML 요소에 `style="..."` 형태의 인라인 스타일을 사용하지 않는다.

스타일은 CSS 파일에서 관리한다.

최종 사이트는 GitHub Pages에 배포되어 외부에서 접근할 수 있어야 한다.

---

# 3. 최종 페이지 구조

웹사이트는 하나의 페이지 안에 다음 영역을 가진다.

```text
Page
│
├── Header
│   └── Navigation
│
├── Main
│   ├── Hero
│   ├── About
│   ├── Skills
│   ├── Projects
│   └── Contact
│
└── Footer
```

HTML은 단순히 `div`만으로 구성하지 않고 구조에 맞는 시맨틱 태그를 사용한다.

주요 태그:

- `header`
- `nav`
- `main`
- `section`
- `article`
- `footer`

---

# 4. Header / Navigation

## 역할

페이지 전체의 주요 섹션으로 이동할 수 있는 네비게이션을 제공한다.

## 포함 요소

- 로고 또는 사이트 이름
- Hero 또는 Home 링크
- About 링크
- Skills 링크
- Projects 링크
- Contact 링크
- 다크 모드 토글
- 모바일 햄버거 버튼

## 데스크톱

네비게이션은 Flexbox를 사용한다.

기본 구조:

```text
Logo                         Navigation Menu        Theme Toggle
```

## 모바일

작은 화면에서는 일반 네비게이션 메뉴를 숨기고 햄버거 버튼을 표시한다.

햄버거 버튼을 누르면 메뉴가 열린다.

다시 누르면 메뉴가 닫힌다.

## 스크롤 상태

페이지를 일정 거리 이상 스크롤하면 Header 또는 Navigation의 배경 스타일이 변경된다.

정확한 기준값은 구현 과정에서 결정할 수 있다.

B1-1의 예시값은 60px이며, 다른 값을 사용하는 경우 README에 명시한다.

# 8. Projects

Projects는 B1-1에서 가장 중요한 동적 영역 중 하나다.

## 역할

GitHub API를 호출하여 본인의 저장소 데이터를 가져오고 화면에 프로젝트 카드로 표시한다.

## 데이터 흐름

```text
페이지 또는 Projects 기능 시작

        ↓

GitHub API 요청

        ↓

현재 상태 변경

        ↓

Projects DOM 렌더링
```

## GitHub API

다음 형태의 API를 사용한다.

```text
https://api.github.com/users/{본인아이디}/repos
```

`fetch`와 `async/await`를 사용하여 데이터를 가져온다.

에러 처리는 `try/catch`를 사용한다.

---

## Projects UI 상태

Projects 영역은 최소한 다음 네 가지 상태를 표현한다.

### Loading

API 요청이 진행 중인 상태.

### Success

API 요청에 성공하고 저장소 데이터가 존재하는 상태.

저장소 데이터를 프로젝트 카드로 변환하여 표시한다.

Projects 카드 레이아웃은 CSS Grid를 사용한다.

반응형 구현에는 다음 개념을 사용한다.

- `auto-fit`
- `minmax`

### Error

API 호출에 실패한 상태.

사용자에게 실패 사실을 알려야 한다.

재시도 버튼을 통해 다시 API 요청을 할 수 있어야 한다.

GitHub API rate limit으로 403 응답이 발생한 경우도 에러 상태로 처리한다.

### Empty

API 요청에는 성공했지만 표시할 프로젝트가 없는 상태.

---

## 프로젝트 필터링

v1.0에서 프로젝트를 특정 조건으로 필터링할 수 있어야 한다.

기본 설계는 GitHub 저장소의 언어 정보를 이용한 필터링으로 한다.

예:

```text
All
HTML
CSS
JavaScript
```

필터 선택 시 전체 데이터를 다시 API에서 요청하지 않는다.

이미 가져온 프로젝트 데이터에서 `filter`를 사용해 조건에 맞는 프로젝트를 선택하고 Projects 영역을 다시 렌더링한다.

상태 흐름:

```text
필터 선택 이벤트

        ↓

현재 filter 상태 변경

        ↓

프로젝트 데이터 filter

        ↓

Projects DOM 다시 렌더링
```

# 9. Contact

## 역할

사용자가 이름, 이메일, 메시지를 입력할 수 있는 문의 폼을 제공한다.

## 입력 필드

- 이름
- 이메일
- 메시지

각 입력 요소에는 올바르게 연결된 `label`이 존재해야 한다.

즉 `label`의 `for`와 입력 요소의 `id`가 대응해야 한다.

## 유효성 검사

다음 검증을 수행한다.

### 필수값

빈 필드는 제출할 수 없다.

### 이메일

올바른 이메일 형식인지 확인한다.

### 오류 표시

검증에 실패하면 해당 입력 필드 근처에 오류 메시지를 표시한다.

### 성공 상태

모든 검증을 통과하면 성공 메시지를 표시한다.

v1.0에서는 실제 이메일 전송을 하지 않는다.

폼 제출 시 `event.preventDefault()`를 사용하여 브라우저의 기본 제출 동작을 막는다.

실제 이메일 전송은 이후 확장 버전의 범위다.

# 11. 다크 모드

## 역할

사용자가 밝은 테마와 어두운 테마를 전환할 수 있게 한다.

## CSS 설계

기본 디자인 값은 CSS 변수로 관리한다.

```css
:root {
  /* light theme variables */
}

[data-theme="dark"] {
  /* dark theme variables */
}
```

## 상태 흐름

```text
다크 모드 버튼 click
→ 현재 theme 상태 변경
→ DOM의 theme 속성 변경
→ CSS 변수 변경
→ 화면 테마 변경
```

## 상태 유지

선택한 테마를 `localStorage`에 저장한다.

페이지를 새로고침해도 이전 테마가 유지되어야 한다.

시스템 다크 모드 자동 감지는 v1.0 필수 범위에 포함하지 않는다.

# 12. 햄버거 메뉴

모바일 화면에서 동작한다.

```text
햄버거 버튼 click
→ 메뉴 상태 변경
→ classList.toggle('active')
→ 메뉴 표시 / 숨김
```

HTML의 `onclick` 속성은 사용하지 않는다.

JavaScript의 `addEventListener`를 사용한다.

# 14. Scroll-to-Top 버튼

사용자가 페이지를 일정 거리 이상 스크롤하면 화면에 나타난다.

버튼을 누르면 페이지 최상단으로 이동한다.

B1-1의 예시 기준은 300px이다.

실제 기준값은 변경할 수 있으며, 변경한 경우 README에 기록한다.

# 15. 스크롤 애니메이션

사용자가 페이지를 스크롤하여 특정 섹션에 접근하면 해당 콘텐츠가 나타나는 시각적 효과를 제공한다.

Intersection Observer를 사용한다.

B1-1은 threshold 0.2 이상을 권장하지만 고정값은 아니다.

다른 값을 사용할 경우 README에 명시한다.

# 16. JavaScript 설계 원칙

JavaScript는 별도 파일에서 관리하며 HTML에서 `defer`를 사용하여 연결한다.

## 변수

`var`를 사용하지 않는다.

- `const`
- `let`

## DOM 선택

- `querySelector`
- `querySelectorAll`

## DOM 변경

- `textContent`
- `innerHTML`
- `classList.add`
- `classList.remove`
- `classList.toggle`

## 이벤트

최종 프로젝트에서는 다음 이벤트를 다룬다.

- `click`
- `submit`
- `scroll`
- `input`

필요한 경우 `event.preventDefault()`를 사용하여 브라우저의 기본 동작을 제어한다.

# 17. ES6+ 사용 설계

v1.0에서는 B1-1에서 요구하는 범위의 ES6+ 문법을 실제 기능 안에서 사용한다.

## 화살표 함수

이벤트 핸들러나 데이터 처리 함수 등에 적절히 사용한다.

## 템플릿 리터럴

GitHub 프로젝트 카드와 같은 동적 HTML 생성에 사용한다.

## 구조분해 할당

GitHub API 데이터 등 객체 또는 배열에서 필요한 값을 추출하는 데 사용한다.

## 배열 메서드

### `map`

GitHub 저장소 데이터를 프로젝트 카드 HTML로 변환할 때 사용한다.

### `forEach`

DOM 요소나 배열을 순회해야 하는 기능에서 사용한다.

### `filter`

GitHub 프로젝트 데이터를 선택한 조건에 따라 필터링하는 데 사용한다.

`filter`는 이 프로젝트에서는 v1.0 필수 구현 범위로 취급한다.

# 24. v1.0에 포함하지 않는 확장 기능

다음 기능은 v1.0 필수 범위에 포함하지 않는다.

## Hero 타이핑 효과

글자가 한 글자씩 나타나는 효과.

향후 확장 버전에서 선택적으로 추가한다.

## 실제 폼 전송

Formspree 또는 EmailJS 등을 이용한 실제 이메일 전송.

향후 확장 버전에서 선택적으로 추가한다.

## 시스템 다크 모드 감지

`prefers-color-scheme`을 이용하여 운영체제 테마를 자동 감지하는 기능.

향후 확장 버전에서 선택적으로 추가한다.

프로젝트 필터링은 원래 B1-1에서 선택 항목으로 제시되지만, 이 프로젝트에서는 학습 목표를 위해 **v1.0 필수 기능으로 승격한다.**

# 25. v1.0 완료 상태

v1.0은 다음과 같은 상태를 의미한다.

```text
반응형 개인 포트폴리오
        +
시맨틱 HTML
        +
Flexbox / Grid 레이아웃
        +
필수 사용자 인터랙션
        +
다크 모드 및 상태 유지
        +
폼 유효성 검사
        +
GitHub API 동적 렌더링
        +
프로젝트 필터링
        +
loading / success / error / empty 처리
        +
최소 3개의 상태 → 렌더링 흐름
        +
GitHub Pages 배포
        +
README 및 제출 자료
```

이 조건을 모두 만족하고 실제 브라우저에서 검증했을 때 B1-1 필수 완료 버전인 `v1.0`으로 판단한다.

# 26. 설계의 우선순위

구현 과정에서 선택이 필요한 경우 다음 순서를 우선한다.

```text
1. B1-1 필수 요구사항 충족
2. 이 프로젝트에서 필수로 승격한 요구사항 충족
3. 웹 동작 원리 이해
4. 코드의 명확성
5. 반응형 및 사용성
6. 시각적 완성도
7. 추가 기능
```

따라서 디자인을 화려하게 만들기 위해 학습 범위를 확대하거나, 아직 필요하지 않은 기술을 도입하지 않는다.
