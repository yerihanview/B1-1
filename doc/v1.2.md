# v1.2 — 실제 Contact Form 전송

## 1. 버전 목표

v1.1까지 완성한 B1-1 기본 기능과 Hero 타이핑 효과를 유지한 채, v1.0에서 **클라이언트 유효성 검사까지만 수행하던 Contact Form을 실제 외부 전송까지 확장**한다.

v1.2의 핵심은 Form UI를 새로 만드는 것이 아니다.

기존 v1.0의 다음 흐름을 그대로 유지한다.

```text
사용자 submit
        ↓
event.preventDefault()
        ↓
Name / Email / Message 값 읽기
        ↓
validation
        ↓
valid / invalid 판단
```

그리고 모든 입력값이 유효한 경우에만 다음 흐름을 추가한다.

```text
validation 통과
        ↓
submitting 상태
        ↓
외부 Form 서비스로 비동기 전송
        ↓
응답 확인
        ↓

성공
→ success 상태
→ 실제 전송 성공 UI

실패
→ error 상태
→ 전송 실패 UI
```

따라서 v1.2의 전체 핵심 흐름은 다음과 같다.

```text
사용자 Submit
        ↓
기존 validation
        ↓

invalid
→ 기존 필드별 오류 UI
→ 실제 전송하지 않음

valid
→ submitting
→ 실제 외부 전송
→ success 또는 error
→ Contact Form UI 갱신
```

v1.2가 끝나면 최소한 다음 관계를 설명할 수 있어야 한다.

```text
왜 validation과 실제 전송은 서로 다른 단계인가
→ 어떤 조건에서 실제 전송을 시작하는가
→ submitting 상태는 왜 필요한가
→ 전송 중 Submit을 다시 누르면 왜 문제가 될 수 있는가
→ async / await는 무엇을 기다리는가
→ try / catch는 어떤 실패를 처리하는가
→ 성공과 실패를 무엇을 기준으로 구분하는가
→ success / error 상태가 어떤 DOM을 변경하는가
→ 실제 배포 환경에서 왜 다시 검증해야 하는가
→ 브라우저 코드에 넣어도 되는 공개 설정값과 넣으면 안 되는 비밀 정보는 어떻게 구분하는가
```

이번 버전에서는 실제 전송 기능 하나에 집중한다.

다음 v1.3 기능은 구현하지 않는다.

```text
prefers-color-scheme
matchMedia
시스템 테마 초기 감지
OS 테마 변경 실시간 반영
```

## 2. 요구사항

### 2.1 v1.1 완료 상태를 기반으로 작업

v1.1까지 완성한 기존 구조와 기능을 모두 유지한다.

최소한 다음 기능이 그대로 동작해야 한다.

```text
Header / Navigation
Hero
Hero typing effect
About
Skills
Projects
Contact
Footer

Responsive layout
Hamburger menu
Smooth internal scroll
Scroll-to-Top
Navigation scroll style

Light / Dark theme
localStorage theme restore

Contact Form validation

GitHub API
loading / success / error / API empty
403 rate limit error
Retry
Projects dynamic rendering
Project filter
Filter empty

Intersection Observer reveal
GitHub Pages deployment
```

Contact Form 실제 전송을 추가하기 위해 다음 기존 구조를 다시 설계하지 않는다.

```text
Projects
API → 원본 repositories → filter() → map() → DOM

Theme
사용자 선택 → data-theme → CSS variables → localStorage

Hero typing
문자열 → current index → textContent → setTimeout → 종료
```

v1.2의 수정 범위는 기본적으로 다음에 한정한다.

```text
Contact Form
+ 외부 전송 서비스 설정
+ 전송 함수
+ submitting / success / error 상태 UI
+ 중복 제출 방지
```

---

### 2.2 기존 Contact Form 구조 유지

기존 Contact Form의 의미 구조를 유지한다.

기본 입력은 다음과 같다.

```text
Name
Email
Message
Submit button
```

기존 `label`과 각 입력 요소의 `for-id` 연결을 유지한다.

실제 전송을 위해 필요한 경우 최소 범위에서 다음을 추가하거나 조정할 수 있다.

```text
전송 상태 메시지 영역
Submit button 상태 표현용 class / attribute
외부 서비스가 요구하는 form field name
JavaScript 선택용 식별자
```

그러나 전송 기능을 위해 Contact section 전체 HTML을 다시 작성하지 않는다.

---

### 2.3 기존 JavaScript validation 유지

v0.6 / v1.0에서 구현한 validation은 v1.2에서도 그대로 전송의 선행 조건으로 사용한다.

최소 검증 항목:

```text
Name 필수값
Email 필수값
Email 형식
Message 필수값
```

기본 흐름:

```text
submit
        ↓
preventDefault()
        ↓
입력값 읽기
        ↓
validation
        ↓

invalid field 존재
→ 필드별 오류 UI
→ 실제 전송 함수 호출 금지

모든 field valid
→ 실제 전송 단계 진입
```

v1.2에서 외부 서비스가 연결되었다는 이유로 기존 JavaScript validation을 제거하지 않는다.

외부 서비스 자체의 검증 기능이 존재하더라도 현재 프로젝트의 클라이언트 validation 학습 구조는 유지한다.

---

### 2.4 `event.preventDefault()` 유지

기존 Form `submit` handler에서 사용하는 `event.preventDefault()`를 유지한다.

v1.2에서는 기본 HTML Form 제출 방식으로 페이지를 이동시키는 대신 JavaScript가 전송 흐름을 제어한다.

기본 관계:

```text
submit event
        ↓
preventDefault()
        ↓
현재 페이지 유지
        ↓
JavaScript validation
        ↓
필요한 경우 비동기 전송
        ↓
현재 페이지에서 결과 UI 표시
```

`preventDefault()`를 제거하고 브라우저 기본 제출과 JavaScript 비동기 전송이 동시에 발생하는 구조를 만들지 않는다.

---

### 2.5 외부 Form 서비스 선택

실제 전송에는 B1-1과 `extended-design.md`에서 허용한 방향에 따라 외부 Form 서비스를 사용한다.

후보 예:

```text
Formspree
EmailJS
```

서비스는 구현 전에 하나를 선택한다.

선택 시 최소한 다음을 확인한다.

```text
정적 GitHub Pages에서 사용할 수 있는가
브라우저 JavaScript에서 연결 가능한가
Name / Email / Message를 전송할 수 있는가
성공 / 실패 결과를 JavaScript에서 판단할 수 있는가
비밀 정보를 repository에 넣지 않고 사용할 수 있는가
현재 학습 범위에 비해 설정이 지나치게 복잡하지 않은가
```

이 문서는 특정 서비스의 세부 API 문법을 고정하지 않는다.

서비스 선택 후 해당 서비스의 **공식 프런트엔드 사용 방식**을 기준으로 구현한다.

외부 서비스를 바꾸기 위해 Contact Form validation 구조 전체를 바꾸지 않는다.

---

### 2.6 서비스 설정값과 비밀 정보 구분

외부 서비스가 요구하는 설정값을 모두 같은 종류의 "키"로 취급하지 않는다.

최소한 다음을 구분한다.

```text
브라우저에서 사용하도록 설계된 공개 식별자 / endpoint
→ 서비스 공식 방식에 따라 프런트엔드에서 사용할 수 있음

서버에서만 보관해야 하는 secret / private key / 민감한 인증 정보
→ 브라우저 JavaScript에 포함하지 않음
→ Git repository에 commit하지 않음
```

다음 방식은 사용하지 않는다.

```text
"동작하니까" 비밀 키를 script.js에 직접 작성
민감한 credential을 GitHub repository에 commit
README에 실제 secret 값 기록
```

서비스 문서가 어떤 값을 클라이언트에서 사용하도록 허용하는지 확인한 뒤 적용한다.

---

### 2.7 실제 전송 데이터

외부 서비스로 보내는 데이터는 기존 Contact Form의 입력값을 기준으로 한다.

최소 데이터:

```text
Name
Email
Message
```

전송 데이터는 현재 사용자가 validation을 통과한 값을 사용한다.

v1.2의 목적과 관계없는 다음 데이터 수집으로 확대하지 않는다.

```text
전화번호
주소
위치 정보
브라우저 fingerprint
사용자 계정
첨부 파일
```

현재 Form에 없는 입력을 실제 전송 기능 때문에 새로 추가하지 않는다.

---

### 2.8 비동기 전송 함수

실제 외부 전송은 별도의 읽기 쉬운 비동기 흐름으로 구성한다.

기본 개념:

```text
sendForm(...)
        ↓
외부 서비스 요청
        ↓
await
        ↓
응답 결과 확인
        ↓
success 또는 error 판단
```

v0.7에서 이미 학습한 다음 개념을 재사용한다.

```text
async
await
try
catch
```

사용하는 서비스가 `fetch()` 기반 연결을 요구한다면 기존 GitHub API에서 배운 HTTP 요청 개념과 연결하여 이해한다.

서비스 전용 SDK를 사용하는 경우에도 핵심 학습 흐름은 다음을 유지한다.

```text
비동기 전송 시작
→ 결과 대기
→ 성공 또는 실패 판단
→ 상태 갱신
→ DOM 갱신
```

---

### 2.9 Form 전송 상태

v1.2에서는 Contact Form 전체의 상태를 최소한 다음과 같이 구분한다.

```text
idle
validation error
submitting
success
error
```

각 상태의 의미는 다음과 같다.

#### Idle

```text
아직 실제 전송 진행 중이 아님
일반적인 입력 가능 상태
```

#### Validation Error

```text
입력값이 유효하지 않음
필드별 오류 UI 표시
외부 전송하지 않음
```

#### Submitting

```text
validation 통과
외부 서비스 요청 진행 중
결과 아직 확정되지 않음
```

#### Success

```text
외부 서비스 전송 성공
실제 전송 성공 UI 표시
```

#### Error

```text
전송 요청 또는 응답 처리 실패
실제 전송 실패 UI 표시
```

복잡한 전역 상태 관리 객체나 상태 관리 라이브러리는 사용하지 않는다.

핵심은 현재 Contact Form이 **어떤 단계에 있는지 코드와 화면에서 구분할 수 있는 것**이다.

---

### 2.10 Validation Error와 전송 Error 구분

두 오류는 의미가 다르다.

```text
Validation Error
→ 사용자 입력값 문제
→ 외부 요청 시작 전

Transmission Error
→ validation은 통과했음
→ 외부 요청 중 또는 응답 처리에서 문제 발생
```

예:

```text
Email 형식 잘못됨
→ validation error
→ Email 필드 근처 오류 메시지

입력은 모두 valid
외부 서비스 요청 실패
→ transmission error
→ Form 전체 전송 실패 메시지
```

전송 실패를 Email 입력 오류처럼 표시하지 않는다.

반대로 입력값 문제를 "서버 전송 실패"로 표시하지 않는다.

---

### 2.11 Submitting 상태 UI

실제 요청이 진행 중임을 사용자가 알 수 있어야 한다.

최소 표현 예:

```text
Sending...
```

또는 현재 사이트 언어에 맞는 짧은 전송 중 메시지를 사용한다.

필요한 경우 Submit button의 표시 문구를 변경할 수 있다.

핵심은 다음 관계다.

```text
validation 성공
        ↓
submitting = true
        ↓
전송 중 UI
        ↓
외부 요청
```

로딩 애니메이션 디자인이나 spinner library를 추가하는 것이 목적은 아니다.

---

### 2.12 중복 제출 방지

전송 중 사용자가 Submit을 반복 클릭하여 같은 메시지가 여러 번 전송되는 상황을 방지한다.

기본 흐름:

```text
첫 Submit
→ validation 통과
→ submitting
→ Submit control 비활성화 또는 재진입 차단

전송 중 두 번째 Submit 시도
→ 추가 전송 시작하지 않음

전송 완료
→ 필요에 따라 Submit control 다시 사용 가능
```

중복 제출 방지는 화면 표현만 바꾸는 것으로 끝나지 않는다.

예를 들어 버튼 문구만 `Sending...`으로 바꾸고 실제 handler는 계속 여러 요청을 시작할 수 있다면 완료가 아니다.

코드 수준에서도 동시에 여러 전송이 시작되지 않아야 한다.

---

### 2.13 Success 상태

외부 서비스가 정상적으로 전송을 완료했다고 판단된 경우에만 success 상태로 전환한다.

기본 흐름:

```text
submitting
        ↓
외부 전송 성공
        ↓
success
        ↓
성공 메시지 표시
```

v1.0의 성공 메시지 의미와 v1.2의 성공 메시지 의미를 구분한다.

```text
v1.0 성공
→ validation 통과
→ 실제 전송 아님

v1.2 성공
→ validation 통과
→ 실제 외부 전송 완료
```

따라서 기존의 "validation 성공" 메시지가 있다면 v1.2에서는 실제 전송 성공을 의미하도록 흐름과 문구를 조정한다.

---

### 2.14 Success 후 Form 처리

실제 전송 성공 후 입력값을 어떻게 처리할지는 한 가지 단순한 정책으로 정한다.

기본 권장 흐름:

```text
전송 성공
→ success 메시지
→ Form 입력값 초기화
```

단, 입력 초기화는 **실제 success가 확인된 뒤에만** 수행한다.

다음 구조는 피한다.

```text
Submit 직후 form reset
→ 외부 전송 실패
→ 사용자가 입력한 내용까지 이미 사라짐
```

현재 코드 구조상 입력값 유지가 더 단순하고 명확하다면 유지할 수 있다.

중요한 것은 성공 전 데이터를 성급하게 없애지 않는 것이다.

---

### 2.15 Error 상태

다음 상황에서는 전송 error 상태가 될 수 있다.

```text
네트워크 요청 실패
외부 서비스 오류 응답
서비스 설정 오류
응답 처리 과정 오류
```

사용자에게 최소한 다음을 알린다.

```text
메시지를 전송하지 못했다.
다시 시도할 수 있다.
```

내부 오류 세부사항을 사용자 화면에 그대로 노출할 필요는 없다.

개발 중에는 Console과 Network 탭으로 원인을 확인할 수 있다.

사용자 화면은 이해 가능한 실패 상태를 제공한다.

---

### 2.16 Error 후 재시도

전송 실패 후 사용자는 입력값을 수정하거나 그대로 다시 Submit하여 재시도할 수 있어야 한다.

기본 흐름:

```text
valid 입력
→ submitting
→ transmission error
→ error UI

사용자 다시 Submit
→ validation 다시 수행
→ valid
→ submitting
→ 다시 외부 전송
```

별도의 복잡한 Retry 버튼을 반드시 추가할 필요는 없다.

기존 Submit control을 다시 사용할 수 있으면 충분하다.

전송 실패 후 `submitting` 상태가 해제되지 않아 버튼이 영구 비활성화되는 문제가 없어야 한다.

---

### 2.17 상태 UI의 이전 흔적 제거

현재 상태와 맞지 않는 이전 메시지가 함께 남지 않아야 한다.

예:

```text
첫 시도
→ error
→ 전송 실패 메시지

두 번째 시도
→ submitting

이때
→ 이전 error 메시지는 현재 상태와 맞게 갱신 또는 제거
```

성공 후 다시 사용자가 입력하고 전송을 시도하는 경우에도 이전 success 메시지가 새 전송 상태와 혼동되지 않아야 한다.

기본 원칙:

```text
현재 상태
→ 현재 상태에 맞는 UI
```

---

### 2.18 Submit button 상태와 접근성

전송 중 Submit control을 비활성화하는 경우 HTML의 실제 `disabled` 상태를 사용할 수 있다.

기본 관계:

```text
submitting
→ disabled
→ 중복 사용자 입력 방지

success / error 종료
→ 필요에 따라 disabled 해제
```

CSS로 비활성화된 것처럼 보이게만 하고 실제로 클릭 가능한 상태를 유지하지 않는다.

기존 button 의미 구조를 유지한다.

접근성 속성 전체를 별도 학습 범위로 확대하지 않는다.

---

### 2.19 사용자 상태 메시지

Contact Form 전체 상태 메시지는 사용자가 현재 결과를 이해할 수 있어야 한다.

최소 구분:

```text
submitting
→ 전송 중

success
→ 실제 전송 완료

error
→ 실제 전송 실패
```

필드별 validation 오류 메시지는 기존 구조를 유지한다.

전체 전송 상태 메시지와 필드 오류 메시지를 하나의 의미로 섞지 않는다.

필요한 경우 기존 상태 메시지 영역을 재사용할 수 있다.

새로운 HTML 요소를 과도하게 추가하지 않는다.

---

### 2.20 `async / await` 재사용

v0.7에서 GitHub API를 통해 학습한 `async / await`를 Form 전송에 다시 적용한다.

두 기능의 공통 구조:

```text
GitHub API
요청 시작
→ await
→ 성공 / 실패
→ Projects UI

Contact Form
전송 시작
→ await
→ 성공 / 실패
→ Contact UI
```

차이:

```text
GitHub API
→ 외부 데이터를 읽음

Contact Form
→ 사용자 입력 데이터를 외부로 보냄
```

비동기 문법 자체를 처음부터 다시 학습하지 않는다.

새로운 맥락에서 같은 개념이 어떻게 쓰이는지를 확인한다.

---

### 2.21 `try / catch` 재사용

외부 전송 중 발생할 수 있는 실패를 처리하기 위해 `try / catch` 구조를 사용할 수 있다.

기본 관계:

```text
try
→ 전송 시도
→ 응답 확인
→ success 처리

catch
→ 전송 실패 처리
→ error UI
```

단, 사용하는 서비스의 API가 실패를 전달하는 방식에 따라 구체적인 코드는 달라질 수 있다.

핵심은 **실패가 발생해도 JavaScript 전체가 중단된 채 사용자에게 아무 설명도 없는 상태로 남지 않는 것**이다.

---

### 2.22 HTTP 응답과 애플리케이션 성공 구분

`fetch()`를 사용하는 서비스라면 네트워크 요청이 완료되었다는 사실만으로 success로 판단하지 않는다.

기본 관계:

```text
response 도착
        ↓
서비스 기준으로 성공 응답인가
        ↓
YES → success
NO  → error
```

이 원칙은 v0.7의 GitHub API에서 배운 다음 내용과 연결된다.

```text
fetch가 완료됨
≠
항상 성공한 HTTP 결과
```

정확한 success 판정 방식은 선택한 서비스의 공식 문서를 기준으로 한다.

---

### 2.23 Form 데이터 표현 방식

외부 서비스가 요구하는 방식에 따라 현재 Form 값을 전송 가능한 형태로 구성한다.

예시 개념:

```text
DOM input values
        ↓
전송용 데이터 구성
        ↓
외부 서비스 요청
```

서비스에 따라 다음 중 하나를 사용할 수 있다.

```text
FormData
JSON 형태
서비스 SDK의 parameter object
```

이 문서는 특정 표현 방식을 고정하지 않는다.

현재 선택한 서비스에서 실제로 필요한 방식만 학습한다.

`FormData`, JSON, SDK parameter를 모두 억지로 사용하지 않는다.

---

### 2.24 실제 배포 환경 검증

v1.2는 로컬에서 전송이 성공하는 것만으로 완료하지 않는다.

최종 GitHub Pages 배포 URL에서 실제 전송을 다시 확인한다.

기본 검증:

```text

        ↓
valid Form 입력
        ↓
Submit
        ↓
submitting
        ↓

        ↓
success
```

또한 실패 상태도 가능한 범위에서 검증한다.

배포 환경에서 다음 문제를 확인한다.

```text
서비스 endpoint / 설정 오류
허용된 origin / domain 설정 문제
잘못된 경로
브라우저 Console error
Network request 실패
```

구체적인 서비스별 배포 설정은 선택한 서비스의 공식 문서를 따른다.

---

### 2.25 실제 수신 확인

UI에서 success가 보이는 것만으로 실제 전송 완료를 판단하지 않는다.

가능한 경우 외부 서비스의 관리 화면 또는 실제 수신 대상에서 메시지가 도착했는지 확인한다.

기본 관계:

```text
브라우저 success UI
        +
외부 서비스 / 수신 결과 확인
        ↓
실제 전송 검증
```

서비스가 정상적으로 요청을 수락했지만 최종 전달 방식이 비동기인 경우에는 해당 서비스가 제공하는 정상 확인 방법을 따른다.

### 2.26 기존 Light / Dark theme와 공존

확인 대상:

```text

submitting
success
transmission error
Submit disabled state
```

전송 상태를 추가하기 위해 theme CSS 구조를 다시 설계하지 않는다.

v1.3의 시스템 theme 감지는 추가하지 않는다.

---

### 2.27 기존 반응형 레이아웃과 공존

Contact Form의 기존 모바일 / 태블릿 / 데스크톱 레이아웃을 유지한다.

```text
모바일
태블릿
데스크톱
```

```text
가로 스크롤
Form 폭 깨짐
긴 오류 메시지 overflow
Submit button 위치 이상
```

전송 기능을 추가하기 위해 Contact Form 레이아웃을 다시 설계하지 않는다.

## 3. 목표 설계

v1.2 완료 시 Contact Form의 전체 구조는 다음과 같다.

```text
Contact Form
│
├── Name
├── Email
├── Message
├── Submit
│
└── 상태 UI
    ├── field validation error
    ├── submitting
    ├── success
    └── transmission error
```

동작 흐름:

```text
사용자 Submit
        ↓
submit event
        ↓
preventDefault()
        ↓
입력값 읽기
        ↓
기존 validation
        ↓

invalid
→ field validation error
→ 외부 요청 없음

valid
        ↓
submitting = true
        ↓
Submit 중복 실행 방지
        ↓
외부 서비스로 데이터 전송
        ↓
await 결과
        ↓

성공
→ success
→ 실제 전송 성공 UI
→ 필요하면 Form reset

실패
→ error
→ 전송 실패 UI
→ 재시도 가능
        ↓
submitting 종료
```

상태 관점:

```text
idle
  ↓ submit
validation
  ├── invalid → validation error
  │                ↓ 사용자 수정 / 재submit
  │                └──────────────→ validation
  │
  └── valid → submitting
                 ├── success → success
                 └── failure → error
                                  ↓ 재submit
                                  └────→ validation
```

v1.0과 비교하면 다음 변화가 생긴다.

```text
v1.0 Contact
입력 / submit
→ validation
→ 오류 또는 "validation 통과" 성공 UI

v1.2 Contact
입력 / submit
→ validation
→ valid일 때 비동기 실제 전송
→ submitting / success / error
→ 실제 전송 결과 UI
```

v0.7과 연결하면 다음 공통 구조를 확인할 수 있다.

```text
v0.7 Projects
외부 요청
→ loading
→ success / error / empty
→ DOM 렌더링

v1.2 Contact
validation 통과
→ submitting
→ success / error
→ DOM 렌더링
```

즉 v1.2는 처음 배우는 비동기 문법이 아니라 **기존 비동기 상태→렌더링 구조를 사용자 데이터 전송이라는 새로운 방향으로 확장하는 버전**이다.

## 4. 새롭게 배우는 개념

### 4.1 실제 Form 전송

v1.0까지의 Contact Form은 입력값을 검사했지만 외부 시스템으로 데이터를 보내지 않았다.

v1.2에서는 처음으로 다음 관계가 생긴다.

```text
브라우저의 사용자 입력
        ↓
외부 서비스 요청
        ↓
브라우저 밖의 시스템으로 전달
```

따라서 다음 두 의미를 구분한다.

```text
validation success
→ 입력 형식이 현재 조건에 맞음

transmission success
→ 외부 서비스가 실제 전송을 성공으로 처리함
```

---

### 4.2 전송 서비스

정적 웹사이트는 자체 서버를 만들지 않아도 외부 Form 서비스를 통해 메시지를 전달할 수 있다.

이번 프로젝트에서는 B1-1이 제시한 방향 안에서 외부 서비스를 하나 사용한다.

핵심은 서비스 제품 기능 전체를 배우는 것이 아니다.

다음 질문에 답할 수 있으면 된다.

```text
브라우저는 어디로 데이터를 보내는가
어떤 데이터가 전달되는가
성공 / 실패를 어떻게 알 수 있는가
어떤 설정값이 필요한가
```

---

### 4.3 비동기 전송

외부 전송은 요청 직후 즉시 결과가 확정되는 동작으로 취급하지 않는다.

```text
전송 시작
        ↓
결과 아직 없음
        ↓
대기
        ↓
나중에 성공 또는 실패 결정
```

이 구조는 v0.7에서 배운 GitHub API 요청과 동일한 비동기 성격을 가진다.

---

### 4.4 `async / await`의 재사용

`async / await`는 읽기 전용 API 호출뿐 아니라 데이터를 보내는 비동기 작업에도 사용할 수 있다.

```text
await
→ 외부 작업의 결과가 준비될 때까지
  현재 비동기 함수의 다음 처리를 기다림
```

JavaScript 전체가 멈춘다고 이해하지 않는다.

이벤트 루프 세부 이론으로 학습 범위를 확대하지 않는다.

---

### 4.5 `try / catch`와 사용자 오류 UI

비동기 전송 실패는 Console에 오류가 찍히는 것으로 끝내지 않는다.

```text
실패 발생
→ catch 또는 서비스 실패 경로
→ Form error 상태
→ 사용자 실패 UI
```

개발자 오류 확인과 사용자 피드백은 서로 다른 역할이라는 것을 이해한다.

---

### 4.6 Submitting 상태

`submitting`은 요청을 시작했지만 아직 결과가 결정되지 않은 상태다.

```text
idle
→ Submit
→ validation 성공
→ submitting
→ success 또는 error
```

이 상태가 없으면 사용자는 클릭이 처리되었는지 알기 어렵고, 프로그램은 중복 제출을 제어하기 어려워질 수 있다.

---

### 4.7 중복 제출

비동기 작업이 끝나기 전에 같은 동작을 다시 시작하면 동일 메시지가 여러 번 전송될 수 있다.

```text
첫 요청 진행 중
+
두 번째 요청 시작
        ↓
중복 데이터 전송 가능
```

따라서 현재 `submitting`인지 판단하거나 Submit control을 비활성화하는 방식으로 재진입을 막는다.

복잡한 동시성 제어 이론으로 확대하지 않는다.

---

### 4.8 Form 상태와 UI 상태

Contact Form의 현재 상태가 화면에 직접 대응한다.

```text
validation error
→ 필드 오류 메시지

submitting
→ 전송 중 표시

success
→ 전송 완료 메시지

error
→ 전송 실패 메시지
```

상태 이름 자체보다 **왜 현재 화면이 그렇게 보여야 하는지** 이해하는 것이 목표다.

---

### 4.9 상태 전이

한 상태가 영구히 유지되는 것이 아니라 사용자 행동과 외부 결과에 따라 바뀐다.

```text
idle
→ validation error
→ submitting
→ success
```

또는:

```text
idle
→ submitting
→ error
→ submitting
→ success
```

이런 변화 순서를 상태 전이라는 관점에서 이해한다.

상태 머신 이론으로 확대하지 않는다.

---

### 4.10 Validation과 전송의 책임 분리

두 기능의 책임을 구분한다.

```text
validateForm()
→ 입력값이 전송 가능한 형식인가 판단

sendForm()
→ valid한 데이터를 외부 서비스로 보냄
```

정확한 함수 이름은 구현에 따라 달라질 수 있다.

중요한 것은 다음 흐름이 코드에서 읽히는 것이다.

```text
먼저 검사
→ 통과하면 전송
```

---

### 4.11 요청과 응답

외부 서비스와의 통신은 다음처럼 이해한다.

```text
Request
→ 브라우저가 데이터와 함께 요청을 보냄

Response
→ 외부 서비스가 처리 결과를 돌려줌
```

HTTP 전체를 다시 공부하지 않는다.

현재 서비스에서 실제로 사용하는 요청 방식과 성공 / 실패 판정에 필요한 부분만 확인한다.

---

### 4.12 FormData / JSON / 서비스 parameter

브라우저의 입력값은 외부 서비스가 받을 수 있는 형식으로 구성되어야 한다.

서비스에 따라 방식이 달라질 수 있다.

```text
FormData
JSON
SDK parameter object
```

이번 버전에서는 선택한 서비스가 실제로 요구하는 하나의 방식만 이해한다.

세 방식을 모두 학습 과제로 만들지 않는다.

---

### 4.13 Client-side 공개 설정과 Secret

브라우저 JavaScript는 사용자가 내려받아 볼 수 있는 코드다.

따라서 브라우저 코드에 존재하는 값은 비밀이라고 가정할 수 없다.

```text
script.js에 들어간 값
→ 사용자도 확인 가능
```

이 사실을 바탕으로 다음을 구분한다.

```text
서비스가 공개 사용을 전제로 한 식별자
→ 공식 방식에 따라 사용 가능

비밀 인증 정보
→ 브라우저에 두지 않음
```

백엔드 비밀 관리 전체를 배우는 단계는 아니다.

---

### 4.14 실제 배포 검증

외부 서비스는 로컬 실행과 GitHub Pages 배포에서 환경이 다를 수 있다.

따라서 다음을 구분한다.

```text
로컬 성공
≠
배포 성공 자동 보장
```

v1.0에서 배운 배포 검증 원칙을 외부 Form 서비스에도 적용한다.

---

### 4.15 DevTools Network 재사용

v0.7 / v0.8에서 API 요청을 확인했던 Network 탭을 Form 전송에서도 사용한다.

다음 질문에 답할 수 있어야 한다.

```text
Submit했을 때 실제 요청이 발생했는가
몇 번 발생했는가
validation 실패 때는 요청이 없는가
응답 상태는 무엇인가
```

중복 제출 검증에도 직접 사용한다.

## 5. 완료 / 검증 기준

### 5.1 기존 validation 유지

다음 기존 validation이 정상 동작한다.

```text
빈 Name
빈 Email
잘못된 Email 형식
빈 Message
```

invalid 상태에서는 실제 외부 요청이 발생하지 않는다.

DevTools Network에서 확인할 수 있어야 한다.

---

### 5.2 Valid 입력만 전송

모든 필드가 valid인 경우에만 외부 서비스 요청이 시작된다.

```text
invalid
→ request 0회

valid
→ request 1회
```

---

### 5.3 Submitting 상태

실제 전송이 진행되는 동안 사용자가 전송 중임을 알 수 있다.

예:

```text
Sending...
```

또는 같은 의미의 상태 표현이 존재한다.

---

### 5.4 중복 제출 방지

전송 중 Submit을 반복해도 같은 메시지에 대한 외부 요청이 동시에 여러 번 발생하지 않는다.

Network 탭에서 확인한다.

---

### 5.5 실제 Success

외부 서비스가 정상 전송 결과를 반환하면 success 상태가 표시된다.

이 success는 단순 validation 통과가 아니라 실제 외부 전송 성공을 의미한다.

---

### 5.6 실제 수신 확인

가능한 경우 외부 서비스 관리 화면 또는 실제 수신 대상에서 전송된 메시지를 확인한다.

UI만 success로 보이고 실제 전달이 되지 않는 상태를 완료로 판단하지 않는다.

---

### 5.7 Error 상태

전송 실패 시 사용자에게 실패 사실을 표시한다.

다음 중 가능한 실패 경로를 최소 하나 실제로 확인한다.

```text
잘못된 서비스 설정
의도적인 잘못된 endpoint / service 설정
네트워크 실패를 재현할 수 있는 개발 환경
서비스가 반환하는 실패 응답
```

실패 재현 방식은 실제 선택한 서비스와 개발 환경에서 안전하고 되돌릴 수 있는 방법을 사용한다.

---

### 5.8 Error 후 재시도

전송 실패 후 Submit을 다시 사용할 수 있다.

```text
error
→ 입력 확인
→ 다시 Submit
→ validation
→ submitting
→ success 또는 error
```

버튼이 영구적으로 disabled 상태에 남지 않는다.

---

### 5.9 상태 UI 일관성

동시에 모순된 상태 메시지가 남지 않는다.

예:

```text
submitting인데 이전 success 메시지가 남음
success인데 Sending...이 계속 표시됨
error인데 Submit이 영구 비활성화됨
```

이런 상태가 없어야 한다.

---

### 5.10 Form reset 정책

Form을 성공 후 초기화하기로 했다면 실제 success 이후에만 초기화된다.

전송 실패 시 사용자가 작성한 입력값이 불필요하게 사라지지 않는다.

Form을 유지하기로 했다면 그 정책도 코드와 UI가 일관되어야 한다.

---

### 5.11 공개 설정과 비밀 정보

repository에 비밀 key / secret / 민감한 credential이 commit되어 있지 않다.

외부 서비스 설정값은 해당 서비스의 공식 프런트엔드 사용 지침과 일치한다.

---

### 5.12 GitHub Pages 검증

배포된 GitHub Pages URL에서 다음을 직접 확인한다.

```text
Form validation
valid submit
submitting
success
actual delivery
error / retry 가능한 흐름
```

로컬 검증만으로 v1.2 완료 처리하지 않는다.

---

### 5.13 모바일 / 태블릿 / 데스크톱

최소 다음 환경에서 Form을 확인한다.

```text
모바일
태블릿
데스크톱
```

상태 메시지와 Submit control이 레이아웃을 깨뜨리지 않는다.

---

### 5.14 Light / Dark theme

최소 다음 상태가 두 theme에서 읽을 수 있다.

```text
validation error
submitting
success
transmission error
disabled Submit
```

---

### 5.15 기존 v1.1 기능 회귀 확인

최소 다음을 다시 확인한다.

```text
Header / Navigation
Hamburger
Smooth scroll
Scroll-to-Top
Navigation scroll style
Theme Toggle
localStorage theme restore
Hero typing
Projects API
Projects filter
Contact validation
Intersection Observer
```

Contact 전송 기능 때문에 기존 기능이 깨지지 않는다.

---

### 5.16 Console / Network

최종 정상 동작에서 의도하지 않은 Console error가 없다.

Network 탭에서 다음 관계를 확인할 수 있다.

```text
invalid submit
→ Form service request 없음

valid submit
→ request 1회

repeated click while submitting
→ 중복 request 없음
```

---

### 5.17 이해 확인

다음 질문에 답할 수 있어야 한다.

```text
validation과 실제 전송은 무엇이 다른가
어떤 조건에서 send 함수가 실행되는가
submitting은 무엇을 의미하는가
왜 중복 제출을 막는가
외부 서비스 요청은 어떤 데이터를 보내는가
async / await가 어디에 사용되는가
try / catch는 어떤 실패를 처리하는가
success는 무엇을 기준으로 결정되는가
error 상태에서는 사용자가 무엇을 할 수 있는가
왜 배포 URL에서도 다시 테스트해야 하는가
왜 브라우저 코드에 secret을 둘 수 없는가
```


Contact Form은 이제 다음 전체 흐름을 가진다.

```text

        ↓

        ↓
client validation
        ↓

invalid
→ field error UI

valid
→ submitting
→ external form service
→ success / error
→ Contact UI
```
