# v1.3 — 시스템 다크 모드 감지 및 실시간 반영

## 1. 버전 목표

v1.2까지 완성한 B1-1 기본 기능과 확장 기능을 모두 유지한 채, 기존 Light / Dark Theme를 **사용자 선택뿐 아니라 시스템 환경 설정과도 연결**한다.

v0.5 / v1.0에서는 theme가 다음 두 입력만으로 결정되었다.

```text
페이지 시작
→ localStorage 확인

저장값 있음
→ 저장된 사용자 theme 적용

저장값 없음
→ 기본 light theme 적용
```

v1.3에서는 저장된 사용자 선택이 없을 때의 기본값을 시스템 theme로 확장한다.

```text
페이지 시작
        ↓
localStorage 확인
        ↓

사용자 저장값 있음
→ 저장된 사용자 theme 적용

사용자 저장값 없음
→ 현재 시스템 theme 확인
→ light / dark 결정
→ DOM theme 적용
```

또한 페이지가 실행 중인 상태에서 OS의 Light / Dark 설정이 바뀌면, **사용자가 직접 선택한 theme가 없는 경우에만** 화면을 즉시 갱신한다.

```text
OS theme change
        ↓
사용자 저장 theme 존재 여부 확인
        ↓

저장값 있음
→ OS 변경 무시
→ 사용자 선택 유지

저장값 없음
→ 새 시스템 theme 적용
→ DOM 갱신
→ 화면 즉시 변경
```

v1.3의 핵심은 단순히 시스템이 dark인지 확인하는 것이 아니다.

다음 두 정보를 분리해서 이해하는 것이다.

```text
theme
→ 현재 화면에 적용할 light / dark 값

theme source
→ 그 값이 어디에서 왔는가
   - user
   - system
```

따라서 이 버전의 핵심 학습 흐름은 다음과 같다.

```text
사용자 선택 ─────┐
                 │
                 ↓
              theme 결정
                 ↑
                 │
시스템 설정 ─────┘

충돌 시
→ 사용자 선택 우선
```

v1.3이 끝나면 최소한 다음 관계를 설명할 수 있어야 한다.

```text
prefers-color-scheme은 무엇을 나타내는가
→ matchMedia는 무엇을 확인하는가
→ MediaQueryList는 어떤 시스템 상태를 나타내는가
→ 초기 load에서 localStorage와 시스템 설정 중 무엇을 먼저 확인하는가
→ 왜 사용자 선택이 시스템 설정보다 우선하는가
→ 현재 theme 값과 theme source는 어떻게 다른가
→ OS theme change 이벤트는 언제 화면 변경으로 이어지는가
→ 사용자 저장값이 있으면 왜 OS change를 무시하는가
→ 사용자 저장값이 없으면 왜 OS change를 즉시 반영하는가
→ DOM의 data-theme와 기존 CSS 변수는 어떻게 그대로 재사용되는가
```

v1.3은 현재 계획된 B1-1 확장 기능의 마지막 버전이다.

완료 후에는 다음 전체 상태가 된다.

```text
v1.0
B1-1 기본 완료 + 프로젝트 필터링
        ↓
v1.1
Hero 타이핑 효과
        ↓
v1.2
실제 Contact Form 전송
        ↓
v1.3
시스템 theme 감지
+ OS theme 변경 실시간 반영
```

## 2. 요구사항

### 2.1 v1.2 완료 상태를 기반으로 작업

v1.2까지 완성한 기존 구조와 기능을 모두 유지한다.

최소한 다음 기능이 그대로 동작해야 한다.

```text
Header / Navigation
Hero
Hero typing effect
About
Skills
Projects
Contact
Footer

Responsive layout
Hamburger menu
Smooth internal scroll
Scroll-to-Top
Navigation scroll style

Light / Dark theme
Theme Toggle
localStorage theme restore

Contact Form validation
Contact Form actual sending
submitting / success / error
중복 제출 방지

GitHub API
loading / success / error / API empty
403 rate limit error
Retry
Projects dynamic rendering
Project filter

Intersection Observer reveal
GitHub Pages deployment
```

시스템 theme 기능을 추가하기 위해 다음 구조를 다시 설계하지 않는다.

```text
Projects

Hero typing
문자열 → index → textContent → setTimeout → 종료

Contact
submit → validation → submitting → external send → success / error
```

v1.3의 수정 범위는 기본적으로 기존 Theme 기능에 한정한다.

```text
기존 Theme 기능
+ 시스템 theme 확인
+ 초기 theme 우선순위
+ OS theme change 감지
+ 사용자 선택과 시스템 선택의 충돌 처리
```

---

### 2.2 기존 Theme 구조 유지

v0.5 / v1.0에서 만든 Theme 구조를 그대로 기반으로 사용한다.

기존 핵심 구조:

```text
Theme Toggle click
        ↓
현재 theme 확인
        ↓
light ↔ dark
        ↓
DOM data-theme 변경
        ↓
CSS 변수 변경
        ↓
화면 변경
        ↓
localStorage 저장
```

기존 CSS의 기본 역할도 유지한다.

```text
:root
→ 기본 theme variables

[data-theme="dark"]
→ dark theme variables
```

v1.3에서는 시스템 theme를 반영하기 위해 각 요소의 색상 규칙을 다시 작성하지 않는다.

시스템 설정은 **어떤 theme 값을 적용할지 결정하는 새로운 입력값**이고, 실제 화면 표현은 기존 `data-theme`와 CSS 변수 구조가 계속 담당한다.

---

### 2.3 `prefers-color-scheme`

시스템의 Light / Dark 선호 설정은 `prefers-color-scheme`을 기준으로 확인한다.

이번 버전에서 필요한 값은 다음 두 가지다.

```text
light
dark
```

핵심 의미:

```text
prefers-color-scheme
→ 사용자의 운영체제 / 브라우저 환경이 선호하는 색상 scheme을 웹페이지에 알려주는 신호
```

모든 CSS Media Feature를 학습하지 않는다.

현재 Theme 기능에 필요한 `prefers-color-scheme`만 다룬다.

---

### 2.4 `matchMedia()`

JavaScript에서는 현재 시스템이 dark theme를 선호하는지 확인하기 위해 `matchMedia()`를 사용한다.

개념 구조:

```text
window.matchMedia(...)
        ↓
prefers-color-scheme 조건 확인
        ↓
MediaQueryList
        ↓
현재 조건 일치 여부 확인
```

예시 개념:

```text
(prefers-color-scheme: dark)
```

정확한 변수명과 코드 배치는 현재 `main.js` 구조에 맞춰 결정한다.

`matchMedia()`의 전체 기능이나 다른 Media Query 활용으로 학습 범위를 확대하지 않는다.

---

### 2.5 현재 시스템 theme 판단

시스템 dark 조건의 일치 여부를 이용하여 현재 시스템 theme를 `light` 또는 `dark`로 결정할 수 있어야 한다.

개념 흐름:

```text
system prefers dark?
        ↓
YES
→ systemTheme = dark

NO
→ systemTheme = light
```

중요한 점은 시스템 theme가 항상 최종 화면 theme가 되는 것은 아니라는 것이다.

시스템 값은 다음 경우에만 최종 theme의 입력으로 사용한다.

```text
저장된 사용자 theme가 없음
```

---

### 2.6 저장된 사용자 선택의 존재 여부

v1.3에서는 `localStorage`에 저장된 `light` / `dark` 값 자체뿐 아니라 **사용자가 직접 선택한 값이 존재하는지**가 중요한 상태가 된다.

개념:

```text
localStorage theme 있음
→ 사용자 선택 있음

localStorage theme 없음
→ 사용자 선택 없음
```

이 구분은 다음 두 기능 모두에 사용된다.

```text
1. 페이지 초기 theme 결정
2. OS theme change 반영 여부 결정
```

별도의 복잡한 사용자 설정 객체를 만들 필요는 없다.

현재 저장값의 존재 여부로 사용자 선택이 있는지를 판단할 수 있으면 충분하다.

---

### 2.7 초기 theme 결정 우선순위

페이지가 시작될 때는 반드시 다음 순서로 theme를 결정한다.

```text
페이지 시작
        ↓
localStorage theme 확인
        ↓

저장값 있음?
        ↓
YES
→ 사용자 저장 theme 사용
→ DOM 적용

NO
→ 시스템 theme 확인
→ light / dark 결정
→ DOM 적용
```

이를 우선순위로 표현하면 다음과 같다.

```text
1순위: 저장된 사용자 선택
2순위: 현재 시스템 설정
```

다음과 같은 흐름으로 만들지 않는다.

```text
잘못된 예
시스템 theme 먼저 적용
→ 잠시 화면 변경
→ 나중에 localStorage 확인
→ 다시 사용자 theme로 변경
```

가능한 범위에서 초기 theme 결정 로직을 한 흐름으로 읽을 수 있게 유지한다.

---

### 2.8 사용자 선택이 시스템 설정보다 우선

사용자가 Theme Toggle로 직접 Light / Dark를 선택한 경우 해당 선택을 시스템 설정보다 우선한다.

예:

```text
시스템: light
사용자 저장값: dark

결과:
화면 = dark
```

또는:

```text
시스템: dark
사용자 저장값: light

결과:
화면 = light
```

이 우선순위는 페이지 시작 시뿐 아니라 실행 중 OS 설정이 바뀔 때도 동일하다.

---

### 2.9 Theme Toggle 기존 동작 유지

사용자가 Theme Toggle을 누르면 기존과 같이 현재 theme를 반대로 변경한다.

```text
Theme Toggle click
        ↓
현재 화면 theme 확인
        ↓
light ↔ dark
        ↓
DOM data-theme 변경
        ↓
localStorage 저장
        ↓
화면 변경
```

v1.3에서 중요한 추가 의미는 다음이다.

```text
Theme Toggle을 사용함
→ 사용자가 명시적으로 theme를 선택함
→ 이후 시스템 theme보다 사용자 선택이 우선함
```

따라서 사용자가 직접 선택한 이후에는 OS theme가 변경되어도 화면이 자동으로 따라가지 않는다.

---

### 2.10 사용자 선택을 `localStorage`에 유지

v0.5에서 사용하던 사용자 theme 저장 기능을 유지한다.

저장 대상:

```text
light
또는
dark
```

v1.3에서도 시스템 theme 자체를 사용자의 선택인 것처럼 `localStorage`에 자동 저장하지 않는다.

그렇게 하면 다음 문제가 생긴다.

```text
첫 방문
→ 시스템 dark
→ dark를 localStorage에 저장

이후
→ 코드상 사용자 선택이 있는 것처럼 보임
→ OS가 light로 바뀌어도 따라가지 않음
```

따라서 의미를 구분한다.

```text
localStorage theme
→ 사용자가 직접 선택한 theme

system theme
→ 사용자 저장값이 없을 때 사용하는 환경 기본값
```

---

### 2.11 시스템 theme를 자동 저장하지 않음

시스템에서 읽은 Light / Dark 값은 현재 화면 theme를 결정하는 데 사용할 수 있지만, 그것을 사용자의 선택으로 `localStorage`에 기록하지 않는다.

기본 흐름:

```text
사용자 선택 없음
OS = dark
        ↓
화면 = dark
        ↓
localStorage theme는 여전히 없음
```

그래야 페이지 실행 중 OS가 `dark → light`로 바뀌었을 때 다음 변화가 가능하다.

```text
OS dark → light
→ 사용자 선택 없음 확인
→ 화면 light로 변경
```

---

### 2.12 `MediaQueryList` 변경 이벤트

`matchMedia()`로 얻은 시스템 theme 조건은 현재 값만 읽는 데 그치지 않는다.

페이지 실행 중 조건이 바뀌는 것도 감지한다.

기본 구조:

```text
MediaQueryList
        ↓
change event
        ↓
현재 시스템 dark 여부 변경
        ↓
OS theme change handler 실행
```

이번 버전에서는 `MediaQueryList`의 모든 API를 학습하지 않는다.

다음 관계만 이해하면 된다.

```text
어떤 시스템 조건을 관찰하는가
→ 언제 change 이벤트가 발생하는가
→ handler가 무엇을 판단하는가
```

---

### 2.13 OS theme 변경 실시간 반영

사용자 선택이 없는 상태에서는 페이지 실행 중 OS theme 변경을 즉시 화면에 반영한다.

예:

```text
사용자 선택 없음
OS = light
화면 = light
        ↓
OS → dark
        ↓
change event
        ↓
새 system theme = dark
        ↓
DOM data-theme = dark
        ↓
화면 즉시 dark
```

반대 방향도 동일하다.

```text
OS dark → light
→ change 감지
→ system theme = light
→ DOM 갱신
→ 화면 light
```

페이지를 새로고침해야만 시스템 변경이 반영되는 구조로 끝내지 않는다.

실행 중 변경 반영까지 v1.3의 명시적인 범위다.

---

### 2.14 OS 변경 시 사용자 선택 존재 여부 재확인

OS theme change handler는 단순히 시스템 값을 읽어 바로 DOM에 적용하지 않는다.

먼저 사용자 저장값이 있는지 확인한다.

```text
OS theme change
        ↓
localStorage 사용자 theme 확인
        ↓

저장값 있음
→ 시스템 변경 무시
→ 사용자 theme 유지

저장값 없음
→ 새 시스템 theme 적용
→ DOM 변경
```

이 조건이 v1.3의 핵심 우선순위 로직이다.

---

### 2.15 사용자 선택이 있을 때 OS 변경 무시

다음 상태를 반드시 검증한다.

```text
OS = light
사용자 선택 = dark
화면 = dark
```

이후 OS를 변경한다.

```text
OS light → dark
또는
OS dark → light
```

결과는 항상 다음과 같아야 한다.

```text
사용자 선택 = dark
화면 = dark
```

즉 OS change 이벤트는 발생할 수 있지만 최종 theme 상태를 바꾸지는 않는다.

---

### 2.16 `theme`와 `theme source` 구분

v1.3에서는 단순히 현재 화면이 `light`인지 `dark`인지만 보면 상태를 완전히 이해할 수 없다.

예를 들어 두 상황은 화면은 같지만 의미가 다르다.

```text
상황 A
OS = dark
사용자 저장값 없음
화면 = dark
source = system

상황 B
OS = light
사용자 저장값 = dark
화면 = dark
source = user
```

두 경우 모두 현재 `theme` 값은 `dark`다.

그러나 다음 OS 변경에 대한 반응은 다르다.

```text
source = system
→ OS change 반영

source = user
→ OS change 무시
```

복잡한 별도 상태 관리 객체를 반드시 만들 필요는 없다.

하지만 코드와 학습 과정에서는 이 두 의미를 구분할 수 있어야 한다.

---

### 2.17 기존 `data-theme` 렌더링 구조 재사용

시스템 theme를 감지한 뒤 실제 화면 변경은 기존 DOM theme 구조를 사용한다.

```text
theme 결정
        ↓
DOM data-theme 변경
        ↓
CSS selector
        ↓
CSS variables
        ↓
화면 theme 변경
```

JavaScript에서 각 요소의 색상을 직접 변경하지 않는다.

시스템 theme와 사용자 theme를 서로 다른 CSS 구현으로 분리하지 않는다.

둘은 **theme를 결정하는 입력 source만 다르고, 최종 렌더링 경로는 동일하다.**

---

### 2.18 시스템 감지와 기존 CSS 역할의 구분

`prefers-color-scheme`은 시스템 선호를 나타내는 기준이고, JavaScript에서는 이를 `matchMedia()`로 읽고 변경 이벤트를 감지한다.

현재 프로젝트의 실제 Light / Dark 표현은 이미 `data-theme`와 CSS 변수로 완성되어 있다.

따라서 v1.3의 기본 설계는 다음 책임 분리를 유지한다.

```text
시스템 환경
→ prefers-color-scheme

JavaScript
→ matchMedia
→ 사용자 선택 여부 확인
→ 최종 theme 결정
→ data-theme 변경

CSS
→ data-theme에 맞는 변수 적용
→ 실제 화면 표현
```

같은 색상 체계를 별도의 시스템 전용 theme CSS로 다시 작성하지 않는다.

---

### 2.19 시스템 설정을 지원하지 않거나 예상과 다른 경우의 범위

v1.3의 목표는 최신 Chrome과 현재 프로젝트 개발 환경에서 `prefers-color-scheme` / `matchMedia`를 사용해 시스템 Light / Dark 상태를 연결하는 것이다.

브라우저 호환성 폴리필, 구형 브라우저 전용 분기, 별도의 fallback library를 추가하는 방향으로 확대하지 않는다.

현재 개발 환경에서 기능이 정상 동작하는지 직접 검증한다.

---

### 2.20 사용자 선택 초기화 UI는 추가하지 않음

현재 Sources는 사용자가 직접 선택한 theme가 있으면 이를 계속 우선하도록 정의한다.

따라서 v1.3에서 다음과 같은 새로운 UI를 임의로 추가하지 않는다.

```text
System theme 버튼
Auto theme 버튼
Reset theme 버튼
3-state theme selector
```

사용자 선택이 없는 상태를 검증할 때는 DevTools에서 해당 `localStorage` 값을 제거하거나 현재 프로젝트의 기존 저장 상태를 초기화하여 확인할 수 있다.

이 버전의 목표는 3가지 theme 선택 UI를 만드는 것이 아니라 **user 선택과 system 설정의 우선순위를 이해하는 것**이다.

---

### 2.21 초기 화면 깜빡임 최적화는 별도 범위로 확대하지 않음

초기 theme 결정 과정에서 페이지가 아주 짧게 기본 theme로 보였다가 바뀌는 문제를 발견할 수 있다.

그러나 v1.3의 핵심 요구사항은 다음이다.

```text
저장 사용자 theme 우선
저장값 없으면 시스템 theme
OS 변경 실시간 반영
```

이를 해결하기 위해 script 위치를 대규모 변경하거나 별도의 inline script, 복잡한 preload 전략, 렌더링 최적화 체계를 추가하는 것은 기본 범위로 삼지 않는다.

실제 사용성 문제가 명확하게 발생하면 현재 구조를 크게 바꾸지 않는 최소 수정만 검토한다.

---

### 2.22 기존 기능과의 공존

v1.3 Theme 확장을 추가한 뒤에도 v1.2까지의 기능 전체가 정상 동작해야 한다.

특히 다음 독립 상태와 충돌하지 않아야 한다.

```text
Theme
→ user / system source
→ light / dark

Hero typing
→ current index

Contact
→ validation / submitting / success / error

Projects
→ loading / success / error / empty
→ current filter

Intersection Observer
→ reveal state
```

Theme 로직을 수정한 뒤 JavaScript 초기 실행 과정에서 오류가 발생하여 다른 기능 전체가 중단되지 않아야 한다.

---

### 2.23 Light / Dark 모든 UI 검증

시스템에서 theme가 결정되든 사용자가 직접 선택하든 최종 렌더링은 같은 Light / Dark UI를 사용한다.

따라서 최소 다음을 두 theme 모두에서 확인한다.

```text
Header / Navigation
Hero / typing
About
Skills
Projects cards / filter / 상태 UI
Contact Form / validation / sending states
Footer
Scroll-to-Top
Intersection Observer로 표시된 콘텐츠
```

시스템 theme 기능 추가 때문에 기존 dark CSS 또는 light CSS를 새로 디자인하지 않는다.

---

### 2.24 GitHub Pages 배포 환경 검증

v1.3은 로컬에서만 검증하고 끝내지 않는다.

GitHub Pages 배포 URL에서도 최소 다음을 확인한다.

```text
localStorage 사용자 선택 없음
→ 시스템 light / dark에 따라 초기 화면 결정

사용자 Theme Toggle 선택
→ localStorage 저장
→ 새로고침 후 유지

사용자 저장값 없음
→ 실행 중 OS theme 변경
→ 화면 즉시 반영

사용자 저장값 있음
→ 실행 중 OS theme 변경
→ 사용자 선택 유지
```

시스템 theme 감지는 별도의 서버 기능이 아니므로 정적 배포에서도 정상 동작해야 한다.

## 3. 목표 설계

v1.3 완료 시 Theme 기능은 다음 구조를 가진다.

```text
                        ┌─────────────────────┐
                        │ localStorage theme? │
                        └──────────┬──────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     │                           │
                    YES                          NO
                     │                           │
                     ↓                           ↓
              user theme 사용          prefers-color-scheme
                     │                           │
                     │                           ↓
                     │                    system theme
                     │                           │
                     └─────────────┬─────────────┘
                                   ↓
                            최종 theme 결정
                                   ↓
                           DOM data-theme
                                   ↓
                            CSS variables
                                   ↓
                                화면
```

초기 로드의 핵심 흐름:

```text
페이지 시작
        ↓
사용자 저장값 확인
        ↓

있음
→ source = user
→ 저장 theme 적용

없음
→ source = system
→ matchMedia로 시스템 theme 확인
→ 시스템 theme 적용
        ↓
DOM data-theme
        ↓
화면
```

사용자 Theme Toggle 흐름:

```text
Theme Toggle click
        ↓
현재 theme 확인
        ↓
다음 theme 결정
        ↓
source = user
        ↓
DOM data-theme 변경
        ↓
localStorage 저장
        ↓
화면 변경
```

OS theme change 흐름:

```text
MediaQueryList change
        ↓
현재 localStorage 사용자 theme 확인
        ↓

사용자 저장값 있음
→ source = user
→ 현재 사용자 theme 유지
→ DOM 변경 없음

사용자 저장값 없음
→ source = system
→ 새 시스템 theme 결정
→ DOM data-theme 변경
→ 화면 즉시 변경
```

v0.5와 비교하면 다음처럼 확장된다.

```text
v0.5
사용자 click
→ theme 결정
→ DOM
→ localStorage

v1.3
사용자 선택 ───┐
               ├→ 우선순위 판단 → theme 결정 → DOM → 화면
시스템 설정 ───┘

+ OS 환경 change event
→ 우선순위 다시 판단
→ 필요한 경우 DOM 갱신
```

이 구조에서 가장 중요한 규칙은 다음 하나다.

```text
사용자의 명시적 선택 > 시스템 설정
```

## 4. 새롭게 배우는 개념

### 4.1 시스템 환경 설정과 웹페이지

웹페이지의 상태는 사용자 click이나 서버 데이터만으로 바뀌는 것이 아니다.

브라우저가 운영체제의 환경 설정을 웹페이지에 전달할 수도 있다.

v1.3의 입력원:

```text
사용자 Theme Toggle
시스템 Light / Dark 설정
```

이 둘이 같은 theme 상태에 영향을 준다.

---

### 4.2 `prefers-color-scheme`

사용자가 시스템에서 선호하는 색상 scheme을 표현하는 Media Feature라는 수준에서 이해한다.

현재 프로젝트에서는 다음 판단에만 사용한다.

```text
시스템이 dark를 선호하는가?
```

Media Query 전체를 다시 학습하지 않는다.

v0.3에서 배운 화면 폭 Media Query와 달리 이번에는 **화면 크기가 아니라 사용자 환경 선호**를 다룬다는 차이를 이해한다.

---

### 4.3 `matchMedia()`

JavaScript가 특정 Media Query 조건의 현재 일치 여부를 확인할 수 있게 해주는 브라우저 API라는 수준에서 이해한다.

핵심 관계:

```text
Media Query 조건
        ↓
matchMedia
        ↓
현재 조건 일치 여부
```

---

### 4.4 `MediaQueryList`

`matchMedia()`가 반환하는 결과가 현재 조건의 상태를 나타내며, 그 조건이 바뀌는 것도 감지할 수 있다는 정도까지 이해한다.

이번 버전에서 필요한 역할:

```text
현재 dark 조건 일치 여부 확인
change event 감지
```

그 밖의 API 전체는 학습하지 않는다.

---

### 4.5 시스템 설정 변경 이벤트

사용자가 OS Light / Dark 설정을 바꾸면 웹페이지가 실행 중에도 그 변화를 감지할 수 있다.

```text
외부 환경 변화
        ↓
change event
        ↓
JavaScript handler
        ↓
상태 판단
        ↓
필요한 DOM 변경
```

v0.4의 사용자 click event와 비교한다.

```text
v0.4
사용자 → 웹페이지 control click

v1.3
사용자 → OS 설정 변경
→ 브라우저가 웹페이지에 change event 전달
```

---

### 4.6 외부 환경 변화에 따른 상태 변경

지금까지 주요 상태 입력은 다음과 같았다.

```text
click
input / submit
API response
scroll / viewport 진입
시간 경과
```

v1.3에서는 새로운 입력이 추가된다.

```text
OS 환경 설정 change
```

이 입력 역시 결국 다음 구조로 연결된다.

```text
Event
→ 조건 판단
→ 상태 결정
→ DOM 변경
→ 화면 변화
```

---

### 4.7 상태의 여러 입력원

하나의 화면 상태에 둘 이상의 입력원이 존재할 수 있음을 이해한다.

```text
Theme 상태
        ↑
        ├── 사용자 선택
        └── 시스템 설정
```

입력원이 여러 개라면 어떤 값을 사용할지 규칙이 필요하다.

---

### 4.8 우선순위 규칙

v1.3의 우선순위는 다음이다.

```text
사용자 명시적 선택
        >
시스템 기본 설정
```

이는 단순한 코드 순서가 아니라 제품 동작 규칙이다.

코드가 이 규칙을 표현하도록 만든다.

---

### 4.9 `theme`와 `theme source`

상태값과 그 상태가 어디에서 왔는지를 구분한다.

```text
theme
→ light / dark

source
→ user / system
```

같은 `dark`라도 source에 따라 이후 시스템 change에 대한 반응이 달라질 수 있다.

---

### 4.10 기본값과 사용자 설정값

시스템 theme는 **사용자 설정이 없을 때 사용하는 기본값**이다.

```text
사용자 선택 없음
→ 시스템 설정 사용

사용자 선택 있음
→ 시스템 기본값보다 사용자 설정 우선
```

이 구조를 통해 기본값과 override의 개념을 경험한다.

---

### 4.11 `localStorage` 의미 확장

v0.5에서는 `localStorage`를 단순히 마지막 theme를 저장하는 곳으로 경험했다.

v1.3에서는 저장값의 **존재 자체가 우선순위를 결정하는 신호**가 된다.

```text
값 있음
→ 사용자가 직접 선택함

값 없음
→ 사용자 선택 없음
→ system을 따름
```

---

### 4.12 초기 상태 결정

초기 상태는 임의의 기본값 하나로 끝나는 것이 아니라 여러 입력의 우선순위를 적용해 계산할 수 있음을 이해한다.

```text
저장 사용자 theme?
        ↓
YES → user theme
NO  → system theme
```

이후 React 등에서 초기 state를 결정할 때도 연결되는 기본 사고방식이다.

---

### 4.13 동일한 렌더 경로 재사용

상태가 어디에서 왔든 최종 theme 렌더링은 하나의 경로를 사용한다.

```text
user theme ───┐
              ├→ final theme → data-theme → CSS → 화면
system theme ─┘
```

두 source마다 별도 화면 구현을 만들지 않는 이유를 이해한다.

---

### 4.14 기존 개념 재사용

v1.3은 다음 기존 개념을 다시 사용한다.

```text
v0.4
addEventListener / event handler

v0.5
state / data-theme / CSS variables / localStorage

v0.6
조건에 따른 상태 결정

v0.7
외부 결과에 따라 상태를 결정하는 사고방식
```

새로운 API 자체보다 기존 개념이 어떻게 결합되는지를 이해한다.

---

### 4.15 이번 버전에서 깊게 다루지 않는 이론

다음 주제로 학습 범위를 확대하지 않는다.

```text
브라우저 렌더링 엔진 내부 구현
운영체제 theme API 내부 구조
모든 CSS Media Feature
MediaQueryList 전체 API
브라우저 호환성 폴리필 설계
복잡한 상태 관리 패턴
React Context / 상태 관리 라이브러리
SSR theme hydration
FOUC 최적화 이론
```

현재 코드에서 다음을 설명할 수 있으면 충분하다.

```text
시스템 상태를 어떻게 읽는가
→ 사용자 선택이 있는지 어떻게 판단하는가
→ 둘 중 무엇이 우선하는가
→ OS change가 언제 DOM 변경으로 이어지는가
```

## 5. 완료 / 검증 기준

### 5.1 초기 상태 — 사용자 선택 없음 / 시스템 light

다음 조건을 만든다.

```text
localStorage theme 없음
OS theme = light
```

페이지를 연다.

결과:

```text
화면 = light
DOM theme = light에 대응하는 상태
사용자 theme가 자동 저장되지 않음
```

---

### 5.2 초기 상태 — 사용자 선택 없음 / 시스템 dark

조건:

```text
localStorage theme 없음
OS theme = dark
```

페이지를 연다.

결과:

```text
화면 = dark
DOM theme = dark
사용자 theme가 자동 저장되지 않음
```

---

### 5.3 초기 상태 — 사용자 선택 있음

조건 예:

```text
localStorage theme = dark
OS theme = light
```

결과:

```text
화면 = dark
사용자 선택 우선
```

반대 조건도 확인한다.

```text
localStorage theme = light
OS theme = dark

결과
→ 화면 = light
```

---

### 5.4 Theme Toggle 사용자 선택

사용자가 Theme Toggle을 누르면:

```text
현재 theme 반전
→ DOM data-theme 갱신
→ 화면 변경
→ localStorage 사용자 theme 저장
```

이후 새로고침해도 해당 사용자 선택이 유지되어야 한다.

---

### 5.5 시스템 theme를 사용자 선택으로 저장하지 않음

조건:

```text
localStorage theme 없음
OS = dark
```

페이지 로드 후 확인한다.

```text
화면 = dark
하지만 localStorage theme는 없음
```

이 검증을 통과해야 시스템 설정과 사용자 선택의 의미가 섞이지 않은 것이다.

---

### 5.6 실행 중 OS 변경 — 사용자 선택 없음

조건:

```text
localStorage theme 없음
현재 OS = light
현재 화면 = light
```

페이지를 닫거나 새로고침하지 않고 OS를 dark로 변경한다.

결과:

```text
change event 감지
→ 사용자 선택 없음 확인
→ system theme dark 결정
→ DOM 갱신
→ 화면 즉시 dark
```

반대 방향도 확인한다.

```text
OS dark → light
→ 화면 즉시 light
```

---

### 5.7 실행 중 OS 변경 — 사용자 선택 있음

조건 예:

```text
localStorage theme = dark
현재 화면 = dark
```

OS theme를 변경한다.

결과:

```text
change event가 발생해도
→ 사용자 저장값 있음
→ OS 변경 무시
→ 화면 dark 유지
```

반대로 사용자 저장값이 light인 경우에도 같은 규칙이 적용되어야 한다.

---

### 5.8 우선순위 일관성

초기 로드와 실행 중 변경에서 동일한 규칙이 적용되어야 한다.

```text
사용자 선택 있음
→ 항상 사용자 선택 우선

사용자 선택 없음
→ 항상 시스템 설정 사용
```

#### 목표

이 Task에서는 change handler를 연결하고 새 시스템 theme를 읽을 수 있게 한다.

#### VS Code AI 요청 예시

```text
- 사용자 theme 있음 → OS 변경을 화면에 적용하지 않음
- 사용자 theme 없음 → 새로운 system light/dark를 DOM data-theme에 적용

제약:
- system theme를 localStorage에 저장하지 마.
- Theme Toggle 구조를 다시 만들지 마.
- 다른 이벤트나 기능은 수정하지 마.
- 외부 library를 사용하지 마.
```

#### Diff 확인

```text
change listener 1개가 명확하게 추가되었는가
OS change마다 사용자 저장값을 확인하는가
system 값을 저장하지 않는가
```

#### 코드 확인

다음 흐름을 직접 추적한다.

```text
MediaQueryList change
→ saved user theme 확인
→ 없음
   → 새 system theme 결정
   → data-theme
→ 있음
   → return / 무시
```

#### 브라우저 확인

먼저 사용자 선택 없는 상태에서 확인한다.

```text

→ 새로고침 없이 화면 dark

OS dark → light
→ 새로고침 없이 화면 light
```

#### 이해 확인

```text
change 이벤트는 무엇이 바뀌었을 때 발생하는가
왜 handler가 localStorage를 다시 확인하는가
```

### Task 6 — 사용자 선택이 있을 때 OS 변경 무시 검증

#### 목표

가장 중요한 충돌 조건을 별도 Task로 검증한다.

새 기능을 추가하는 Task가 아니라 **우선순위 검증 Task**다.

#### VS Code AI 요청 예시

```text

OS theme가 변경되어도 화면 theme가 바뀌면 안 된다.

코드에서:
- OS change handler가 saved user theme를 확인하는 위치
- 사용자 선택이 있으면 DOM 변경을 건너뛰는 위치

```

```text
검증만 했다면 변경 없음
문제가 있었다면 해당 조건만 최소 수정
```

```text
savedTheme 있음

```

```text

```


## 8. v1.3 완료 후 상태

v1.3가 완료되면 B1-1 프로젝트는 현재 계획된 기본 기능과 확장 기능을 모두 가진다.

```text
v1.0
B1-1 필수 요구사항
+ Project filtering
+ GitHub Pages deployment

        ↓

v1.1
Hero typing effect

        ↓

v1.2
Actual Contact Form sending

        ↓

v1.3
System theme detection
+ real-time OS theme change
```

Theme 기능은 최종적으로 다음 구조가 된다.

```text
                     Theme Inputs
                         │
          ┌──────────────┴──────────────┐
          │                             │
          ↓                             ↓
   User Preference               System Preference
   localStorage                  prefers-color-scheme
          │                             │
          └──────────────┬──────────────┘
                         ↓
                 Priority Decision
                         ↓
            user preference exists?
                 │               │
                YES              NO
                 │               │
                 ↓               ↓
             user theme      system theme
                 └───────┬───────┘
                         ↓
                     data-theme
                         ↓
                   CSS variables
                         ↓
                       화면
```

실행 중에는 다음 흐름이 추가된다.

```text
OS theme change
        ↓
MediaQueryList change event
        ↓
user preference exists?
        ↓

YES
→ 사용자 선택 유지

NO
→ 새 system theme 적용
→ data-theme 변경
→ 화면 실시간 변경
```

학습 관점에서 B1-1 전체 과정은 다음까지 확장된다.

```text
HTML structure
→ CSS expression
→ responsive layout
→ DOM / user events
→ state / localStorage
→ form validation state
→ async API state
→ data filtering
→ viewport observation
→ deployment
→ time-based DOM change
→ async outbound form state
→ external environment state
```

v1.3에서 새롭게 완성되는 마지막 핵심 흐름은 다음이다.

```text
외부 환경 변화
→ browser event
→ priority 판단
→ state 결정
→ DOM 변경
→ 화면 변화
```

그리고 Theme 상태에서는 다음 제품 규칙을 설명할 수 있어야 한다.

```text
사용자의 명시적인 선택이 시스템 기본 설정보다 우선한다.
```

이 상태가 `extended-design.md`에 정의된 현재 B1-1 확장 설계의 완료 기준이다.
