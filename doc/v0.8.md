# v0.8 — 프로젝트 필터링

## 1. 버전 목표

v0.7에서 GitHub API로 가져온 전체 repository 데이터를 기반으로, 사용자가 선택한 언어 조건에 따라 **화면에 보여줄 프로젝트 데이터만 가공하여 다시 렌더링하는 구조**를 구현한다.

이 버전의 핵심 흐름은 다음과 같다.

```text
사용자 filter 선택
        ↓
현재 filter 상태 변경
        ↓
v0.7에서 받은 원본 repositories 유지
        ↓
filter() 적용
        ↓
filtered repositories
        ↓
Project 카드 표현으로 변환
        ↓
Projects DOM 재렌더링
```

v0.8의 가장 중요한 학습 포인트는 **원본 데이터와 화면에 보여줄 파생 데이터를 구분하는 것**이다.

```text
원본 repositories
→ GitHub API에서 받은 전체 데이터
→ filter 선택이 바뀌어도 유지

filter 상태
→ 사용자가 현재 선택한 조건

filtered repositories
→ 원본 repositories에 현재 filter를 적용한 결과
→ 화면에 보여줄 데이터
```

필터 선택 때마다 GitHub API를 다시 호출하지 않는다.

```text
잘못된 구조
filter click
→ API 재요청
→ 새로운 응답
→ 렌더링

v0.8 구조
filter click
→ 이미 받은 원본 데이터 사용
→ filter()
→ 재렌더링
```

v0.8이 끝나면 최소한 다음 관계를 설명할 수 있어야 한다.

```text
원본 repository 데이터는 어디에 유지되는가
→ 현재 filter 상태는 무엇인가
→ filter()는 어떤 조건으로 데이터를 고르는가
→ filter() 결과는 원본과 어떤 관계인가
→ filtered data가 어떻게 map()과 연결되는가
→ 왜 filter 선택 때 API를 다시 호출하지 않는가
→ API empty와 Filter empty는 어떻게 다른가
→ filter를 All로 바꾸면 왜 원본 전체가 다시 보이는가
```

B1-1 원문에서는 프로젝트 필터링이 선택 과제지만, 이 프로젝트에서는 학습 목표를 위해 `v1.0` 필수 범위로 취급한다.

## 2. 요구사항

### 2.1 v0.7의 API 구조를 그대로 기반으로 작업

v0.7에서 이미 구현한 다음 구조를 유지한다.

```text
GitHub API 요청
→ loading
→ HTTP 응답
→ success / empty / error
→ Projects DOM 렌더링

error
→ Retry
→ 다시 loading
```

v0.8에서는 API 요청 흐름 자체를 다시 설계하지 않는다.

특히 다음 기능을 유지한다.

- GitHub API 요청
- `fetch`
- `async / await`
- `try / catch`
- HTTP 응답 확인
- `403` rate limit 오류 경로
- loading / success / error / empty 상태
- Retry
- repository 데이터의 동적 Project 카드 렌더링
- 기존 Projects CSS Grid

필터 구현을 위해 기존 API 코드를 불필요하게 다시 작성하거나 별도의 두 번째 API 요청 함수를 만들지 않는다.

---

### 2.2 원본 repositories 데이터 유지

GitHub API 요청에 성공하여 repository 배열을 얻은 뒤, 필터링에 사용할 수 있도록 **전체 원본 데이터를 유지**한다.

개념 구조:

```text
GitHub API response
        ↓
JSON repositories
        ↓
원본 repositories로 보관
        ↓
필터 기능의 기준 데이터
```

필터를 한 번 적용한 결과를 다음 필터의 원본으로 사용하지 않는다.

잘못된 흐름:

```text
전체 repositories
→ JavaScript filter
→ JavaScript만 남음
→ 다시 CSS filter
→ 이미 줄어든 데이터에서 CSS만 찾음
```

이렇게 되면 이전 필터 결과 때문에 원래 있던 데이터가 복구되지 않을 수 있다.

기본 원칙은 항상 다음과 같다.

```text
현재 filter 변경
        ↓
항상 전체 원본 repositories에서 다시 filter()
```

즉 원본 데이터는 필터 결과와 분리한다.

---

### 2.3 현재 filter 상태

사용자가 현재 어떤 조건을 선택했는지 JavaScript에서 알 수 있어야 한다.

최소 상태 예:

```text
All
HTML
CSS
JavaScript
```

정확한 언어 목록은 실제 GitHub repository 데이터와 UI 설계에 맞게 정할 수 있다.

상태의 의미는 다음과 같다.

```text
currentFilter = All
→ 모든 repository 표시

currentFilter = JavaScript
→ language가 JavaScript인 repository만 표시
```

복잡한 상태 객체나 상태 관리 라이브러리는 사용하지 않는다.

현재 선택값 하나를 명확하게 관리할 수 있으면 충분하다.

---

### 2.4 필터 UI

Projects 영역에 사용자가 필터 조건을 선택할 수 있는 UI를 추가한다.

B1-1 원문의 방향에 맞춰 언어별 필터 control을 사용한다.

예:

```text
[ All ] [ HTML ] [ CSS ] [ JavaScript ]
```

필터가 동작을 실행하는 control이라면 HTML 의미상 `button`을 기본 선택으로 한다.

필터 버튼은 페이지 이동을 위한 링크가 아니다.

각 버튼은 JavaScript에서 어떤 filter를 의미하는지 식별할 수 있어야 한다.

필요하면 다음과 같은 방식을 사용할 수 있다.

```text
data-* attribute
class
```

정확한 속성명과 class명은 기존 프로젝트 명명 방식에 맞춘다.

필터 UI를 위해 외부 UI 라이브러리를 추가하지 않는다.

---

### 2.5 기본 filter 상태는 All

Projects 데이터가 정상적으로 로드되면 기본 상태에서는 전체 repository가 보이도록 한다.

```text
API success
→ 원본 repositories 저장
→ currentFilter = All
→ 전체 repositories 렌더링
```

기본 필터 상태 때문에 일부 repository가 처음부터 숨겨져서는 안 된다.

Retry 후 API 요청이 다시 성공한 경우에도 기존 filter 상태를 어떻게 처리할지는 현재 구조가 단순하고 예측 가능하도록 정한다.

기본 설계는 다음을 권장한다.

```text
새 API 성공 결과
→ 원본 repositories 갱신
→ 현재 filter 적용
→ 결과 렌더링
```

단, 프로젝트가 복잡해지지 않도록 별도 영속 저장은 하지 않는다.

필터 상태를 `localStorage`에 저장하지 않는다.

---

### 2.6 저장소 `language` 기준 필터링

필터 조건은 GitHub repository 데이터의 언어 정보를 기준으로 한다.

개념 구조:

```text
repository
├── name
├── description
├── language
└── html_url
```

현재 filter가 `JavaScript`라면:

```text
repository.language === 'JavaScript'
```

와 같은 조건을 기준으로 해당 repository만 선택한다.

정확한 비교 코드는 구현 단계에서 현재 데이터와 코드 스타일에 맞춰 작성한다.

대소문자 변환, 별칭 처리, 복잡한 정규화 시스템은 필요하지 않다.

GitHub API가 제공하는 `language` 값을 그대로 활용하는 단순한 구조를 우선한다.

---

### 2.7 `filter()`를 핵심 배열 메서드로 실제 사용

v0.8에서는 `Array.prototype.filter()`를 프로젝트 필터링의 핵심 처리에 실제로 사용한다.

핵심 관계:

```text
원본 repositories
        ↓ filter()
조건을 만족하는 repository만 선택
        ↓
새로운 filtered repositories
```

이 버전에서 이해할 핵심은 다음이다.

```text
filter()
→ 원본 배열에서 조건에 맞는 요소만 골라
→ 새로운 배열을 만든다.
```

배열 고급 이론이나 함수형 프로그래밍으로 학습 범위를 확대하지 않는다.

---

### 2.8 All 조건

`All`은 특정 language를 고르는 필터가 아니다.

기본 의미:

```text
All
→ 원본 repositories 전체 사용
```

불필요하게 모든 요소가 `true`가 되도록 복잡한 filter 조건을 만들 필요는 없다.

코드 구조에 따라:

```text
All
→ 원본 배열 그대로 렌더 함수에 전달
```

하거나 동일한 의미를 읽기 쉬운 방식으로 구현할 수 있다.

핵심은 `All`을 선택했을 때 **원본 전체 데이터가 다시 화면에 나타나는 것**이다.

---

### 2.9 `filter()`와 `map()`의 역할 분리

v0.7에서 `map()`은 repository 데이터를 Project 카드 표현으로 변환하는 데 사용했다.

v0.8에서는 그 앞에 `filter()`가 추가된다.

```text
원본 repositories
        ↓ filter()
필터 조건에 맞는 repositories
        ↓ map()
Project 카드 표현
        ↓
Projects DOM
```

두 메서드의 역할을 구분한다.

```text
filter()
→ 어떤 repository를 보여줄 것인가

map()
→ 선택된 repository를 어떤 카드 표현으로 바꿀 것인가
```

필터링을 위해 기존 카드 생성 `map()` 코드를 불필요하게 다시 작성하지 않는다.

가능하면 v0.7의 기존 카드 렌더링 구조를 재사용한다.

---

### 2.10 필터 선택 이벤트

사용자가 필터 control을 선택하면 JavaScript의 `click` 이벤트로 처리한다.

기본 흐름:

```text
Filter button click
        ↓
선택한 filter 값 확인
        ↓
currentFilter 변경
        ↓
원본 repositories에서 filter()
        ↓
Projects 재렌더링
```

이벤트는 기존 프로젝트 원칙대로 `addEventListener()`를 사용한다.

HTML의 inline event handler는 사용하지 않는다.

---

### 2.11 필터 선택 상태의 시각적 표현

사용자는 현재 어떤 필터가 선택되어 있는지 화면에서 알 수 있어야 한다.

예:

```text
All             ← 선택됨
HTML
CSS
JavaScript
```

또는 버튼 스타일의 차이로 현재 active filter를 표현할 수 있다.

기본 역할 분담:

```text
JavaScript
→ 현재 filter 상태 결정
→ 필요한 active 상태 class/attribute 변경

CSS
→ 선택된 filter의 시각 표현
```

JavaScript에서 버튼 색상 등을 직접 반복 지정하지 않는다.

필터 UI의 시각 디자인을 복잡하게 만드는 것은 이번 버전의 목표가 아니다.

---

### 2.12 필터된 결과 재렌더링

filter 선택 후 기존 Projects DOM을 현재 filtered repositories에 맞게 갱신한다.

기본 흐름:

```text
현재 화면
→ 전체 project cards

사용자 JavaScript 선택
→ filtered repositories 생성
→ Projects 영역 재렌더링
→ JavaScript project cards만 표시
```

다시 `All`을 선택하면:

```text
원본 repositories 전체
→ 기존 render 흐름
→ 전체 cards 다시 표시
```

DOM에서 기존 카드를 개별적으로 숨기고 보이는 방식보다, 현재 프로젝트의 v0.7 렌더링 구조를 활용하여 **현재 화면용 데이터로 Projects 영역을 다시 렌더링하는 구조**를 우선한다.

---

### 2.13 API empty와 Filter empty 구분

v0.8에서는 두 종류의 empty를 구분해야 한다.

#### API empty

```text
GitHub API 요청 성공
        ↓
원본 repositories = 0개
        ↓
API empty
```

이 상태는 v0.7에서 이미 구현했다.

원본 데이터 자체가 없기 때문에 필터할 대상도 없다.

#### Filter empty

```text
GitHub API 요청 성공
        ↓
원본 repositories는 존재
        ↓
사용자가 특정 filter 선택
        ↓
조건에 맞는 repository = 0개
        ↓
Filter empty
```

두 상태는 사용자 화면에 빈 상태 메시지가 필요하다는 점에서는 비슷하지만 원인은 다르다.

```text
API empty
→ 원본 데이터 없음

Filter empty
→ 원본 데이터는 있으나 현재 조건과 일치하는 데이터 없음
```

코드와 학습 과정에서 이 차이를 설명할 수 있어야 한다.

---

### 2.14 Filter empty UI

현재 filter에 맞는 repository가 하나도 없으면 빈 상태를 표시한다.

예:

```text
No projects match this filter.
```

정확한 문구는 실제 사이트 언어와 디자인에 맞게 정한다.

Filter empty에서 다음과 같은 오해를 주면 안 된다.

```text
Projects를 불러오지 못했습니다.
```

이는 error 상태의 의미이기 때문이다.

또한 API empty와 동일한 문구를 사용할 수는 있지만, 구현과 이해 수준에서는 원인이 다르다는 점을 구분한다.

---

### 2.15 Error / Loading 상태와 필터 UI 관계

필터는 **성공적으로 받은 원본 repository 데이터에 적용하는 기능**이다.

따라서 API가 loading 또는 error 상태일 때 필터가 실제 데이터를 필터링하는 구조를 만들지 않는다.

기본 개념:

```text
loading
→ 아직 원본 데이터 준비되지 않음

error
→ 사용할 정상 원본 데이터 없음

success
→ 원본 데이터 존재 가능
→ filter 사용 가능

API empty
→ 원본 데이터 0개
```

필터 UI를 언제 보이거나 활성화할지는 기존 HTML 구조와 사용성을 보고 결정할 수 있다.

단, 필터 버튼을 눌렀다고 API error를 success처럼 처리해서는 안 된다.

---

### 2.16 필터 선택 시 API 재호출 금지

이 버전의 핵심 검증 조건이다.

다음 흐름이 존재해서는 안 된다.

```text
filter click
→ fetch()
→ GitHub API 요청
```

필터 선택은 이미 받은 데이터를 가공하는 동작이다.

Network 탭에서 필터 버튼을 여러 번 눌러도 새로운 GitHub API 요청이 발생하지 않는지 직접 확인한다.

Retry는 예외다.

```text
Error 상태의 Retry click
→ API 요청 다시 실행
```

이는 v0.7의 기존 기능이며 정상 동작이다.

---

### 2.17 필터 결과는 저장하지 않음

`filtered repositories`는 화면을 만들기 위한 **파생 데이터**다.

이 결과를 `localStorage` 등에 저장하지 않는다.

```text
원본 repositories
+
currentFilter
        ↓
필요할 때 filtered repositories 계산
```

필터 결과를 별도의 영속 데이터처럼 관리하지 않는다.

이번 버전에서는 필터 상태 자체도 페이지 새로고침 후 유지할 필요가 없다.

---

### 2.18 새로운 API 구조를 추가하지 않음

v0.8에서 다음은 구현하지 않는다.

- 새로운 GitHub API endpoint
- language별 API 요청
- GitHub Search API
- pagination
- repository 추가 상세 요청
- 인증
- 서버 측 필터링

필터링은 브라우저에 이미 존재하는 repository 배열을 대상으로 한다.

---

### 2.19 기존 기능과의 공존

프로젝트 필터링을 추가한 뒤에도 이전 버전 기능이 계속 정상 동작해야 한다.

확인 대상:

```text
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Theme Toggle
Light / Dark theme
localStorage theme 복원
Contact Form validation
GitHub API loading / success / error / empty
403 rate limit 오류 경로
Retry
Projects responsive Grid
```

필터 UI와 Filter empty 상태도 light / dark theme에서 읽을 수 있어야 한다.

## 3. 목표 설계

v0.8 완료 시 전체 학습 구조는 다음과 같다.

```text
HTML 구조                    ← v0.1
        ↓
CSS 기본 표현                ← v0.2
        ↓
반응형 Grid                  ← v0.3
        ↓
DOM / Event                  ← v0.4
        ↓
Theme State / localStorage   ← v0.5
        ↓
Form Validation State        ← v0.6
        ↓
GitHub API / Async State     ← v0.7
        ↓
원본 repositories
        ↓
Filter UI
        ↓
currentFilter
        ↓
filter()
        ↓
filtered repositories
        ↓
map()
        ↓
Project cards
        ↓
Projects DOM 재렌더링
```

핵심 데이터 구조는 다음과 같다.

```text
GitHub API
        ↓
원본 repositories
        │
        │  유지
        │
        ├───────────────┐
        │               │
        ↓               ↓
currentFilter        All 선택
        ↓               ↓
filter()          원본 전체 사용
        ↓               │
filtered repos          │
        └───────┬───────┘
                ↓
              map()
                ↓
         Project card HTML
                ↓
          Projects DOM
```

사용자 이벤트 관점:

```text
사용자 filter click
        ↓
click handler
        ↓
선택값 읽기
        ↓
currentFilter 변경
        ↓
원본 repositories 기준으로 데이터 선택
        ↓
현재 화면용 repositories 결정
        ↓
기존 Project render 함수 재사용
        ↓
Projects 화면 갱신
```

빈 상태는 다음처럼 구분한다.

```text
API 요청 성공
        ↓
원본 repositories 0개
        ↓
API empty

원본 repositories 1개 이상
        ↓
특정 filter 적용
        ↓
filtered repositories 0개
        ↓
Filter empty
```

v0.7과 v0.8의 차이는 다음과 같다.

```text
v0.7
외부 데이터 요청
→ 비동기 상태 결정
→ 원본 repository 렌더링

v0.8
이미 받은 원본 데이터
→ 사용자 filter 상태
→ 파생 데이터 계산
→ 같은 Projects 영역 재렌더링
```

## 4. 새롭게 배우는 개념

### 4.1 원본 데이터와 파생 데이터

이번 버전의 핵심 개념이다.

#### 원본 데이터

```text
GitHub API에서 받은 전체 repositories
```

필터 조건이 바뀌어도 원본은 유지한다.

#### 파생 데이터

```text
원본 repositories
+
현재 filter 조건
        ↓
filtered repositories
```

화면에 필요한 순간 계산된 결과다.

핵심 질문:

```text
현재 화면에 JavaScript 프로젝트만 보인다.
그렇다면 HTML 프로젝트 데이터는 사라진 것인가?
```

답은 아니다.

원본 데이터에는 계속 존재하고, 현재 filter 결과에 포함되지 않았을 뿐이다.

---

### 4.2 상태가 데이터 가공을 결정하는 구조

v0.5와 v0.6에서는 상태가 주로 UI 표현을 직접 결정했다.

v0.8에서는 상태가 먼저 **어떤 데이터를 화면에 사용할지** 결정한다.

```text
currentFilter
        ↓
데이터 선택 기준 결정
        ↓
filtered repositories
        ↓
렌더링
```

즉 상태와 렌더링 사이에 데이터 가공 단계가 추가된다.

---

### 4.3 `filter()`

`filter()`는 배열의 각 요소에 조건을 적용하여 조건을 만족하는 요소만 포함한 **새 배열**을 만든다.

개념 구조:

```text
[repo A, repo B, repo C]
        ↓ filter(condition)
[repo A, repo C]
```

원본 배열의 모든 요소를 카드로 바꾸는 `map()`과 역할이 다르다.

이 버전에서는 `filter()`의 내부 구현, callback 고급 패턴, 함수형 프로그래밍 이론까지 확대하지 않는다.

---

### 4.4 Filter Callback

`filter()`는 각 repository가 현재 조건을 만족하는지 판단하는 함수를 사용한다.

개념:

```text
repository 하나
        ↓
현재 filter와 일치하는가?
        ↓
true
→ 결과 배열에 포함

false
→ 결과 배열에서 제외
```

이번 프로젝트에서는 `repository.language`가 핵심 비교 대상이다.

---

### 4.5 `filter()`는 원본을 직접 지우는 작업이 아님

이번 버전에서 매우 중요하다.

```text
원본 repositories
        ↓ filter()
새 filtered repositories
```

필터를 적용했다고 원본 repository가 삭제되는 것이 아니다.

따라서 다른 filter를 선택할 때 다시 원본 전체를 기준으로 계산할 수 있다.

이 특징이 `All`로 되돌리는 동작과 연결된다.

---

### 4.6 `filter()`와 `map()` 비교

현재 프로젝트의 실제 용도로 구분한다.

```text
filter()
→ 데이터의 개수를 줄일 수 있음
→ 어떤 repository를 사용할지 선택

map()
→ 각 repository를 다른 표현으로 변환
→ repository → Project card
```

전체 흐름:

```text
repositories
        ↓ filter
필요한 repositories
        ↓ map
card HTML
```

배열 메서드 전체 목록을 학습하지 않는다.

---

### 4.7 상태와 파생 데이터

`filtered repositories`를 별도의 독립된 원본처럼 취급하지 않는다.

다음 관계로 이해한다.

```text
원본 data + filter state
        ↓
파생 data
```

filter state가 바뀌면 같은 원본에서 다른 결과가 만들어진다.

예:

```text
원본 8개

All
→ 8개

JavaScript
→ 3개

CSS
→ 1개

All
→ 다시 8개
```

---

### 4.8 UI 상태와 데이터 상태의 연결

선택된 버튼의 active 표현과 실제 `currentFilter` 값이 서로 어긋나지 않아야 한다.

```text
화면에서는 JavaScript 버튼 활성
하지만 currentFilter = CSS
```

같은 모순이 생기면 안 된다.

기본 관계:

```text
사용자 click
→ currentFilter 변경
→ filter UI active 상태 변경
→ 같은 filter 값으로 데이터 가공
```

---

### 4.9 이벤트 → 상태 → 데이터 가공 → 렌더링

v0.8에서 새롭게 확장되는 전체 흐름이다.

```text
Event
→ State
→ Data Transform
→ Render
```

현재 기능에 대입하면:

```text
filter button click
→ currentFilter 변경
→ repositories.filter(...)
→ filtered repositories
→ Project cards 재렌더링
```

B1-1에서 이후 React의 상태와 렌더링 개념을 이해하기 위한 중요한 연결점이다.

단, React 자체는 이번 버전에서 배우지 않는다.

---

### 4.10 데이터 재사용

같은 서버 데이터를 사용자 조건에 따라 여러 방식으로 보여줄 수 있음을 이해한다.

```text
서버 요청 1회
        ↓
원본 데이터 1개
        ↓
All / HTML / CSS / JavaScript
        ↓
여러 화면 결과
```

필터를 바꿀 때마다 서버가 새 데이터를 보내야 하는 것은 아니다.

---

### 4.11 API 요청과 클라이언트 필터링의 차이

두 동작을 구분한다.

```text
API 요청
→ 브라우저 밖의 GitHub 서버에서 데이터 가져오기

클라이언트 필터링
→ 이미 브라우저 안에 있는 데이터에서 조건에 맞는 값 선택
```

v0.8에서는 두 번째 동작을 구현한다.

---

### 4.12 API Empty와 Filter Empty

두 상태는 배열 길이가 `0`이라는 결과만 보면 비슷하지만 **원인이 다르다.**

```text
API empty
원본.length === 0

Filter empty
원본.length > 0
filtered.length === 0
```

이 차이를 코드와 사용자 흐름에서 설명할 수 있어야 한다.

---

### 4.13 재렌더링

필터가 바뀔 때 기존 페이지 전체를 새로고침하지 않는다.

현재 Projects 영역의 DOM만 새 데이터에 맞게 갱신한다.

```text
같은 HTML 페이지
        ↓
상태 변경
        ↓
Projects DOM 내용 변경
```

v0.7에서 외부 데이터 응답에 따라 Projects DOM을 바꿨던 구조를 사용자 filter 이벤트에 재사용한다.

---

### 4.14 Network 탭을 이용한 동작 검증

필터의 핵심 설계가 실제로 지켜지는지 DevTools Network에서 확인한다.

```text
페이지 로드
→ GitHub API 요청 발생

filter click
→ 새 GitHub API 요청 없음

다른 filter click
→ 새 GitHub API 요청 없음
```

Error 상태에서 Retry를 누른 경우에는 새 요청이 발생하는 것이 정상이다.

## 5. 완료 / 검증 기준

### 5.1 필터 UI 존재

Projects 영역에 언어 기준 filter control이 존재한다.

최소한 `All`과 실제로 사용할 하나 이상의 language filter가 있다.

필터 control은 사용자가 동작을 실행하는 의미에 맞는 구조를 가진다.

---

### 5.2 기본 상태

API 요청 성공 후 기본적으로 전체 repository가 표시된다.

기본 filter 상태가 `All`임을 확인할 수 있다.

선택된 filter UI도 현재 상태와 일치한다.

---

### 5.3 원본 데이터 유지

GitHub API에서 받은 전체 repositories가 필터 기준 데이터로 유지된다.

한 번 필터링한 결과를 다음 필터의 원본으로 사용하지 않는다.

다음 흐름이 정상 동작한다.

```text
All
→ JavaScript
→ CSS
→ All
```

마지막 `All`에서 처음의 전체 repository가 다시 표시되어야 한다.

---

### 5.4 `filter()` 실제 사용

language 기준 repository 선택에 `filter()`가 실제 사용된다.

단순히 DOM 요소를 CSS로 숨기는 것만으로 필터 기능을 구현하지 않는다.

현재 코드에서 다음을 설명할 수 있다.

```text
filter()의 입력 배열은 무엇인가
조건은 무엇인가
결과 배열은 무엇인가
```

---

### 5.5 `filter()` → `map()` 흐름

현재 코드에서 다음 역할이 분리되어 있다.

```text
filter()
→ 표시할 repositories 선택

map()
→ 선택된 repositories를 카드 표현으로 변환
```

기존 v0.7의 카드 렌더링 구조가 가능한 범위에서 재사용된다.

---

### 5.6 필터 선택

각 filter를 선택했을 때 현재 filter 상태가 변경된다.

선택한 language에 맞는 Project 카드만 표시된다.

다른 filter를 선택하면 이전 결과가 남지 않고 새 결과로 갱신된다.

---

### 5.7 All 복원

특정 language filter를 선택한 뒤 `All`을 선택하면 원본 전체 repository가 다시 표시된다.

API를 다시 호출하지 않아도 동작해야 한다.

---

### 5.8 Filter empty

원본 repositories는 존재하지만 현재 filter와 일치하는 repository가 없을 때 Filter empty UI가 표시된다.

이 상태에서 error 메시지를 표시하지 않는다.

다른 filter 또는 `All`을 선택하면 정상 Project 카드가 다시 표시된다.

---

### 5.9 API empty와 구분

다음 두 테스트의 원인을 설명할 수 있다.

```text
원본 repository 0개
→ API empty

원본 repository 있음
현재 filter 결과 0개
→ Filter empty
```

두 상태를 동일한 개념으로 설명하지 않는다.

---

### 5.10 필터 선택 시 API 요청 없음

DevTools Network에서 다음을 확인한다.

```text
filter click
→ GitHub API 요청 없음

filter 변경 반복
→ GitHub API 요청 없음
```

필터 기능이 `fetch()`와 직접 연결되어 있지 않다.

---

### 5.11 Retry 유지

기존 API error 상태에서 Retry가 계속 정상 동작한다.

```text
error
→ Retry
→ loading
→ success / API empty / error
```

Retry는 실제 API 요청을 다시 수행한다.

필터 기능 추가가 Retry 흐름을 깨뜨리지 않는다.

---

### 5.12 Loading / Error 상태 유지

API 요청 중에는 기존 loading UI가 정상 동작한다.

API 오류에서는 기존 error UI와 Retry가 정상 표시된다.

필터 UI 때문에 loading 또는 error 상태가 Project 카드 success 상태처럼 보이지 않는다.

---

### 5.13 기존 Projects Grid 유지

필터된 Project 카드도 기존 CSS Grid 안에서 정상 배치된다.

다음 기존 구조를 JavaScript 레이아웃으로 교체하지 않는다.

```text
CSS Grid
repeat()
auto-fit
minmax()
```

모바일 / 태블릿 / 데스크톱에서 필터 결과의 카드 수가 달라져도 레이아웃이 깨지지 않는다.

---

### 5.14 Light / Dark Theme

필터 버튼의 기본 상태와 선택 상태, Filter empty UI가 light / dark theme 모두에서 읽을 수 있다.

Theme Toggle과 filter 기능이 서로 영향을 주지 않는다.

---

### 5.15 기존 기능 회귀 확인

다음 기능이 정상 동작한다.

```text
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Theme Toggle
localStorage theme 복원
Contact Form validation
GitHub API loading / success / error / empty
403 rate limit 오류 경로
Retry
```

---

### 5.16 Console 확인

다음 동작을 반복해도 현재 구현 때문에 발생하는 JavaScript 오류가 없어야 한다.

```text
필터 반복 선택
All 복원
Filter empty 발생
Retry 후 success
Theme Toggle
반응형 화면 변경
```

---

### 5.17 Network 확인

DevTools Network에서 최소 다음을 직접 확인한다.

```text
초기 API 요청
→ 존재

Filter 선택
→ 추가 API 요청 없음

Retry
→ 새 API 요청 존재
```

---

### 5.18 DOM 확인

DevTools Elements에서 필터 전후 Projects 영역을 확인한다.

```text
All
→ 전체 Project cards

특정 language
→ 해당 Project cards만 존재

Filter empty
→ 카드 대신 빈 상태 UI
```

선택된 filter control의 active 상태도 확인한다.
