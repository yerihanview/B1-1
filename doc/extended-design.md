# B1-1 Extended Design

## 1. 문서 목적

이 문서는 B1-1 프로젝트의 **v1.0 이후 확장 설계**를 정의한다.

`final-design.md`가 B1-1 기본 완료 목표인 `v1.0`의 최종 상태를 정의한다면, 이 문서는 `v1.0`을 기반으로 추가할 확장 기능을 정의한다.

현재 계획된 확장 범위는 다음과 같다.

```text
v1.0
    B1-1 필수 요구사항
    + 프로젝트 필터링

v1.1
    Hero 타이핑 효과

v1.2
    실제 Contact Form 전송

v1.3
    시스템 다크 모드 감지
    + 실행 중 시스템 테마 변경 실시간 반영
```

`v1.3`은 현재 계획된 B1-1 확장 기능까지 모두 완료한 기준점이다.

이 문서는 각 기능의 **목표 상태와 동작 구조**를 정의한다.

구체적인 구현 순서는 `roadmap.md`에서 관리하고, 각 버전의 상세 구현 범위와 학습 내용은 `vX.X.md`에서 관리한다.

---

# 2. 설계 기준

확장 기능은 `v1.0`의 기존 구조와 동작을 유지하면서 추가한다.

따라서 다음 원칙을 따른다.

- `v1.0`에서 완성된 기능을 불필요하게 다시 작성하지 않는다.
- 확장 기능 때문에 기존 구조를 과도하게 변경하지 않는다.
- 새로운 라이브러리나 기술은 해당 기능에 실제로 필요한 경우에만 사용한다.
- 현재 버전보다 뒤의 기능을 선행 구현하지 않는다.
- 각 확장 기능 역시 사용자 이벤트, 상태 변화, 화면 변화의 관계를 이해할 수 있어야 한다.

확장 기능의 목적은 웹사이트를 복잡하게 만드는 것이 아니라, B1-1에서 제시한 선택 기능을 기존 학습 내용 위에 추가로 경험하는 것이다.

# 3. v1.1 — Hero 타이핑 효과

## 3.1 목표

Hero 영역의 소개 문구 일부가 한 글자씩 나타나는 타이핑 효과를 추가한다.

이 기능은 기존 Hero 구조를 유지하면서 JavaScript에 의한 시간 기반 DOM 변경을 경험하는 것을 목표로 한다.

---

## 3.2 사용자에게 보이는 동작

페이지가 로드되면 Hero의 지정된 텍스트가 한 글자씩 순서대로 나타난다.

예:

```text
Frontend Developer
```

가 다음과 같이 변화한다.

```text
F
Fr
Fro
Fron
Front
...
Frontend Developer
```

타이핑 효과의 대상 문구와 속도는 구현 단계에서 결정한다.

---

## 3.3 상태 및 동작 구조

기본 흐름은 다음과 같다.

```text
타이핑 시작

    ↓

현재 출력할 글자 위치 확인

    ↓

문자열 일부 추출

    ↓

DOM textContent 변경

    ↓

일정 시간 후 다음 글자 처리
```

필요한 상태의 예:

```text
전체 문자열
현재 글자 위치
현재 화면에 표시할 문자열
```

---

## 3.4 주요 학습 개념

이 버전에서 새롭게 다룰 핵심 개념은 다음과 같다.

- 문자열과 인덱스
- 반복적인 시간 기반 실행
- `setTimeout` 또는 필요한 타이머 개념
- `textContent`를 이용한 DOM 변경
- 함수의 반복 호출
- 종료 조건

복잡한 애니메이션 라이브러리는 사용하지 않는다.

---

## 3.5 기존 기능과의 관계

기존 Hero의 다음 기능은 그대로 유지한다.

- 인사말
- 자기소개
- CTA
- 반응형 레이아웃

타이핑 효과는 Hero의 내용 전달을 방해하지 않는 보조적인 시각 효과로 추가한다.

JavaScript가 정상 실행되지 않더라도 사용자가 Hero의 핵심 내용을 이해할 수 있는 구조를 유지한다.

---

## 3.6 v1.1 완료 상태

다음을 만족하면 v1.1 설계 목표를 충족한다.

- Hero에 타이핑 효과가 동작한다.
- 텍스트가 정해진 순서대로 한 글자씩 표시된다.
- 타이핑이 종료 조건에서 정상적으로 멈춘다.
- 기존 Hero 레이아웃과 CTA가 정상 동작한다.
- 모바일과 데스크톱에서 레이아웃이 깨지지 않는다.
- 타이핑 효과가 어떤 상태와 DOM 변경으로 구현되는지 설명할 수 있다.

# 4. v1.2 — 실제 Contact Form 전송

## 4.1 목표

`v1.0`의 Contact Form은 클라이언트 측 유효성 검사 후 성공 메시지만 표시한다.

v1.2에서는 이를 확장하여 사용자가 입력한 내용을 **실제로 외부 서비스로 전송할 수 있도록 한다.**

B1-1에서 제시한 Formspree 또는 EmailJS와 같은 방식을 사용할 수 있다.

구체적인 서비스 선택은 해당 버전 구현 전에 결정한다.

---

## 4.2 사용자에게 보이는 동작

기본 사용자 흐름:

```text
이름 / 이메일 / 메시지 입력

        ↓

Submit

        ↓

클라이언트 유효성 검사

        ↓

유효하지 않음
→ 기존 오류 메시지 표시

유효함
→ 실제 전송 시작

        ↓

전송 성공 또는 실패

        ↓

결과 UI 표시
```

---

## 4.3 Form 상태

v1.2에서는 기존 validation 상태에 전송 상태가 추가된다.

최소한 다음 상태를 구분한다.

### Idle

사용자가 아직 전송을 시도하지 않은 기본 상태.

### Validation Error

입력값이 유효하지 않은 상태.

기존 v1.0 유효성 검사 동작을 그대로 사용한다.

### Submitting

외부 서비스로 데이터를 전송하고 있는 상태.

사용자가 전송 중임을 알 수 있어야 한다.

필요하면 중복 제출도 방지한다.

### Success

실제 전송이 정상 완료된 상태.

성공 메시지를 표시한다.

### Error

전송 과정에서 문제가 발생한 상태.

사용자에게 전송 실패 사실을 표시한다.

---

## 4.4 상태 및 렌더링 흐름

```text
submit 이벤트

    ↓

validation

    ↓

유효하면 submitting 상태

    ↓

외부 서비스로 전송

    ↓

success 또는 error

    ↓

Contact Form UI 갱신
```

이 기능을 통해 기존 v1.0의 상태→렌더링 구조를 비동기 전송까지 확장한다.

---

## 4.5 주요 학습 개념

사용하는 서비스에 따라 세부 구현은 달라질 수 있지만 핵심 학습 범위는 다음과 같다.

- 외부 서비스와 웹페이지의 연결
- 폼 데이터 전송
- 비동기 처리
- 전송 중 상태
- 성공 상태
- 실패 상태
- 사용자 피드백
- 중복 제출 방지의 필요성

v1.0에서 학습한 `async/await`, `try/catch` 등의 개념과 연결하여 이해한다.

---

## 4.6 보안 및 설정 원칙

외부 서비스를 사용하면서 브라우저 코드에 노출해서는 안 되는 비밀 정보를 임의로 포함하지 않는다.

사용하는 서비스가 공개용 식별자 또는 설정값을 요구한다면 해당 서비스의 프런트엔드 사용 방식을 따른다.

GitHub repository에 비밀 키나 민감한 인증 정보를 commit하지 않는다.

---

## 4.7 기존 기능과의 관계

v1.0에서 구현한 다음 기능을 제거하거나 대체하지 않는다.

- 필수값 검사
- 이메일 형식 검사
- 필드별 오류 메시지
- submit 이벤트
- `preventDefault()`

기존 유효성 검사를 통과한 경우에만 실제 전송 단계로 넘어간다.

---

## 4.8 v1.2 완료 상태

다음을 만족하면 v1.2 설계 목표를 충족한다.

- 기존 폼 유효성 검사가 정상 동작한다.
- 유효한 데이터만 실제 전송을 시도한다.
- 전송 중 상태를 사용자에게 표시한다.
- 성공한 경우 성공 상태를 표시한다.
- 실패한 경우 실패 상태를 표시한다.
- 반복 클릭으로 불필요한 중복 전송이 발생하지 않도록 처리한다.
- 실제 배포된 GitHub Pages에서도 전송 기능이 정상 동작한다.
- validation과 실제 전송 과정의 차이를 설명할 수 있다.
- 비동기 전송의 상태→렌더링 흐름을 설명할 수 있다.

# 5. v1.3 — 시스템 다크 모드 감지

## 5.1 목표

v1.0에서는 사용자가 직접 선택한 테마를 `localStorage`에 저장하고 복원한다.

v1.3에서는 이를 확장하여 다음 두 가지 기능을 추가한다.

1. 사용자가 아직 테마를 직접 선택하지 않은 경우 시스템 테마를 초기 테마로 사용한다.
2. 사용자가 직접 선택한 테마가 없는 상태에서는 페이지 실행 중 OS의 테마 설정이 변경되면 이를 실시간으로 화면에 반영한다.

B1-1에서 제시한 `prefers-color-scheme` 기반 시스템 설정 감지를 구현하고, 이 프로젝트에서는 **시스템 설정 변경의 실시간 반영까지 확장 범위에 포함한다.**

---

## 5.2 테마 결정 우선순위

테마 결정의 핵심 원칙은 **사용자의 명시적인 선택이 시스템 설정보다 우선한다**는 것이다.

초기 로드 시 다음 순서로 결정한다.

```text
1. 사용자가 이전에 직접 선택한 테마가 있는가?

        YES
        ↓

localStorage의 사용자 선택 사용

        NO
        ↓

2. 현재 시스템 테마 확인

        dark
        ↓

dark theme

        light
        ↓

light theme
```

따라서 시스템 테마는 저장된 사용자 선택이 없을 때 기본값 역할을 한다.

---

# 6. 시스템 테마 감지

시스템 설정은 `prefers-color-scheme`을 기준으로 감지한다.

CSS에서는 다음 Media Feature를 사용한다.

```css
prefers-color-scheme
```

JavaScript에서는 시스템 테마 상태와 변경 여부를 확인하기 위해 `matchMedia`를 사용한다.

기본 개념 구조는 다음과 같다.

```text
prefers-color-scheme 확인

        ↓

현재 OS 테마 상태 확인

        ↓

dark 또는 light 결정
```

실제 API 문법과 이벤트 연결 방법은 `v1.3.md`의 학습 단계에서 다룬다.

---

# 7. 사용자 선택과 localStorage

v1.0에서 구현한 사용자 테마 선택과 `localStorage` 저장 기능은 그대로 유지한다.

예:

```text
시스템: light

사용자 선택: dark

localStorage: dark

결과: dark
```

사용자가 직접 테마를 선택한 이후에는 시스템 설정이 변경되더라도 사용자 선택을 유지한다.

즉 다음 두 상태를 구분해야 한다.

```text
사용자 선택 있음
→ 사용자 선택 우선

사용자 선택 없음
→ 시스템 설정을 따름
```

---

# 8. 초기 상태 결정 흐름

페이지가 처음 로드될 때의 흐름은 다음과 같다.

```text
페이지 로드

    ↓

localStorage 확인

    ↓

저장값 있음
→ 저장된 theme 사용

저장값 없음
→ 현재 prefers-color-scheme 확인

    ↓

초기 theme 결정

    ↓

DOM theme 속성 변경

    ↓

CSS 변수에 의해 화면 변경
```

---

# 9. 사용자 직접 변경 흐름

사용자가 Theme Toggle을 누르면 시스템 설정과 관계없이 사용자의 선택을 저장한다.

```text
Theme Toggle click

    ↓

theme 상태 변경

    ↓

DOM theme 속성 변경

    ↓

localStorage에 사용자 선택 저장

    ↓

화면 변경
```

이후 OS 테마가 바뀌더라도 저장된 사용자 선택이 우선한다.

---

# 10. OS 테마 변경 실시간 반영

사용자가 직접 선택한 테마가 없는 상태에서는 실행 중인 페이지가 OS의 테마 변경을 감지한다.

예:

```text
사용자 선택 없음
현재 OS: light
현재 화면: light

        ↓

사용자가 OS 설정을 dark로 변경

        ↓

prefers-color-scheme 변경 감지

        ↓

현재 시스템 theme 상태 변경

        ↓

DOM theme 속성 변경

        ↓

화면이 즉시 dark로 변경
```

반대 방향도 동일하게 동작한다.

```text
OS dark → light
→ 변경 감지
→ DOM 갱신
→ light theme 표시
```

JavaScript에서는 시스템 테마를 나타내는 `MediaQueryList`의 변경 이벤트를 감지한다.

구체적인 이벤트 API 문법은 `v1.3.md`에서 학습한다.

---

# 11. 실시간 반영과 사용자 선택의 충돌 처리

OS 테마 변경이 항상 화면에 적용되는 것은 아니다.

다음 우선순위를 반드시 지킨다.

```text
OS 테마 변경 발생

        ↓

사용자가 직접 저장한 theme가 있는가?

        YES
        ↓

OS 변경 무시
사용자 선택 유지

        NO
        ↓

새로운 시스템 theme 적용

        ↓

DOM 업데이트
```

예를 들어:

```text
OS: light
사용자 선택: dark
화면: dark

OS가 dark 또는 light로 변경됨

결과:
사용자 선택 dark 유지
```

반대로 사용자 선택이 없다면:

```text
OS: light
사용자 선택: 없음
화면: light

OS → dark

결과:
화면 → dark
```

이 우선순위는 초기 로드와 실행 중 변경 모두 동일하게 적용한다.

---

# 12. 상태 및 렌더링 구조

v1.3의 테마 상태는 단순한 light/dark 값만으로 보지 않는다.

다음 두 정보를 구분해서 이해한다.

```text
theme
    현재 화면에 적용할 light / dark 값

theme source
    사용자 선택인지
    시스템 설정인지
```

초기 로드:

```text
페이지 로드
→ 사용자 저장값 확인
→ 없으면 시스템 설정 확인
→ theme 결정
→ DOM 변경
```

사용자 변경:

```text
Theme Toggle click
→ 사용자 theme 결정
→ localStorage 저장
→ DOM 변경
```

시스템 변경:

```text
OS theme change
→ 사용자 저장값 존재 여부 확인

저장값 없음
→ 시스템 theme로 상태 변경
→ DOM 변경

저장값 있음
→ 현재 사용자 theme 유지
```

# 13. 주요 학습 개념

v1.3에서 새롭게 다룰 핵심 개념은 다음과 같다.

- 시스템 환경 설정과 웹페이지의 관계
- `prefers-color-scheme`
- `matchMedia`
- 시스템 설정 변경 이벤트
- 외부 환경 변화에 따른 상태 변경
- 기본값과 사용자 설정값의 우선순위
- `localStorage`와 시스템 설정의 결합
- 초기 상태 결정
- 동일한 상태에 여러 입력원이 있을 때의 우선순위

핵심은 API 자체를 암기하는 것이 아니라 다음 구조를 이해하는 것이다.

```text
사용자 설정
        ↘
          theme 결정
        ↗
시스템 설정
```

그리고 두 입력이 충돌할 때 어떤 값이 우선하는지 설명할 수 있어야 한다.

# 14. v1.3 완료 상태

다음을 모두 만족하면 v1.3 설계 목표를 충족한다.

- 저장된 사용자 테마가 없으면 시스템 테마를 기준으로 초기 화면이 결정된다.
- 저장된 사용자 테마가 있으면 해당 값이 시스템 설정보다 우선한다.
- 사용자가 Theme Toggle로 테마를 직접 변경할 수 있다.
- 사용자가 직접 변경한 테마는 `localStorage`에 저장된다.
- 새로고침 후에도 사용자 선택이 유지된다.
- 사용자 선택이 없는 상태에서 OS 테마를 변경하면 실행 중인 페이지가 즉시 변경된 테마를 반영한다.
- 사용자 선택이 있는 상태에서는 OS 테마가 변경되어도 사용자 선택을 유지한다.
- light / dark 상태 모두 기존 UI가 정상 표시된다.
- 시스템 설정, 사용자 선택, `localStorage`의 우선순위를 설명할 수 있다.
- OS 설정 변경 이벤트가 상태와 DOM 변경으로 어떻게 연결되는지 설명할 수 있다.

# 16. 확장 기능과 학습 목표의 관계

각 버전은 서로 다른 종류의 웹 동작을 경험하도록 설계한다.

```text
v1.1
시간에 따른 DOM 변경

v1.2
비동기 외부 서비스 전송
+ 비동기 상태 렌더링

v1.3
외부 환경을 이용한 초기 상태 결정
+ 외부 환경 변화 이벤트에 따른 상태 변경
```

이 기능들은 각각 새로운 기술을 많이 추가하는 것이 목적이 아니다.

`v1.0`에서 익힌 다음 기본 구조를 다른 상황에 적용하는 것이 목적이다.

```text
입력 / 사용자 이벤트 / 외부 환경 변화

        ↓

JavaScript 상태 결정

        ↓

DOM 또는 UI 변경

        ↓

사용자가 결과 확인
```

---

# 17. 확장 설계에서 다루지 않는 범위

현재 `extended-design.md`에서는 다음과 같은 추가 확장은 다루지 않는다.

- React / Vue 등의 프레임워크 전환
- 백엔드 서버 직접 구축
- 데이터베이스
- 사용자 로그인
- 관리자 기능
- CMS
- 복잡한 애니메이션 라이브러리
- 별도의 빌드 도구 도입
- 테스트 프레임워크 도입
- TypeScript 전환
- 과도한 성능 최적화

이러한 기술이 유용할 수 있더라도 B1-1과 현재 확장 학습 목표에는 필요하지 않다.

필요한 기술은 이후 미션에서 별도로 학습한다.

# 18. 문서 관계

프로젝트 설계 문서의 관계는 다음과 같다.

```text
WORKFLOW.md
    └─ 프로젝트 전체를 어떤 방식으로 개발하고 학습할 것인가

final-design.md
    └─ v1.0에서 무엇을 완성할 것인가

extended-design.md
    └─ v1.0 이후 v1.3까지 무엇을 추가할 것인가

roadmap.md
    └─ v0.x부터 v1.3까지 어떤 순서로 개발할 것인가

vX.X.md
    └─ 해당 버전에서 정확히 무엇을 만들고 배울 것인가
```

`extended-design.md`는 `final-design.md`를 대체하지 않는다.

`v1.0`까지는 `final-design.md`를 목표 설계로 사용하고, `v1.1`부터는 `final-design.md`의 완성 상태를 유지하면서 이 문서에 정의된 확장 설계를 추가한다.
