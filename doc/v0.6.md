# v0.6 — Contact Form 유효성 검사

## 1. 버전 목표

v0.5에서 익힌 **상태가 화면을 결정하는 구조**를 Contact Form에 적용하여, 사용자의 입력값을 검사하고 검증 결과에 따라 오류 또는 성공 UI가 달라지는 흐름을 구현한다.

이 버전의 핵심 흐름은 다음과 같다.

```text
사용자 입력 / submit
        ↓
입력값 읽기
        ↓
validation 조건 확인
        ↓
필드별 validation 상태 결정
        ↓
오류 메시지 또는 성공 메시지 렌더링
```

v0.6가 끝나면 최소한 다음 관계를 설명할 수 있어야 한다.

```text
어떤 form event가 발생했는가
→ 어떤 입력값을 읽는가
→ 어떤 조건으로 유효 / 무효를 판단하는가
→ 어떤 validation 상태가 만들어지는가
→ 어떤 DOM이 변경되는가
→ 사용자에게 어떤 결과가 보이는가
```

이번 버전에서는 **클라이언트 측 유효성 검사와 사용자 피드백만 구현한다.**

실제 이메일 전송이나 외부 Form 서비스 연결은 하지 않는다.

---

## 2. 요구사항

### 2.1 기존 Contact Form을 기반으로 작업

v0.1에서 만든 Contact Form과 v0.2~v0.5에서 적용한 기존 구조, 스타일, 반응형 레이아웃, JavaScript 기능을 유지한다.

기본 입력 필드는 다음과 같다.

```text
Name
Email
Message
Submit button
```

기존 `label`과 각 입력 요소의 `for-id` 연결도 유지한다.

유효성 검사를 위해 필요한 경우 다음 요소를 추가할 수 있다.

```text
필드별 오류 메시지 영역
전체 성공 메시지 영역
validation 상태를 표현하기 위한 class
JavaScript에서 선택하기 위한 class 또는 id
```

단, validation을 위해 기존 HTML 의미 구조를 불필요하게 다시 작성하지 않는다.

---

### 2.2 Form `submit` 이벤트

사용자가 제출 버튼을 누르면 Form의 `submit` 이벤트를 처리한다.

기본 흐름:

```text
Submit
        ↓
form submit event
        ↓
Event Handler 실행
```

제출 버튼의 단순 `click`만을 기준으로 검증하지 않는다.

Form 제출이라는 의미에 맞는 `submit` 이벤트를 사용한다.

이벤트는 기존 JavaScript 원칙대로 `addEventListener()`로 연결한다.

HTML의 inline event handler는 사용하지 않는다.

---

### 2.3 `event.preventDefault()`

v1.0에서는 Contact Form 데이터를 실제 서버로 전송하지 않는다.

따라서 `submit` 이벤트에서 브라우저의 기본 제출 동작을 막는다.

기본 관계:

```text
submit event
        ↓
event.preventDefault()
        ↓
페이지 이동 / 실제 전송 방지
        ↓
JavaScript validation 계속 실행
```

`preventDefault()`를 단순히 외워서 사용하는 것이 아니라, **브라우저의 기본 동작을 왜 막는지** 설명할 수 있어야 한다.

---

### 2.4 입력값 읽기

JavaScript에서 최소한 다음 입력값을 읽는다.

```text
Name input value
Email input value
Message textarea value
```

사용자가 공백만 입력한 경우를 빈 값으로 취급할 수 있도록 필요한 경우 문자열 앞뒤 공백을 제거한다.

정확한 API 문법은 구현 과정에서 확인한다.

핵심은 다음 관계다.

```text
DOM input element
        ↓
현재 value 읽기
        ↓
검증 조건에 사용
```

---

### 2.5 필수값 검사

다음 필드는 빈 값으로 제출할 수 없다.

```text
Name
Email
Message
```

각 필드에 대해 최소한 다음 상태를 구분한다.

```text
값 있음
→ 다음 검사 진행 또는 valid

값 없음
→ invalid
→ 해당 필드 근처에 오류 메시지 표시
```

오류 메시지는 사용자가 어떤 입력을 수정해야 하는지 알 수 있는 위치에 표시한다.

단순히 Console에 오류를 출력하는 것으로 완료하지 않는다.

---

### 2.6 이메일 형식 검사

Email 필드는 값이 존재하는 것만으로 완료하지 않는다.

이메일 형식이 유효한지 추가로 확인한다.

기본 흐름:

```text
Email 값 없음
→ 필수값 오류

Email 값 있음
→ 이메일 형식 확인

형식 유효
→ valid

형식 무효
→ email 오류 메시지
```

B1-1 기준 문서는 **이메일 형식 검증이 존재해야 한다는 요구사항까지 정의하며, 정확한 검증 알고리즘이나 정규식을 지정하지 않는다.**

따라서 이 프로젝트에서는 복잡한 RFC 수준 이메일 검증을 구현하지 않는다.

현재 미션에서 일반적인 이메일 입력 오류를 판단할 수 있는 단순하고 읽기 쉬운 검증 방식을 사용한다.

---

### 2.7 Validation 상태

각 입력 필드는 최소한 다음 두 상태로 이해한다.

```text
valid
invalid
```

Form 전체는 제출 시점에 다음과 같이 판단할 수 있다.

```text
하나 이상의 invalid field 존재
→ form invalid

모든 field valid
→ form valid
```

복잡한 상태 객체나 상태 관리 라이브러리는 사용하지 않는다.

핵심은 다음 질문에 답할 수 있어야 한다.

```text
현재 어떤 필드가 왜 invalid인가?
모든 필드가 valid한가?
```

---

### 2.8 필드별 오류 메시지

검증에 실패한 필드에는 해당 필드 근처에 오류 메시지를 표시한다.

예:

```text
Name
[             ]
이름을 입력하세요.

Email
[             ]
올바른 이메일 형식을 입력하세요.
```

정확한 문구와 class 이름은 실제 구현에서 결정한다.

오류 메시지는 validation 결과에 따라 DOM에서 표시되거나 내용이 변경되어야 한다.

JavaScript에서 화면 디자인 전체를 직접 작성하지 않는다.

기본 역할:

```text
JavaScript
→ validation 판단
→ 오류 상태 / 메시지 DOM 변경

CSS
→ 오류 상태의 시각 표현
```

---

### 2.9 오류 상태 시각 표현

필요하면 invalid field를 시각적으로 구분한다.

예:

```text
오류 메시지 표시
입력 테두리 또는 관련 텍스트 상태 변경
```

정확한 디자인은 자유롭게 정할 수 있다.

단, 색상이나 장식을 복잡하게 만드는 것이 목적은 아니다.

사용자가 **어떤 필드에 문제가 있는지 알 수 있는 정도**면 충분하다.

CSS class를 이용하여 상태를 표현하는 방식을 기본으로 한다.

---

### 2.10 성공 메시지

모든 입력값이 검증을 통과하면 Contact 영역에 성공 메시지를 표시한다.

예:

```text
모든 입력값 valid
        ↓
Form 전체 valid
        ↓
성공 메시지 표시
```

이 성공 메시지는 **실제 이메일이나 데이터 전송 성공을 의미하지 않는다.**

v0.6 / v1.0에서는 외부 전송을 하지 않으므로 의미는 다음과 같다.

```text
입력값이 현재 클라이언트 validation을 통과했다.
```

실제 전송 성공 / 실패 상태는 v1.2의 범위다.

---

### 2.11 `input` 이벤트

B1-1 최종 JavaScript 범위에는 `input` 이벤트가 포함된다.

v0.6에서는 사용자가 오류가 발생한 필드의 값을 수정할 때 필요한 범위에서 `input` 이벤트를 사용한다.

기본 예:

```text
submit
→ Email invalid
→ 오류 메시지 표시

사용자가 Email 수정
→ input event
→ 해당 필드 다시 확인
→ valid해지면 오류 상태 해제
```

모든 키 입력마다 Form 전체를 복잡하게 재검증할 필요는 없다.

`input` 이벤트는 **사용자가 잘못된 값을 수정했을 때 피드백을 갱신하는 정도**로 사용한다.

---

### 2.12 HTML 기본 Validation과 JavaScript Validation의 관계

기존 Email 입력은 의미에 맞게 다음 구조를 유지할 수 있다.

```html
<input type="email">
```

`required` 속성의 사용 여부는 B1-1 기준 문서에서 구현 방식까지 고정하지 않는다.

이 프로젝트의 핵심 학습 목표는 다음 JavaScript 흐름을 직접 이해하는 것이다.

```text
submit event
→ preventDefault()
→ value 읽기
→ 조건 판단
→ 오류 / 성공 DOM 렌더링
```

따라서 브라우저 기본 validation UI가 JavaScript 검증 흐름을 가려 버리지 않도록 구현 방식을 선택한다.

기본 원칙:

```text
HTML
→ 입력의 의미와 Form 구조 담당

JavaScript
→ 이번 버전의 validation 판단과 사용자 메시지 담당
```

`required` 또는 브라우저 기본 validation 기능을 함께 사용할 경우에도 **사용자에게 서로 다른 두 종류의 오류 UI가 중복되어 나타나지 않도록 한다.**

---

### 2.13 오류 상태 초기화와 갱신

여러 번 Submit해도 이전 오류가 잘못 남아 있거나 새로운 오류와 중복되지 않아야 한다.

예:

```text
첫 Submit
→ Name 오류
→ Email 오류

사용자 수정

두 번째 Submit
→ Name valid
→ Email valid

결과
→ 이전 오류 메시지 제거
→ 성공 메시지 표시
```

반대로 성공 메시지가 표시된 뒤 사용자가 다시 잘못된 값을 입력하고 Submit했다면 성공 상태가 그대로 남아 있어서는 안 된다.

현재 입력값을 기준으로 UI를 다시 갱신해야 한다.

---

### 2.14 기존 기능과의 공존

Form validation을 추가해도 v0.4와 v0.5에서 구현한 기존 기능이 계속 정상 동작해야 한다.

확인 대상:

```text
Hamburger menu
Navigation / CTA 내부 이동
부드러운 스크롤
Scroll-to-Top
Navigation scroll style
Theme Toggle
Light / Dark theme
localStorage theme 복원
```

Form 오류 상태와 성공 메시지는 light / dark theme 모두에서 읽을 수 있어야 한다.

---

## 3. 목표 설계

v0.6 완료 시 전체 학습 구조는 다음과 같다.

```text
HTML 구조                    ← v0.1
        ↓
CSS 기본 표현                ← v0.2
        ↓
반응형 레이아웃              ← v0.3
        ↓
DOM / Event                  ← v0.4
        ↓
Theme State / localStorage   ← v0.5
        ↓
Form Input
        ↓
submit / input Event
        ↓
입력값 읽기
        ↓
Validation 조건 판단
        ↓
필드별 valid / invalid 상태
        ↓
오류 또는 성공 DOM 렌더링
```

Submit 시 기본 흐름:

```text
사용자 Submit
        ↓
submit event
        ↓
preventDefault()
        ↓
Name / Email / Message 값 읽기
        ↓
각 필드 검사
        ↓
하나라도 invalid
→ 필드별 오류 UI

모두 valid
→ 오류 UI 제거
→ 성공 메시지
```

사용자가 오류를 수정하는 흐름:

```text
invalid field 수정
        ↓
input event
        ↓
해당 값 다시 확인
        ↓
valid해짐
        ↓
해당 오류 상태 해제
```

v0.5와 연결하면 다음 차이를 확인할 수 있다.

```text
v0.5
사용자 click
→ theme 상태 변경
→ theme UI 렌더링
→ 상태 저장

v0.6
사용자 input / submit
→ 입력값 검사
→ validation 상태 결정
→ 오류 / 성공 UI 렌더링
```

v0.6에서는 상태를 저장하지 않는다.

Form 입력이나 validation 결과를 `localStorage`에 저장하지 않는다.

## 4. 새롭게 배우는 개념

### 4.1 Form Event

Form은 단순히 input과 button을 모아 둔 화면이 아니라 사용자 입력을 하나의 제출 동작으로 처리할 수 있는 구조라는 것을 이해한다.

이번 버전에서 핵심 이벤트는 다음 두 가지다.

```text
submit
input
```

---

### 4.2 `submit` Event

`submit`은 Form이 제출될 때 발생하는 이벤트다.

제출 버튼의 `click`과 구분한다.

핵심 관계:

```text
button click 등으로 제출 시도
        ↓
form submit
        ↓
submit handler
```

현재 기능이 **버튼 자체의 클릭 처리**가 아니라 **Form 제출 처리**이므로 Form의 `submit` 이벤트를 기준으로 구현한다.

---

### 4.3 Event Object

이벤트 핸들러가 발생한 이벤트에 대한 정보를 받을 수 있다는 것을 이해한다.

이번 버전에서는 주로 `preventDefault()`를 사용하기 위해 event object를 다룬다.

Event object 전체 API를 학습하지 않는다.

---

### 4.4 `event.preventDefault()`

브라우저가 이벤트에 대해 기본으로 수행하려는 동작을 막을 수 있음을 이해한다.

현재 Form에서는 다음 목적이다.

```text
기본 Form 제출
→ 페이지 이동 또는 전송 가능

preventDefault()
→ 기본 제출 중단
→ 현재 페이지에서 JavaScript validation 수행
```

---

### 4.5 Input Value

Form 요소는 사용자가 현재 입력한 값을 가지고 있으며 JavaScript에서 그 값을 읽을 수 있음을 이해한다.

```text
input / textarea DOM 요소
        ↓
현재 value
        ↓
validation 입력 데이터
```

---

### 4.6 문자열 공백 처리

사용자가 다음처럼 입력했을 때를 생각한다.

```text
"     "
```

문자 자체는 존재하지만 실제 내용은 없는 입력일 수 있다.

필요한 경우 앞뒤 공백을 제거한 뒤 빈 값인지 검사한다.

문자열 API 전체를 학습하지 않는다.

현재 validation에서 필요한 범위만 이해한다.

---

### 4.7 조건문과 Validation

v0.4에서 스크롤 위치에 따라 UI를 바꾸기 위해 조건문을 사용했다.

v0.6에서는 입력값을 판단하기 위해 사용한다.

예:

```text
값이 비어 있는가?
→ 오류

그렇지 않은가?
→ 다음 검사
```

Email에는 조건이 하나 더 존재한다.

```text
값이 있는가?
        ↓
이메일 형식이 유효한가?
```

---

### 4.8 Validation

Validation은 입력값이 현재 기능이 요구하는 조건을 만족하는지 확인하는 과정이라는 수준에서 이해한다.

현재 조건:

```text
Name
→ 비어 있지 않음

Email
→ 비어 있지 않음
→ 이메일 형식 유효

Message
→ 비어 있지 않음
```

복잡한 보안 검증, 서버 검증, 데이터 정제 전체로 학습 범위를 확대하지 않는다.

---

### 4.9 필드 상태와 Form 상태

개별 필드와 Form 전체의 상태를 구분한다.

```text
Name valid
Email invalid
Message valid

        ↓
Form 전체 invalid
```

반대로:

```text
Name valid
Email valid
Message valid

        ↓
Form 전체 valid
```

Form 전체 상태는 각 필드의 결과로 결정된다는 것을 이해한다.

---

### 4.10 Validation State → Rendering

이번 버전에서 가장 중요한 구조다.

```text
입력값
        ↓
validation 상태
        ↓
DOM 변경
        ↓
사용자 피드백
```

예:

```text
Email invalid
→ 이메일 오류 메시지 표시

Email valid
→ 이메일 오류 메시지 제거
```

상태가 단순한 내부 값으로 끝나는 것이 아니라 화면에 연결되어야 한다.

---

### 4.11 `textContent`

오류 또는 성공 메시지의 텍스트를 DOM에서 변경할 때 사용할 수 있다.

v0.4에서 배운 DOM 변경을 Form 피드백에 적용한다.

동적으로 복잡한 HTML 구조를 생성하는 것은 아직 핵심이 아니다.

`innerHTML`을 사용할 이유가 없다면 단순 메시지 변경에는 `textContent`를 우선 고려한다.

---

### 4.12 CSS Class와 오류 상태

v0.4에서 class가 UI 상태를 표현할 수 있음을 배웠다.

v0.6에서도 같은 원리를 사용할 수 있다.

```text
JavaScript
→ invalid class 추가

CSS
→ invalid 상태 표현
```

Theme의 `data-theme`처럼 모든 상태를 attribute로 통일해야 하는 것은 아니다.

현재 기능에서 읽기 쉬운 방식을 사용한다.

---

### 4.13 `input` Event

사용자가 input 또는 textarea의 값을 변경할 때 발생하는 이벤트임을 이해한다.

이번 버전에서는 주로 다음 용도로 사용한다.

```text
사용자가 invalid 값을 수정
→ input event
→ 현재 오류 상태 갱신
```

`input` 이벤트를 이용한 복잡한 실시간 Form 시스템으로 확대하지 않는다.

---

### 4.14 클라이언트 Validation의 한계

현재 validation은 브라우저 안에서 실행되는 **사용자 경험을 위한 클라이언트 검증**이다.

이 단계에서는 실제 서버가 없으므로 서버 측 validation을 구현하지 않는다.

또한 성공 메시지는 실제 데이터 전송 성공을 의미하지 않는다.

이 차이를 설명할 수 있어야 한다.

---

### 4.15 DevTools를 이용한 Form 확인

Form validation이 예상대로 동작하지 않을 때 다음을 확인할 수 있어야 한다.

```text
Console 오류
선택한 Form / input DOM 요소
입력 요소의 현재 value
오류 class 추가 / 제거 여부
오류 메시지 DOM 내용
```

문제가 발생했다고 전체 코드를 바로 다시 작성하지 않는다.

## 5. 완료 / 검증 기준

### 5.1 Form 구조 유지

다음 필드가 모두 존재한다.

```text
Name
Email
Message
Submit
```

각 입력 요소의 label 연결이 유지된다.

---

### 5.2 `submit` 이벤트

Form의 `submit` 이벤트가 `addEventListener()`로 연결되어 있다.

inline event handler를 사용하지 않는다.

제출 버튼 click만을 기준으로 전체 Form validation을 구현하지 않는다.

---

### 5.3 기본 제출 방지

Submit 시 `event.preventDefault()`가 적용되어 실제 페이지 이동이나 외부 전송이 발생하지 않는다.

왜 기본 제출을 막는지 설명할 수 있다.

---

### 5.4 필수값 검증

각 필드를 비운 상태로 Submit했을 때 다음 필드에 오류가 표시된다.

```text
Name
Email
Message
```

공백만 입력한 경우도 정상적인 값으로 처리되지 않는다.

---

### 5.5 이메일 형식 검증

Email에 명백히 잘못된 형식을 입력했을 때 Email 오류 메시지가 표시된다.

올바른 형식의 Email을 입력하면 해당 오류가 사라진다.

현재 이메일 검증 방식이 어떤 조건을 확인하는지 설명할 수 있다.

---

### 5.6 필드별 오류 메시지

오류 메시지가 해당 입력 필드 근처에 표시된다.

사용자가 어느 필드를 수정해야 하는지 구분할 수 있다.

모든 오류를 하나의 일반 메시지만으로 처리하지 않는다.

---

### 5.7 오류 상태 갱신

잘못된 값을 수정한 뒤 다시 검증하면 이전 오류 상태가 정상적으로 제거된다.

오류 메시지가 중복 생성되거나 계속 누적되지 않는다.

---

### 5.8 `input` 이벤트

오류가 발생한 필드를 수정할 때 필요한 범위에서 `input` 이벤트를 통해 오류 UI를 갱신할 수 있다.

`input` 이벤트가 어떤 상황에서 발생하고 무엇을 갱신하는지 설명할 수 있다.

---

### 5.9 성공 상태

다음 조건을 모두 만족한 뒤 Submit하면 성공 메시지가 표시된다.

```text
Name valid
Email valid
Message valid
```

성공 메시지가 실제 외부 전송 성공을 의미하지 않는다는 점을 이해한다.

---

### 5.10 성공 / 오류 상태 전환

다음 흐름이 모순 없이 동작한다.

```text
invalid Submit
→ 오류 표시

값 수정
→ 오류 해제

valid Submit
→ 성공 표시
```

필요하면 반대 흐름도 확인한다.

```text
성공 상태
→ 값 다시 잘못 입력
→ Submit
→ 성공 상태 제거
→ 오류 표시
```

---

### 5.11 실제 전송 없음

다음이 구현되어 있지 않다.

```text
Formspree
EmailJS
fetch를 이용한 Form 전송
백엔드 API 전송
```

Form validation이 끝나도 외부로 데이터가 전송되지 않는다.

---

### 5.12 Light / Dark Theme 확인

light와 dark theme 모두에서 다음이 읽기 쉬워야 한다.

```text
input
textarea
오류 메시지
오류 상태
성공 메시지
```

v0.6 때문에 v0.5의 Theme Toggle이나 localStorage 복원이 깨지지 않는다.

---

### 5.13 모바일 / 데스크톱 확인

모바일과 데스크톱에서 Form을 입력하고 Submit할 수 있다.

오류 메시지 때문에 Form 레이아웃이 viewport 밖으로 벗어나거나 심하게 깨지지 않는다.

다음을 검토한다.

```text
Form submit이 addEventListener로 연결되어 있는가
preventDefault의 목적을 설명할 수 있는가
Name / Email / Message 값을 읽는 코드가 명확한가
빈 값 검사가 동작하는가
Email 형식 검사가 동작하는가
오류 메시지가 필드 근처에 표시되는가
오류가 수정 후 정상적으로 제거되는가
성공 메시지는 모든 필드가 valid할 때만 표시되는가
성공 메시지가 실제 전송 성공을 의미하지 않는가
오류 메시지가 반복 Submit마다 중복 생성되지 않는가
input 이벤트가 필요한 범위에서 사용되는가
실제 Form 전송을 선행 구현하지 않았는가
GitHub API를 선행 구현하지 않았는가
Form 값을 localStorage에 저장하지 않았는가
Theme Toggle이 정상 동작하는가
기존 v0.4 인터랙션이 정상 동작하는가
모바일 / 데스크톱에서 Form 레이아웃이 정상인가
Console 오류가 없는가
```

```text
HTML 구조                     완료

기본 DOM 인터랙션             완료
Theme 상태                    완료
localStorage theme 유지       완료

Contact Form submit            동작
preventDefault                 적용
입력값 읽기                   적용
필수값 검사                   적용
Email 형식 검사               적용
필드별 오류 상태              적용
필드별 오류 메시지            적용
input 기반 오류 갱신          적용
validation 성공 메시지        적용

실제 Form 전송                없음
Formspree / EmailJS            없음
GitHub API                     없음
Projects 동적 렌더링          없음
프로젝트 필터                 없음
Intersection Observer          없음
시스템 theme 감지             없음
```

즉,

> **사용자가 입력한 값을 JavaScript가 검사하고, 각 필드의 validation 상태에 따라 오류 또는 성공 UI를 렌더링하지만 실제 데이터 전송은 하지 않는 Contact Form**

이 v0.6의 최종 산출물이다.
