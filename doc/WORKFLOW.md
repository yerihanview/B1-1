# B1-1 Development & Learning Workflow

## 기준 문서와 Sources

프로젝트의 확정된 설계 및 학습 문서는 ChatGPT Project의 Sources에 등록한다.

이후 ChatGPT와 진행하는 설계, 버전 명세 작성, 학습 계획 수립 및 부합성 검토는 **Sources에 등록된 최신 확정 문서를 기준으로 한다.**

기준 문서에는 다음이 포함된다.

* B1-1 미션 원문
* `WORKFLOW.md`
* `final-design.md`
* `extended-design.md`
* `roadmap.md`
* 확정된 각 `vX.X.md`

대화 중 과거에 제안하거나 논의한 내용과 Sources의 최신 문서가 다를 경우에는 **Sources의 최신 확정 문서를 우선한다.**

새로운 문서를 작성하거나 기존 문서를 수정할 때는 관련 Sources 문서와의 부합성을 확인한다.

초안이나 폐기된 버전은 Sources의 기준 문서로 유지하지 않는다. 문서의 변경 이력은 Git repository에서 관리하고, Sources에는 현재 기준으로 사용할 최신 확정본을 둔다.


## 1. 문서 목적

이 문서는 B1-1 미션을 진행하는 동안 적용할 **개발·학습 운영 원칙**을 정의한다.

B1-1의 목표는 단순히 동작하는 웹사이트를 완성하는 것이 아니다.

순수 HTML, CSS, JavaScript를 사용하여 직접 구현하면서 다음 흐름을 이해하는 것이 핵심이다.

> 사용자 이벤트 → 상태 변경 → DOM 업데이트 → 화면 변화

따라서 AI가 결과물을 대신 완성하는 방식이 아니라, 최종 목표를 먼저 설계하고 이를 작은 단계로 나누어 직접 코드의 변화를 확인하며 개발한다.

이 문서는 프로젝트 전체에서 공통으로 적용하며, 개별 버전의 구체적인 구현 요구사항은 `docs/vX.X.md`에서 관리한다.

---

## 2. B1-1 개발 원칙

### 2.1 최종 목표를 먼저 설계한다

개발을 시작하기 전에 B1-1의 최종 산출물이 어떤 구조와 기능을 가져야 하는지 먼저 정의한다.

B1-1 기본 완료 목표인 `v1.0`의 최종 설계는 `docs/final-design.md`에서 관리한다.

`v1.0` 이후 확장 목표인 `v1.3`의 추가 설계는 `docs/extended-design.md`에서 관리한다.

개발 중 새로운 아이디어가 생기더라도 최종 설계 또는 확장 설계를 즉시 변경하지 않는다.

필요한 경우 먼저 설계 변경 여부를 검토한 뒤 문서를 수정한다.

---

### 2.2 최종 결과물을 점진적으로 개발한다

최종 결과물을 한 번에 구현하지 않는다.

완성까지 필요한 과정을 여러 버전으로 나누고, 각 버전은 이전 버전 위에 필요한 개념과 기능을 추가하는 방식으로 진행한다.

전체 버전 순서와 각 버전의 목적은 `docs/roadmap.md`에서 관리한다.

현재 버전에서 요구하지 않는 기능을 미리 구현하지 않는다.

---

### 2.3 현재 버전의 범위를 우선한다

각 버전 개발은 해당 버전 문서에 정의된 범위만을 대상으로 한다.

각 버전 문서에는 반드시 다음 항목이 포함되어야 한다.

- 요구사항
- 목표 설계
- 새롭게 배우는 개념
- 완료/검증 기준
- 이번 버전에서 다루지 않을 범위

현재 버전에서 필요하지 않은 다음 단계의 기술이나 기능은 구현하지 않는다.

코드를 더 고급스럽게 만드는 것보다 **현재 단계의 학습 목표를 정확하게 이해하는 것**을 우선한다.

---

### 2.4 기본 완료 범위와 확장 과제를 분리한다

B1-1의 필수 요구사항과 보너스 과제를 명확히 구분한다.

단, **프로젝트 필터링은 B1-1 원문에서는 선택 과제이지만 이 프로젝트에서는 학습 목표를 위해 `v1.0` 필수 범위로 승격한다.**

따라서 `v1.0`은 다음을 완료한 기준선이다.

- B1-1의 필수 요구사항 전체
- 프로젝트 필터링

나머지 보너스 과제는 `v1.0` 완료 이후 별도 확장 버전으로 구현한다.

버전 체계는 다음 원칙을 따른다.

```text
v0.x
    v1.0 목표를 점진적으로 구현하는 단계

v1.0
    B1-1 필수 요구사항 전체
    + 프로젝트 필터링 완료

v1.1
    Hero 타이핑 효과 추가

v1.2
    실제 폼 전송 추가

v1.3
    시스템 다크 모드 감지 추가
    → 현재 계획된 확장 기능 전체 완료
```

`v1.0`은 B1-1 기본 완료 기준이며, `v1.3`은 현재 계획된 확장 기능까지 모두 구현한 완료 기준이다.

`v1.0` 이후의 확장 기능은 `docs/extended-design.md`를 기준으로 설계한다.

확장 기능의 실제 구현 순서와 각 버전의 범위는 `roadmap.md`에서 관리한다.

현재 버전에서 요구하지 않는 확장 기능을 선행 구현하지 않는다.

## 3. 학습 범위 원칙

### 3.1 B1-1에 필요한 개념만 학습한다

학습 범위는 B1-1 요구사항을 기준으로 결정한다.

B1-1에서 직접 사용하거나 이해해야 하는 개념을 우선하고, 이후 미션에서 배울 기술은 필요 이상으로 선행 학습하지 않는다.

특히 B1-1에서는 다음 영역을 중심으로 학습한다.

- HTML 구조와 시맨틱 마크업
- CSS 레이아웃과 반응형 디자인
- Flexbox와 Grid
- DOM 선택과 조작
- 브라우저 이벤트
- JavaScript의 기본 상태 처리
- 폼 유효성 검사
- `fetch`
- `async/await`
- 비동기 요청의 로딩 / 성공 / 에러 / 빈 상태
- `localStorage`
- Intersection Observer
- GitHub API
- GitHub Pages 배포

ES6+ 문법은 B1-1에서 실제로 요구하거나 사용하는 범위에 한정한다.

필수적으로 다룰 문법은 다음과 같다.

- 화살표 함수
- 템플릿 리터럴
- 구조분해 할당
- `map`
- `forEach`
- `filter`

`filter`는 프로젝트 필터링 구현에 사용하며 `v1.0` 학습 범위에 포함한다.

React, Vue 등의 프레임워크 학습은 이 미션의 범위에 포함하지 않는다.

---

### 3.2 구현 전에 필요한 개념을 확인한다

새로운 기능을 구현하기 전에 그 기능을 이해하는 데 필요한 핵심 개념을 먼저 확인한다.

단, 개념 학습 자체를 별도의 장기 과정으로 만들지 않는다.

목표는 다음 질문에 답할 수 있는 수준이다.

- 이 기능은 무엇을 하는가?
- 왜 필요한가?
- 어떤 코드가 핵심 역할을 하는가?
- 사용자 동작이 어떤 과정을 거쳐 화면 변화로 이어지는가?

세부 문법이나 API는 필요할 때 확인한다.

---

### 3.3 설명할 수 있어야 완료로 본다

AI가 만든 코드가 정상 동작하는 것만으로는 학습 완료로 보지 않는다.

중요한 코드에 대해서는 최소한 다음을 설명할 수 있어야 한다.

- 이 코드가 왜 존재하는가?
- 입력 또는 이벤트는 무엇인가?
- 어떤 상태가 바뀌는가?
- DOM이 어떻게 변경되는가?
- 화면에서 어떤 결과가 나타나는가?

B1-1의 핵심 기능에서는 특히 다음 흐름을 확인한다.

> 이벤트 → 상태 변경 → 렌더링

B1-1의 필수 요구사항에서는 최소 3가지 이상의 상태→렌더링 흐름을 실제 코드에서 확인한다.

대표적인 흐름은 다음과 같다.

```text
다크 모드
사용자 이벤트
→ theme 상태 변경
→ DOM 또는 스타일 변경
→ 화면 테마 변경

GitHub API
API 요청
→ loading / success / error / empty 상태
→ Projects 영역 DOM 렌더링

폼
입력 또는 submit 이벤트
→ validation 상태 변경
→ 에러 또는 성공 UI 렌더링
```

## 4. 개발 환경

기본 개발 환경은 다음과 같다.

- 로컬 PC
- VS Code
- VS Code의 AI 코딩 도구
- Live Server
- Git
- GitHub
- 최신 Chrome

코드는 로컬에서 직접 실행하고 브라우저에서 확인한다.

B1-1에서는 핵심 기능 구현을 대체하는 다음 프레임워크 및 라이브러리를 사용하지 않는다.

- React
- Vue
- jQuery
- Bootstrap
- Tailwind CSS

기본 구현은 순수 HTML, CSS, JavaScript로 작성한다.

단, B1-1에서 허용하는 다음 도구는 사용할 수 있다.

- Font Awesome
- Google Fonts

허용된 도구를 사용하더라도 HTML/CSS/JavaScript의 핵심 구현을 대신하도록 사용하지 않는다.

## 5. AI 역할 분담

### 5.1 ChatGPT의 역할

ChatGPT는 프로젝트의 **설계·학습·검증 파트너**로 사용한다.

주요 역할은 다음과 같다.

- 최종 산출물 설계
- 버전 로드맵 설계
- 버전별 요구사항 작성
- 선수 개념 정리
- 학습 범위 통제
- 완료 기준과 검증 방법 설계
- 구현 결과에 대한 개념적 검토
- 다음 버전으로 넘어가도 되는지 점검

ChatGPT가 직접 전체 코드를 작성하는 것을 기본 개발 방식으로 삼지 않는다.

---

### 5.2 VS Code AI의 역할

VS Code AI는 **실제 코드 작성 및 수정 보조 도구**로 사용한다.

주요 역할은 다음과 같다.

- 현재 Task에 필요한 코드 작성
- 기존 코드의 작은 수정
- 오류 원인 분석
- 필요한 코드 설명
- 리팩터링 보조

VS Code AI에게 현재 버전 전체를 한 번에 구현하도록 요청하지 않는다.

---

## 6. Task 단위 개발 방식

각 버전은 다시 여러 개의 작은 Task로 나누어 진행한다.

하나의 Task는 가능하면 **한 가지 명확한 변화**만 포함한다.

예:

- HTML에 About 섹션 추가
- 네비게이션을 Flexbox로 배치
- 모바일 햄버거 버튼 추가
- 버튼 클릭 이벤트 연결
- 다크 모드 상태 저장
- GitHub API 호출 함수 작성
- 로딩 상태 UI 추가

다음과 같은 요청은 피한다.

> “v0.3 전체를 구현해줘.”

대신 다음처럼 요청한다.

> “현재 v0.3 요구사항 중 햄버거 버튼의 HTML 구조만 추가해줘. 아직 JavaScript 동작은 구현하지 마.”

Task가 작아야 코드 변경의 이유와 결과를 직접 확인할 수 있다.

---

## 7. Task 실행 절차

각 Task는 다음 순서로 진행한다.

### 1. Task 확인

현재 버전 문서에서 이번에 구현할 요구사항을 확인한다.

확인할 내용:

- 무엇을 추가하거나 수정하는가?
- 이번 Task에서 새로 사용하는 개념은 무엇인가?
- 무엇은 아직 구현하지 않는가?

---

### 2. VS Code AI에 요청

AI에게 현재 Task의 범위를 명확하게 전달한다.

가능하면 다음 정보를 포함한다.

- 현재 버전
- 이번 Task의 목표
- 수정 대상 파일
- 반드시 지켜야 할 제약
- 아직 구현하면 안 되는 범위

AI가 필요 이상의 기능을 추가하지 못하도록 범위를 제한한다.

---

### 3. Diff 확인

AI가 코드를 수정하면 먼저 변경된 diff를 확인한다.

확인할 내용:

- 어떤 파일이 변경되었는가?
- 요청하지 않은 파일이 변경되었는가?
- 요청하지 않은 기능이 추가되었는가?
- 기존 코드를 불필요하게 크게 수정했는가?

범위를 벗어난 수정은 적용하지 않거나 되돌린다.

---

### 4. 코드 확인

변경된 코드를 직접 읽는다.

최소한 다음을 확인한다.

- 새 코드의 위치
- 주요 HTML 요소
- 주요 CSS 규칙
- 주요 JavaScript 변수와 함수
- 이벤트가 연결되는 위치
- 상태가 변경되는 위치
- DOM이 변경되는 위치

이해되지 않는 부분은 AI에게 해당 코드만 설명하도록 요청한다.

---

### 5. 브라우저 확인

Live Server로 실제 결과를 확인한다.

기능에 따라 다음을 확인한다.

- 화면이 의도한 구조로 표시되는가?
- 클릭이 정상 동작하는가?
- 입력에 따라 화면이 바뀌는가?
- 스크롤 동작이 정상인가?
- 새로고침 이후 상태가 유지되는가?
- 모바일/태블릿/데스크톱에서 레이아웃이 정상인가?
- 정상 상태뿐 아니라 에러나 빈 상태도 확인했는가?

코드만 보고 완료로 판단하지 않는다.

---

### 6. 이해 확인

Task를 완료하기 전에 다음 질문에 답할 수 있는지 확인한다.

- 무엇을 구현했는가?
- 핵심 코드는 어디에 있는가?
- 왜 이렇게 구현했는가?
- 사용자 행동이 화면 변화로 어떻게 연결되는가?

설명할 수 없다면 해당 부분을 다시 확인한 후 완료 처리한다.

---

## 8. AI가 범위를 벗어났을 때의 처리

VS Code AI가 현재 Task에서 요구하지 않은 기능을 추가할 수 있다.

다음과 같은 경우 그대로 받아들이지 않는다.

- 다음 버전 기능을 미리 구현
- `v1.0` 이전에 `v1.1` 이후의 확장 기능을 구현
- 새로운 라이브러리 추가
- 필요 없는 추상화
- 과도한 리팩터링
- 아직 배우지 않은 기술로 기존 코드를 교체
- 현재 요구사항과 관계없는 UI 개선

이 경우 AI에게 현재 Task 범위만 남기도록 수정하도록 요청하거나 변경을 되돌린다.

**더 많은 코드가 더 좋은 결과라는 기준을 사용하지 않는다.**

## 9. 버전 완료 절차

한 버전의 모든 Task가 끝났다고 바로 다음 버전으로 넘어가지 않는다.

버전 문서의 완료/검증 기준을 다시 확인한다.

최소한 다음을 점검한다.

### 기능 검증

- 버전에서 요구한 기능이 모두 동작하는가?
- 브라우저에서 직접 확인했는가?

### 코드 검증

- 현재 버전에서 요구하지 않은 코드가 들어가 있지 않은가?
- HTML/CSS/JavaScript의 역할이 불필요하게 섞여 있지 않은가?

### 학습 검증

- 이번 버전에서 새롭게 배운 핵심 개념을 설명할 수 있는가?
- 주요 코드가 어떤 역할을 하는지 설명할 수 있는가?

### 범위 검증

- 다음 버전의 요구사항을 선행 구현하지 않았는가?
- `v1.0` 이전에 `v1.1` 이후의 확장 기능을 구현하지 않았는가?
- B1-1과 현재 프로젝트 목표에서 요구하지 않는 기술을 불필요하게 추가하지 않았는가?

모든 기준을 만족하면 해당 버전을 완료한다.

## 10. Git 및 GitHub 운영

소스 코드와 개발·학습 문서는 하나의 GitHub repository에서 함께 관리한다.

기본 구조는 다음과 같이 유지한다.

```text
project-root/
├── README.md
├── index.html
├── css/
├── js/
├── images/
└── docs/
    ├── WORKFLOW.md
    ├── final-design.md
    ├── extended-design.md
    ├── roadmap.md
    ├── v0.1.md
    ├── v0.2.md
    └── ...
```

`README.md`와 `docs/`의 역할은 구분한다.

### README.md

외부 사용자 또는 평가자에게 프로젝트를 설명한다.

최종적으로 B1-1에서 요구하는 다음 내용을 포함한다.

- 프로젝트 설명
- 사용 기술
- 배포 URL
- 스크린샷
- 필요한 동작 기준값 등 공개할 설정 정보

### docs/

개발과 학습을 위한 내부 설계 기록을 관리한다.

다음을 포함한다.

- 개발 운영 방식
- v1.0 최종 설계
- v1.3 확장 설계
- 버전 로드맵
- 버전별 요구사항
- 학습 목표
- 완료 및 검증 기준

## 11. Commit / Push / Tag 원칙

Task 진행 중에는 필요에 따라 commit할 수 있다.

단, **버전 완료 시점에는 반드시 코드와 해당 버전 문서가 서로 일치하는 상태**를 만든다.

버전 완료 절차:

1. 버전 요구사항 최종 확인
2. 코드 검증
3. 브라우저 검증
4. 학습 이해 확인
5. 관련 문서 상태 확인
6. commit
7. GitHub push
8. 버전 tag 생성
9. tag push

예:

```bash
git add .
git commit -m "Complete v0.1"
git push

git tag v0.1
git push origin v0.1
```

Tag는 해당 버전이 실제로 완료되었을 때만 생성한다.

`v1.0` tag는 B1-1 필수 요구사항과 프로젝트 필터링이 모두 완료되고 검증된 시점에 생성한다.

`v1.1`, `v1.2`, `v1.3` tag는 각각의 확장 기능이 독립적으로 완료되고 검증되었을 때 생성한다.

`v1.3` tag는 현재 계획된 모든 확장 기능이 완료된 기준점이다.

## 12. 문제 해결 원칙

오류가 발생하면 AI에게 즉시 전체 코드를 다시 작성시키지 않는다.

다음 순서로 문제를 확인한다.

1. 어떤 동작이 예상과 다른지 확인
2. 브라우저 콘솔 확인
3. 관련 코드 위치 확인
4. 원인을 추정
5. 필요한 부분만 AI에게 질문
6. 최소한의 코드 수정
7. 다시 검증

오류 수정 역시 하나의 학습 과정으로 취급한다.

## 13. 설계 변경 원칙

개발 중 기존 설계를 바꿔야 할 이유가 생길 수 있다.

이 경우 코드부터 임의로 변경하지 않는다.

변경이 다음 중 어디에 해당하는지 먼저 판단한다.

- 단순 구현 방식 변경
- 현재 버전 요구사항 변경
- 버전 로드맵 변경
- `v1.0` 최종 설계 변경
- `v1.3` 확장 설계 변경

로드맵, 최종 설계 또는 확장 설계에 영향을 주는 변경이라면 관련 문서를 먼저 수정한 후 구현한다.

코드와 문서가 서로 다른 방향을 가리키는 상태를 만들지 않는다.

## 14. B1-1에서 특히 지켜야 할 기준

B1-1에서는 UI의 화려함보다 웹의 기본 동작 원리를 이해하는 것을 우선한다.

따라서 다음 원칙을 유지한다.

- 순수 HTML/CSS/JavaScript로 구현한다.
- HTML의 시맨틱 구조를 이해한다.
- CSS의 Flexbox와 Grid를 목적에 맞게 사용한다.
- JavaScript 이벤트는 `addEventListener`로 연결한다.
- DOM을 직접 선택하고 변경하는 과정을 이해한다.
- 상태 변화와 화면 변화의 관계를 확인한다.
- 비동기 API의 로딩/성공/에러/빈 상태를 직접 처리한다.
- 기능이 동작하는 것뿐 아니라 왜 동작하는지 설명할 수 있어야 한다.
- B1-1 완료와 현재 프로젝트 목표에 필요하지 않은 고급 기술을 추가하지 않는다.
- 프로젝트 필터링은 `v1.0` 필수 범위로 구현한다.
- `v1.0`을 완료하기 전에는 `v1.1` 이후의 확장 기능을 구현하지 않는다.

## 15. 이 문서의 적용 범위

이 문서는 B1-1 전체 개발 과정에 적용되는 운영 규칙이다.

`v1.0`의 최종 화면과 기능 구조는 `final-design.md`에서 정의한다.

`v1.0` 이후 `v1.3`까지 추가되는 확장 기능은 `extended-design.md`에서 정의한다.

전체 개발 단계는 `roadmap.md`에서 정의한다.

각 단계의 구체적인 개발 내용은 `vX.X.md`에서 정의한다.

문서 간 역할은 다음과 같이 구분한다.

```text
WORKFLOW.md
    └─ 어떻게 개발하고 학습할 것인가

final-design.md
    └─ v1.0에서 무엇을 완성할 것인가

extended-design.md
    └─ v1.0 이후 v1.3까지 무엇을 추가할 것인가

roadmap.md
    └─ 어떤 순서로 완성할 것인가

vX.X.md
    └─ 이번 버전에서 정확히 무엇을 만들고 배울 것인가
```

현재 작업에서는 항상 **현재 버전의 `vX.X.md`를 실행 기준**으로 삼는다.
